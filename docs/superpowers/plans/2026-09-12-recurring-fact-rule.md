# Факт на повторяющееся событие: чьё поле recurring_rule_id — план реализации (ANO-91)

**Цель:** дать возможность отметить оплаченными аренду, ипотеку, подписки — всё, ради чего повторяющиеся правила заводились. Сейчас факт на порождённое правилом событие падает с 500.

**Задача:** [ANO-91](https://linear.app/anotherspace1/issue/ANO-91).

**Стек:** Java 21, Spring Boot 4.0.3, PostgreSQL, Flyway, JUnit 5, Mockito, Testcontainers.

---

## Симптом

```
факт на ОБЫЧНЫЙ плановый расход          -> 200
факт на событие, ПОРОЖДЁННОЕ ПРАВИЛОМ    -> 500
```

Запросы идентичны, отличается только происхождение плана.

## Что установлено чтением кода и живой базы

**Два места во всём бэкенде пишут `recurring_rule_id`, и они дают чистое разбиение:**

| место | что пишет |
|---|---|
| `RecurringEventGenerator:74-75` | `.eventKind(PLAN)` + `.recurringRule(rule)` — только планы, всегда |
| `FinancialEventService:290` | `.recurringRule(plan.getRecurringRule())` на строке с `.eventKind(FACT)` |

Генератор физически не умеет создать FACT — `eventKind` захардкожен, других сборщиков в классе нет.

**Уникальный индекс V16 не различает вид строки:**

```sql
CREATE UNIQUE INDEX uq_events_rule_date_active ON financial_events (recurring_rule_id, date)
    WHERE recurring_rule_id IS NOT NULL AND is_deleted = FALSE;
```

Факт наследует правило родителя. Если его дата совпала с датой родительского плана — конфликт по ключу `(rule_id, date)`, `DataIntegrityViolationException`, 500.

**Живая база подтверждает полную блокировку:**

```
PLAN   522 строки,  331 с правилом
FACT   560 строк,     0 с правилом
```

Ни одного факта с правилом не существует. То есть за всё время ни один повторяющийся платёж не был отмечен оплаченным — ни разу.

## Главное: поле выдано не тому, кому предназначалось

Проверено, кому вообще нужен `recurring_rule_id` **на строке факта**. Ответ — практически никому.

Пять репозиторных запросов по `recurring_rule_id` написаны в предположении, что правило несут только планы: **ни один не фильтрует по `event_kind`**.

| запрос | строка | как отсекает факты |
|---|---|---|
| `findMaxActiveDateByRule` | `:140` | `status='PLANNED'` — факт всегда EXECUTED, отсекается случайно |
| `softDeletePlanEventsByRuleFromDate` | `:148` | то же, несмотря на слово `Plan` в имени |
| `findExecutedDatesByRule` | `:155` | **не отсекает** — факт попадает в множество исполненных дат |
| `findMaxExecutedDateByRule` | `:161` | **не отсекает** |
| `findActiveByRuleAndDate` | `:167` | **не отсекает**, возвращает `Optional` |

Последствие уже лечили симптоматически: `RecurringRuleService:150-153` содержит защитный клэмп с комментарием «lastExec раньше startDate возможен у FACT с ручной датой». То есть авторы знали, что факты засоряют выборку правила.

**Единственный настоящий потребитель правила на факте** — иконка ↻ в тултипе прошедшего месяца (`BaselineTimelineBuilder:507` → `BreakdownItemDto.isRecurring` → `MonthTooltip.tsx:59`). Она сегодня **мертва**: фактов с правилом ноль, значит флаг всегда `false`. И тестом не покрыта.

**Утверждение задачи «наследование нужно, чтобы факт не считался внеплановым» кодом не подтверждается.** Плановость факта несёт `parent_event_id`, а не правило: просрочка считается через `NOT EXISTS` по родителю (`:105-110`, `:204-209`), агрегаты фактов — `GROUP BY parentEventId` (`:68-74`). `PredictionService` правило не читает вовсе.

**«Чтобы факт попадал в отчёты правила»** — проверять не на чем: эндпоинтов и отчётов по правилу в проекте нет, ни один контроллер слова `recurring` не упоминает.

## Два пути починки

### Путь А — не наследовать правило фактом (рекомендую)

Одна строка: убрать `.recurringRule(plan.getRecurringRule())` из `createLinkedFact`.

Тогда `recurring_rule_id` несут **только планы**, и:

* конфликт по индексу становится невозможным **по построению** — факту нечем столкнуться;
* пять запросов выше становятся корректными **автоматически**: факт в них попасть не может, различать `event_kind` незачем;
* защитный клэмп в `RecurringRuleService:150` теряет смысл (оставить, но пометить);
* индекс V16 остаётся как есть и **наконец начинает означать ровно то, что заявлено**: одно правило — один план на дату. Миграция схемы не нужна;
* несколько фактов на один план (заложено дизайном — `COUNT`+`SUM GROUP BY parentEventId`) начинают работать для повторяющихся планов тоже.

Цена: иконка ↻ на прошедших фактах не появится. Она и сейчас не работает; если понадобится — правило достаётся через `parent_event_id` одним джойном.

### Путь Б — сузить индекс до `event_kind='PLAN'`

Миграция V23, наследование остаётся.

**Но одного сужения недостаточно.** После него пара PLAN+FACT на одну дату становится легальной, и `findActiveByRuleAndDate` (`Optional`, без фильтра по виду) вернёт две строки → `NonUniqueResultException` → **500 просто переезжает** в редактирование правила со `scope=FOLLOWING/ALL` (`FinancialEventService:232`). Моки в тестах это скроют.

Значит путь Б — это миграция **плюс** правка трёх запросов (`findActiveByRuleAndDate`, `findExecutedDatesByRule`, `findMaxExecutedDateByRule`), и двусмысленность «чьё это поле» остаётся в коде навсегда.

### Почему А

Дефект не в ограничении, а в том, что **факту выдали поле, которое принадлежит плану**. Путь Б чинит ограничение и оставляет причину; путь А убирает причину, и ограничение начинает быть верным само.

Плюс А снимает риск, а не переносит его: при Б три запроса остаются неправильными-но-недостижимыми, а это ровно тот тип ловушки, который в этом проекте находят раз за разом.

## Что меняется

| файл | правка |
|---|---|
| `service/FinancialEventService.java:290` | убрать наследование правила |
| `V23__clear_rule_on_facts.sql` | обнулить `recurring_rule_id` у существующих FACT-строк |
| `service/RecurringRuleService.java:150` | пометить клэмп как более не нужный, оставить |
| `test/.../FinancialEventServiceTest.java:205-234` | тест фиксирует наследование — переписать на обратное утверждение |

Миграция данных нужна: на стенде таких строк ноль, но на боевой базе владельца могли остаться факты с правилом, записанные когда дата не совпадала. Они продолжат засорять выборки правила.

Форма миграции под мультиюзер: это `UPDATE` по `event_kind`, колонки владельца не касается, переделывать позже не придётся.

## Тесты — каждый со своей мутацией

| тест | уровень | утверждение | мутация |
|---|---|---|---|
| `factOnRecurringPlan_succeeds` | IT Testcontainers | факт на порождённое правилом событие той же датой — **200**, а не 500 | вернуть наследование |
| `factOnRecurringPlan_carriesNoRule` | IT | у созданного факта `recurring_rule_id IS NULL`, а `parent_event_id` проставлен | вернуть наследование |
| `twoFactsOnOneRecurringPlan_bothSucceed` | IT | два частичных платежа на один повторяющийся план проходят | вернуть наследование |
| `ruleRegenerate_ignoresFacts` | IT | факт не подавляет генерацию плана на свою дату | вернуть наследование |
| `V23_clearsRuleOnExistingFacts` | IT | миграция обнуляет правило у FACT и **не трогает** PLAN | убрать `AND event_kind='FACT'` из миграции |

Уровень интеграционный обязателен: дефект живёт в индексе базы, юнит на моках его не увидит — что и доказано существующим тестом `FinancialEventServiceTest:205-234`, который фиксирует наследование и зелёный при полностью сломанном поведении.

1. `mvnw verify` целиком.
2. Каждый тест уронить своей мутацией.
3. Стенд: создать повторяющееся правило, отметить платёж оплаченным той же датой — было 500, ожидается 200.

5. `node tools/ano50-stage34.mjs` — этап журнала и повторяющихся правил.

## Чего не делаем

* Не трогаем индекс V16 — он остаётся и становится корректным.
* Не возвращаем иконку ↻ для фактов. Если понадобится — отдельной задачей через `parent_event_id`.
* Не чиним `findExecutedDatesByRule` и соседей: после А факт туда не попадёт. Отметить в ANO-23 как место, где различие PLAN/FACT выражено неявно.
