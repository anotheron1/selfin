# Возврат сконвертированной хотелки: судьба артефакта — план реализации (ANO-103, вторая половина)

**Цель:** довести ANO-103 до полного обещания спеки. Сейчас сконвертированная хотелка умеет вернуться в OPEN/DISMISSED, но созданный артефакт остаётся всегда — выбора удалить его нет.

**Спека:** `docs/superpowers/specs/2026-05-29-wishlist-planning-design.md:66`:

> «Конверсия — не точка невозврата: `FIXED → OPEN` возможен в любой момент, при этом сконвертированный артефакт **остаётся (или удаляется по явному выбору)**.»

Первая часть фразы исполнена коммитом `51d1720` (миграция V22 + обработчик 409 + guard в `PocketEngine`). Эта задача — про скобки.

**Стек:** Java 21, Spring Boot 4.0.3, PostgreSQL, Flyway, JUnit 5, Testcontainers.

---

## Почему это не косметика

Человек нажал «перевести в план», передумал и вернул хотелку в обсуждение. Хотелка снова в списке — а созданный план продолжает висеть в траектории и есть деньги. То есть **решение отменено наполовину**: в модуле хотелок отмена видна, в кармашке нет.

Это тот же класс, из-за которого ANO-103 и заводилась: из состояния нет выхода. Мы открыли дверь и не убрали за ней стену.

---

## Три решения, которые надо назвать явно

### Решение 1. Флаг, а не отдельная ручка

`WishlistStatusUpdateDto` получает необязательное поле `deleteArtifact`. Отсутствует или `false` — поведение ровно как сейчас, ни один существующий вызов не меняется. `true` — артефакт удаляется, ссылка очищается.

Почему флагом: удаление артефакта не имеет смысла в отрыве от смены статуса. Отдельная ручка позволила бы удалить артефакт, оставив хотелку в FIXED, — то есть создать строку, которая утверждает «я сконвертирована» и ссылается в пустоту.

### Решение 2. Удаление мягкое, как везде в продукте

`is_deleted = true`, не физическое удаление. Согласуется с `FinancialEventService.delete` и с остальной моделью.

### Решение 3 — главное. Отказываемся удалять артефакт, за которым уже стоят деньги

**Это то место, где задача задевает целостность денег, а не интерфейс.**

Артефакт — это либо `PLAN`-событие, либо копилка. За время, пока хотелка была сконвертирована, с ними могло случиться следующее:

| артефакт | что могло случиться | почему нельзя просто удалить |
|---|---|---|
| PLAN-событие | к нему привязаны FACT-записи | удаление плана осиротит факты: траты были реальными, а их родитель исчезнет |
| копилка | в неё переводили деньги | это **ровно ANO-86**: копилка помечается удалённой, движения и событие перевода остаются, деньги для человека уничтожаются |

Поэтому: **если за артефактом есть факты или деньги — отказ 409 с объяснением**, а не молчаливое удаление. Статус при этом всё равно меняется: возврат в обсуждение не должен блокироваться тем, что артефакт удалить нельзя.

Отдельно и жёстко: **не переиспользовать `TargetFundService.delete`.** Он сломан — это и есть ANO-86, и вызвать его отсюда значит размножить дефект по второму адресу. Пока ANO-86 не починен, копилка с деньгами из этой ручки не удаляется вовсе.

Альтернатива, которую сознательно **не** берём: удалять артефакт вместе с фактами. Это уничтожение реальной истории трат по нажатию одной кнопки в модуле хотелок. Если такое поведение когда-нибудь понадобится, оно должно быть отдельным явным действием в журнале, а не побочным эффектом смены статуса.

## Что меняется в коде

| файл | правка |
|---|---|
| `dto/wishlist/WishlistStatusUpdateDto.java` | добавить `Boolean deleteArtifact` |
| `service/FinancialEventService.setWishlistStatus` | принять флаг; при `true` — проверить и удалить артефакт, очистить ссылку |
| `service/TargetFundService.setWishlistStatus` | то же для строки-копилки |
| `controller/FinancialEventController` | прокинуть флаг |
| `controller/TargetFundController` | прокинуть флаг |

Симметрия обязательна: хотелкой может быть и событие, и копилка, и V18 ставила ограничения на обе таблицы.

## Тесты — по одному на каждое утверждение, каждый со своей мутацией

| тест | утверждение | мутация, которая обязана его уронить |
|---|---|---|
| `deleteArtifact_absent_keepsArtifact` | без флага артефакт жив, ссылка цела — обратная совместимость | сделать удаление поведением по умолчанию |
| `deleteArtifact_true_softDeletesPlanAndClearsLink` | с флагом план помечен удалённым, ссылка очищена | не очищать ссылку |
| `deleteArtifact_refusesWhenPlanHasFacts` | план с фактами не удаляется, ответ 409 | убрать проверку на факты |
| `deleteArtifact_refusesWhenFundHasMoney` | копилка с деньгами не удаляется, ответ 409 | убрать проверку на баланс |
| `deleteArtifact_statusChangesEvenWhenRefused` | при отказе удалить статус всё равно сменился | откатывать статус вместе с отказом |

Уровень: интеграционный на Testcontainers — правка ходит в базу и проверяет состояние двух таблиц.

## Чего эта задача НЕ делает

- Не чинит ANO-86. Наоборот, обходит его стороной и явно отказывается идти через сломанный путь.
- Не трогает интерфейс. Флаг появляется в API; кнопку в хотелках заводить отдельно.
- Не решает, что делать с артефактом по умолчанию, — по умолчанию он остаётся, как и было.
