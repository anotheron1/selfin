# Срез 4 — «Деньги»: план

**Цель:** «Деньги» списком на деталях дизайн-системы по доскам холста лица; карта заводится ответом на «Для чего эта карта?» и сразу с остатком; все остатки — одним листом; отметка «в кредит» у траты; копилка на своём счёте принимает перевод; НЗ — копилка.

**Спека:** `docs/superpowers/specs/2026-11-19-slice4-money-design.md` — номера пунктов «п. N» ниже ведут туда.

**Стек:** Java 21 / Spring Boot, React 18 / TypeScript, vitest, JUnit 5 + Testcontainers.

## Общие условия

* Код среза 4 — после вливания шести PR среза 3 (решение 54): форма «+» и карточка записи среза 3 — основа PR 6.
* Сборка: `JAVA_HOME="/c/Users/Kirill/.jdks/jbr-21.0.8" ./mvnw verify` из `backend` — юниты и IT; фронт — `npm test -- --run`, `npx tsc --noEmit`, `npm run build` из `frontend`.
* «Сегодня» в `service` и `controller` — только из внедрённого `Clock` (сторож `ClockInjectionGuardTest`). Новая меняющая ручка — с `@WritesData`; предпросмотр листа — `@WritesData(false)`, как примерка. Счёт в стороже `VisitDaysIT` растёт вместе с ручками.
* Тесты фронта рендерят разметку на сервере, как `frame.test.tsx`; нажатия проверяет стенд.
* Каждая задача: тест красный → правка → зелёный. Мутации — на итоговом коде PR, по одной на условие, CONTROL первым.
* Шесть PR, по одному, каждый — своя сессия от `main` после вливания предыдущего. Описание — «Part of ANO-…», строка «Закроет: —». Задача Linear закрывается словом владельца, когда влит последний PR с её частью.
* Перед «ждёт ок» — `bash tools/pr-ready.sh <N>`, выход 0. Не вливаю: после «ок» владелец говорит, когда прошёл CI.
* Миграции — со следующего свободного номера в `main` на начало PR. На 19.11 в `main` последняя — `V36`; срез 3 займёт `V37`.
* Опись — 40 функций спеки. Перед показом каждого PR — «опись сверена: N функций, потерь нет» по тем функциям, которые PR трогает. Старая деталь удаляется в том PR, который её заменил, не раньше.
* Одно правило — одно место. Насколько запись двигает остаток основной — `AnchorWindow.balanceEffect`, его зовут три места: `AccountBalanceService.factsDelta`, `BalanceCheckpointService` (строка 109) и шаг 1 `PocketEngine` (строка 77). «В кредит» и перевод в копилку на счёте меняют только его.

## PR 1. Карты и остатки (бэк)

Пп. 3–5, 8 и 12 (сервер). ANO-260, ANO-61 (сервер), замечание 1.2.

### Задача 1.0. Сверка на стенде — до кода

Тестовый человек, только чтение: «Свободно», «на картах», капитал и остаток каждой карты — числами в PR. Есть ли у него вторая карта «на всё», наличные с остатком, ручная запись долга по кредитке. По коду «Сделать основной» сдвигает «Свободно» на записи после последнего обновления прежней основной (`AccountService.makeDefault` переставляет только флаг, `AccountBalanceService.balanceAt` прибавляет записи только к основной). Подтверждается в задаче 1.4 тестом, не на стенде.

### Задача 1.1. «Для чего эта карта?» и остаток при заведении (п. 4)

* `AccountCreateDto` — ещё `purpose` (`SPEND`, `SAVINGS`, `CREDIT`) и остаток; у кредитки — доступное, лимит, «возвращаю до».
* `AccountService.create` раскладывает ответ по осям таблицей п. 4 и пишет первое обновление через `BalanceCheckpointService` в той же транзакции.
* Проверки — 400: `SPEND` без категории или с доходной; остаток у `SPEND`; у `CREDIT` нет лимита; «возвращаю до» выше лимита — те же слова, что сейчас.
* Запрос без `purpose` — прежний путь: им пользуется нынешний лист добавления (`AccountForm`) до PR 4. Прежний вид запроса уходит в PR 4 вместе с этим листом.
* Юниты на каждый ответ и каждую проверку; IT `POST /accounts` с ответом: оси счёта, первое обновление, ошибка обновления не оставляет карты.

### Задача 1.2. Наличные у каждого (п. 5)

* Миграция: каждому, у кого нет живого счёта CASH без остатка, — карта «Наличные», CASH, остаток не ведётся, категория расхода «Наличные». Категория есть расходом — берётся она; нет — заводится.
* Имя «Наличные» уже занято доходной категорией (`uq_categories_owner_name`) — миграция не падает; что тогда с категорией карты — решается в задаче и показывается владельцу в PR.
* `Registration` заводит наличные вместе с основной.
* IT: миграция на трёх людях — без наличных, с наличными без остатка, с наличными с остатком; второй прогон ничего не добавляет; новый человек после входа видит две карты.

### Задача 1.3. Лист и пакет обновлений (п. 3)

* `GET /api/v1/balance-checkpoints/sheet` — карты с остатком: основная, вторая «на всё», накопительные, кредитки. У каждой — «по записям» на сегодня (`balanceAt`) и дата последнего обновления. Поля «переводы после обновления» и «в кредит записано» — пустые до PR 2.
* `POST /api/v1/balance-checkpoints/batch` — все введённые числа одной транзакцией, пустые пропущены; ответ — «Свободно» до и после, разница у каждой карты, у накопительной — рост сверх переводов.
* `POST /api/v1/balance-checkpoints/preview` — тот же код, что пакет, в транзакции с откатом: итог совпадает с записью по построению.
* Старые обновления не правятся и не удаляются.
* IT: «по записям» у основной и у неосновной карты; пустое поле; ошибка в одном числе — не записано ни одного; предпросмотр равен итогу; чужие карты не видны.

### Задача 1.4. «Сделать основной» без сдвига «Свободно» (п. 12)

* `AccountService.makeDefault` в той же транзакции пишет обеим картам обновление на сегодня — их нынешние остатки, затем переставляет флаг.
* У карты без обновления — 400.
* Тест красный до правки: записи после обновления прежней основной, смена основной — «Свободно» сдвинулось. После правки — прежнее. IT через `/pocket`.

### Задача 1.5. Капитал — сверка, без кода (п. 8)

Изменение за месяц уже есть (`CapitalSummaryDto.Deltas.month`), график без `from` отдаёт историю с первой точки (`CapitalService.trajectory`). Период по умолчанию считается на клиенте по первой точке — PR 3. Если чего-то не хватает — правка здесь же, с IT.

### Задача 1.6. Мутации, стенд, PR

* Мутации — каждая строка таблицы п. 4, каждая проверка 1.1, условие миграции 1.2, пропуск пустого поля и откат 1.3, оба обновления 1.4.
* Стенд, тестовый человек, «Свободно» числами до и после: заведение каждого ответа; пакет обновлений; предпросмотр против итога; «Сделать основной». Через API стенда; после — как было.

### Задача 2.1. «В кредит» (п. 1)

* Миграция: у записи столбец `on_credit`, по умолчанию «нет».
* `balanceEffect`: расход с отметкой — 0. Три места из «Общих условий» берут признак у записи.
* `ExpectationMatch` пропускает запись с отметкой.
* `POST /events/facts` и `PATCH /events/{id}/fact` — отметка; правка отметки — правило `ExpectationMatch` заново, `resettlePlan` у старой строки. Отметка у дохода, перевода в копилку и факта к плану — 400.
* Юниты на `balanceEffect`, на пропуск в правиле и на каждую проверку. IT: остаток основной и «Свободно» не меняются; запись видна в журнале и в аналитике; в категории с ожиданием строка не гасится; снять отметку — «Свободно» меньше на сумму.

### Задача 2.2. «В кредит записано» (п. 2)

В ответе листа 1.3 — сумма записей с отметкой с даты самого старого обновления среди кредиток, граница — `AnchorWindow`. Нет кредиток — поля нет. IT: две кредитки с разными датами; запись до самого старого обновления не считается.

### Задача 2.3. Копилка на своём счёте принимает перевод (п. 6)

* Запрет `rejectTransferToAccountBackedFund` снимается.
* `balanceEffect`: перевод в копилку, которая на дату записи лежит на своём счёте (история `FundAccountLink`), уменьшает остаток основной; снятие — увеличивает.
* Остаток счёта копилки — последнее обновление плюс переводы в копилку после него (`balanceAt`); граница — `AnchorWindow`.
* Строка «Уже в копилках» такую копилку не вычитает — проверить по коду.
* Ответ листа 1.3: у накопительной — переводы после обновления; рост сверх переводов — по ним.
* IT: перевод — основная меньше, счёт больше, капитал прежний; снятие — зеркально; новое обновление счёта включает прежние переводы; перевод до привязки копилки к счёту основную не трогает и капитал прошлых месяцев не переписывает (ANO-158); у отвязанной копилки нет баланса без подкрепления (ANO-163).

### Задача 2.4. НЗ — копилка (п. 7)

**Перенесена в PR 6** — слово владельца 22.11: «мне нз не критично, вполне себе ждёт 6 пр». Сервер НЗ — миграция, движок, примерка, отказы, `bufferAmount` — уходит в PR 6 вместе с листом НЗ (задача 6.3); пункты ниже — его.

* Миграция: у цели признак запаса; каждому — цель «НЗ», первой, «сколько держать» — `bufferAmount` или 0, без счёта.
* `PocketEngine` (строка 242) и примерка `PocketSandboxService` (строка 126) берут «сколько держать» НЗ без счёта; НЗ на счёте — 0.
* Перевод в НЗ без счёта — 400; удалить НЗ — 400.
* `bufferAmount` в «Настройках» до PR 6 читает и пишет «сколько держать» НЗ: старый `NzSheet` работает до замены. В PR 6 поле уходит из `PocketSettingsDto`.
* Предупреждение «придётся взять из НЗ» и жёлтые месяцы «Что с капиталом» идут от того же числа — тест на каждое.
* IT: миграция переносит `bufferAmount`; НЗ на основной — «Свободно» меньше; привязали к вкладу — не меньше, НЗ равен остатку вклада; правка через старую ручку меняет НЗ.

### Задача 2.5. Мутации, стенд, PR

* Мутации — каждая ветка `balanceEffect` (расход с отметкой и без, перевод на счёт и без, снятие), пропуск в правиле, каждая проверка 2.1, граница 2.2, остаток счёта копилки, «Уже в копилках», каждая ветка НЗ.
