## 2. Решения по шагам: зачем, почему так, как ещё было можно

### Разбор вопросов для сервера

**Зачем.** План шагов 6–7 писался 17.10, до первого взгляда на сервер. 24.10 выяснилось: порты 80 и 443 держит nginx друга, на сервере живут его сайты. Работать по старому плану значило бы строить на Caddy то, что там не встанет.

**Как.** 13 пунктов — по одному, что это, зачем, стоит ли; решения — в самом разборе. Вопрос про прокси вырос в отдельный разбор схемы (`2026-10-24-proxy-scheme-analysis.md`).

**Почему не иначе.**
* *Сразу ставить по плану* — переделка на сервере друга дороже, чем разбор.
* *Решать за тебя* — половина пунктов твоя: деньги, риск, отношения с другом, закрытие репозитория.
* *Делать всё и сразу* — шифрование и вынос копий, закрытие репозитория ты отложил (ANO-239, ANO-240): к запуску они не нужны, а решения по ним — твои.

### 6.1. Тексты под копии на сервере

**Зачем.** Политика и согласие обещали зашифрованную копию во внешнем хранилище, а на запуске копия — на том же сервере и без шифрования. Текст не должен обещать то, чего нет.

**Как.** Копия — на том же сервере, 7 дней, без шифрования, доступ — как к самой базе; новая редакция и версия согласия — в трёх местах, сторож сверяет их.

**Почему не иначе.**
* *Оставить тексты до ANO-239* — с первого дня текст говорил бы неправду.
* *Не поднимать версию* — не доказать, какую редакцию человек принял.
* *Поток повторного согласия (ANO-238)* — людей на сервере ещё не было, повторно спрашивать было некого.

**Что поймали.** Codex — один P2: тексты не совпадают с нынешним скриптом копий. Ответ: ворота — порядок шага 6, тексты и скрипт расходятся только до 6.3. На стенде шага найдена ANO-244: первый вход после пересборки бэка упал по тайм-ауту ключей Keycloak.

### 6.2. Дверь nginx без Caddy

**Зачем.** За nginx друга Caddy теряет обе свои роли — сертификат и заголовок схемы, — а запрос шёл бы через три прокси.

**Как.** Правила закрытия Keycloak — в nginx экранов (`^~` и `= /auth/`), Keycloak — через переменную и `resolver`, явные пределы тела и тайм-ауты на обоих звеньях, `nginx -t` при сборке образа. Caddy убран, nginx экранов слушает только `127.0.0.1`. Для nginx друга — два шаблона двери: сначала порт 80 для проверки Let's Encrypt, после сертификата — 443. `keycloak-check` проверяет шесть закрытых адресов, в том числе другие их написания.

**Почему не иначе.**
* *nginx друга → Caddy → nginx экранов* — три прокси, а Caddy за чужим nginx сертификат не получит.
* *Правила закрытия в nginx друга* — правка чужого конфига, против твоего правила 24.10.
* *`certbot --nginx`* — сам правит конфиги, в том числе чужие.
* *Сертификат через DNS* — на сервере лёг бы токен DNS-провайдера.

### 6.3. Копии «только на сервере»

**Зачем.** Твоё решение 24.10 — запуск без шифрования, копии на сервере 7 дней. Скрипт копий без ключа и хранилища просто падал.

**Как.** Явный режим `local` или `external`; без режима — ошибка. В `local` — уборка старше 6 суток до копии, журнал удалений — после. Копия пишется в скрытую папку `.part` и переносится целиком; время — с секундами.

**Почему не иначе.**
* *«Нет ключа — пишем открытым текстом»* — однажды забытый ключ выгрузил бы открытые копии наружу.
* *Отдельный скрипт для `local`* — два скрипта разъедутся.
* *Без уборки* — диск сервера друга кончится.

**Что поймали.** Codex — два круга: повтор в ту же минуту затирал готовую копию; две копии в одну секунду делили одну папку `.part`. Оба — тестами и правкой.

### 6.4. Репетиция и ссылка «только в Keycloak»

**Зачем.** Прогнать цепочку так, как она встанет у друга, до того как трогать его сервер; приготовить твой вход для шага 7.

**Как.** Серверная сборка отдельным проектом на машине стенда, перед ней — nginx той же версии, что у друга, с самоподписанным сертификатом: `keycloak-check` 41 из 41, изоляция, копия. Ссылка `tools/owner-link.mjs` — вход клиента `selfin` прямо в Keycloak: Keycloak заводит учётную запись, а сайт этот вход не начинал, не принимает и строк не заводит.

**Почему не иначе.**
* *Консоль учётной записи по туннелю* — шаг 3 показал: через туннель сервер называет себя публичным адресом, а снаружи консоль закрыта.
* *Сразу вход в приложение* — ловушка шага 7: заводит пустую учётную запись со стартовым набором.
* *Связь по номеру Telegram, а не Keycloak* — номер человека у Telegram может зависеть от бота (разбор, пункт 6).

**Что поймали.** `isolation-check` брал токен через публичный адрес, где реалм `master` с 6.2 закрыт, — поправлено.

### 6.5. Установка

**Зачем.** Сам запуск — каждая правка сервера с твоего «да».

**Как.** Ключ SSH заменён (старый побывал в чате). Клон — `/opt/selfin`. В `.env` пять паролей сгенерированы на сервере без вывода; ключи бота ты вписал одноразовым скриптом — секрет без эха, отказ на пустом и на символах, которые compose исказил бы. Дверь — в две фазы, с проверкой nginx друга до и после. Запуск — 69 секунд. Адреса возврата стенда у клиента `selfin` убраны. Проверки: `keycloak-check` по публичному адресу, вход временного человека формой через браузер, изоляция, копия вручную, уборка.

**Почему не иначе.**
* *Пароли вводишь ты* — ты разрешил генерировать их на сервере, не видя (24.10): меньше рук у секретов.
* *Ключи бота — через чат* — секреты в чат не идут.
* *Сразу файл двери с портом 443* — certbot по webroot сначала проверяет порт 80, а nginx с отсутствующим сертификатом не прошёл бы `nginx -t`.

**Что поймали.**
* **`conf.d` nginx читает раньше `sites-enabled`.** Без явного `default_server` у друга наш файл отвечал бы на голый адрес и чужие имена. У друга он объявлен — проверено до правки; отпечаток его сайтов до и после совпал.
* **@BotFather переименовал поле** «Allowed URLs» в «Redirect URIs» — поправлено в шаблонах и плане (#197).
* **В бесплатном UptimeRobot срок сертификата — платный** (корона в настройках) — срок смотрит Red Sift.
* **`docker compose run` внутри скрипта, поданного через `ssh … bash -s`, съедает хвост скрипта:** следующие команды молча не выполнились. Такие вызовы — с `< /dev/null`.
* **План назвал инструмент, который этого не умеет:** «вход формой — `second-person`», а он пароль не отдаёт. Вход формой на сервере проверен скриптом по образцу репетиции 6.4.

### 7. Переезд твоей истории

**Зачем.** Цель вехи — ты работаешь на сервере со своей историей.

**Как.** Дамп — с копии тома твоей базы; «до» — твоим же образом на копии из дампа. На сервере: копия → бэк остановлен → база пересоздана пустой → дамп → миграции `V30`–`V36`; количества по 12 таблицам те же, все строки — у синтетического владельца. Ты вошёл по ссылке только в Keycloak, твой номер — в `SELFIN_OWNER_SUB`, твой обычный вход привязал историю — числа совпали. Изоляция — на твоих данных, после свежей копии.

**Почему не иначе.**
* *Поднять твой контейнер базы* — его порт занят другим твоим проектом; останавливать чужое ради дампа — лишнее. Копия тома: оригинал подключался только на чтение.
* *«До» по SQL* — правило «замер через продукт»: числа экрана считает код, а не запрос.
* *Залить дамп в живую базу без пересоздания* — остался бы стартовый набор синтетического владельца.
* *Сначала вход в приложение* — ловушка шага 7.

**Что поймали.** Первая попытка дампа при неудачном старте контейнера оставила пустой файл: команда без `set -e` шла дальше. Пойман сразу, файл удалён. Проверка «дамп дописан до конца» по трём последним строкам дала ложный ноль: pg_dump 15.17 дописывает после конца строку защиты `\unrestrict`.

### ANO-197: восстановление на настоящей копии

**Зачем.** В самой задаче: копия, которую ни разу не разворачивали, копией не считается. На стенде восстанавливали — но копию стенда.

**Как.** Свежая копия с твоей историей развёрнута во временном Postgres на самом сервере: манифест сошёлся — 16 таблиц, количества и отпечатки, журнал удалений; каждый связанный человек — учётная запись реалма; вход через Telegram в восстановленном реалме включён; удалённый из журнала не вернулся. Временный Postgres удалён.

**Почему не иначе.**
* *На стенде, как в цели вехи* — копия с твоими данными открытым текстом ушла бы с сервера, а копии по твоему решению живут только на нём.
* *Штатным `restore` в живые базы* — перезаписал бы рабочие данные.
* *`tools/restore-check.mjs`* — он для восстановленной живой системы с поднятым Keycloak; его проверки повторены запросами.

### ANO-244: ключи Keycloak с запасом

**Зачем.** Spring Security 7 ждёт ключи реалма полсекунды. На холодном Keycloak — после перезагрузки сервера или его перезапуска — первый вход падал бы.

**Как.** Один клиент ключей — 2 с на соединение, 5 с на чтение. Bearer — настройщик декодера, который собирает Boot; вход через браузер — своя фабрика декодеров ID token, тот же декодер, что у библиотеки, один на регистрацию. `keycloak-check` больше не падает на относительном адресе.

**Почему не иначе.**
* *Повтор запроса ключей* — с теми же 500 мс на медленном Keycloak падает так же.
* *Прогрев при старте* — Keycloak может ещё не подняться, а декодер входа заводится лениво.
* *Свой Bearer-декодер целиком* — проверки издателя и аудитории разошлись бы с конфигурацией Boot.

**Что поймали.** Первый замер на стенде дал 504 и «до», и «после»: посредник пересылал заголовки соединения, клиент JDK предлагал HTTP/2 (`Upgrade: h2c`), и обмен кода на токен висел минуту. Замер мерил посредника, а не продукт; посредник поправлен, замер переснят.

## 3. Как работали

Сервер — по шагам с твоим «да» на каждую правку; перед каждой правкой — чтение того, что там уже есть, после — проверка и откат, если не сошлось.

## 4. Что было трудно

* **Чужой сервер.** Его nginx, его сайты, занятые порты. Каждая правка — своим файлом, с `nginx -t` перед перезагрузкой, с отпечатком его сайтов до и после.
* **Секреты без рук.** Пароли — сгенерированы на сервере, ключи бота — твоим скриптом, пароль администратора — инструментам из `.env` без вывода. Ни одно значение не прошло через чат, логи или репозиторий.
* **Сюрпризы твоей машины.** Node спрашивает DNS у VPN и получает отказ на всё (ложная тревога о поддомене 24.10); порт 5432 занят другим проектом.
* **Инструменты замера, которые врут.** Посредник с HTTP/2, `docker compose run`, съедающий скрипт, проверка конца дампа по трём строкам — каждый раз ошибка была в измерении, а не в продукте, и находилась чтением журналов, а не повтором.
* **Ты на телефоне.** Шаги, которые требуют твоего компьютера (ключи бота, вход по ссылке), — отдельными короткими инструкциями; первая была слишком плотной («Бошка не варит»), дальше — по шагам с номерами.

## 6. Правки процесса

По правилу 02.10 — только с доказательством.

| случай | цена | повторится |
|---|---|---|
| номер задачи в заголовке PR — #162 (спринт 5), #190 и #199 (спринт 6) | Linear связывает задачу при открытии PR и закрыл бы её при вливании; ворота ловят только перед вливанием | да: срезы называют задачи, заголовок пишется по ним; три случая за два спринта |

**Предложение** (то же, что в первой части, теперь с третьим случаем): не открывать PR с `ANO-` в заголовке или имени ветки — обёртка над `gh pr create` с тем же признаком, что у ворот. Решение — твоё.

Записано как наблюдение, без правки: многошаговые команды, которые пишут данные, — с `set -e`. Один случай, вреда нет; повторится — повод.
