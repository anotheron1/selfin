# Скелет: счета и поведенческие модели (ANO-9)

Дата: 2026-08-12. Статус: дизайн, ожидает реализации.
Родитель: ANO-5 «Пересборка — core loop как стержень». Задача: ANO-9.

---

## 1. Рамка: зачем это вообще

Продукт продаёт подход к личным финансам, а не программу (§1.1 в `2026-06-19-product-rethink-design.md`, коммент в ANO-5). Счета — первая проверка этого подхода на прочность, потому что три из пяти принципов выражаются именно через них:

- **Принцип 1** (деньги делятся при поступлении) — счета-корзины с зонами ответственности.
- **Принцип 2** (глубина контроля выбирается на каждый объект осознанно) — тумблер «слежу за остатком» живёт на счёте, а не в глобальном режиме приложения.
- **Принцип 4** (обязательство измеряется планкой возврата) — кредитный счёт хранит доступный остаток и планку, а не долг.

Отсюда главное анти-требование, заданное автором ещё в июле: **счета не должны появляться в ежедневном вводе.** «Я очень не хочу дрочить каждую транзакцию с выбором, с какого счёта она была совершена». Модель, которая заставляет выбирать счёт при каждой трате, эту задачу проваливает, даже если технически корректна.

Второе требование, менее очевидное: глубина слежения — **функция цены ввода**. Автор готов вести транзакции и балансы, если ввод станет дешёвым (импорт выписки, ANO-10). Значит модель обязана выдержать оба края — от «вообще не знаю остаток» до «знаю каждую операцию» — а импорт потом заполняет её сверху, ничего не переделывая.

---

## 2. Что решено

Выбран подход **«Счёт владеет остатками»**: счёт становится адресом для уже существующего механизма чекпоинтов, а не новым параллельным миром.

| Решение | Обоснование |
|---|---|
| Счёт — настраиваемый объект с четырьмя осями | Принцип 2: настройка на объекте, не в режиме |
| Свободные деньги = сумма ликвидных счетов, за которыми следишь | Тумблер «слежу за остатком» одновременно решает участие в кармашке: за чем не следишь, того не можешь посчитать |
| У кредитного счёта чекпоинт хранит **доступный остаток**, не долг | Принцип 4; так мыслит пользователь |
| Кредитки уезжают из Капитала в счета, вручную | Данные в Капитале, похоже, записаны наизнанку — автоматика угадала бы неверно |
| Копилка получает необязательную ссылку на счёт и тогда **теряет собственный баланс** | Иначе два числа за одни деньги разъедутся |
| Счёт не появляется в форме ввода транзакции | Главное анти-требование |

Отвергнуты: «полная модель сразу» (адрес счёта на каждой транзакции + переводы) — даёт трение раньше ценности; «счёт как голая настройка» (деньги остаются где были) — не даёт мультисчёт, ради которого всё затевалось.

## 3. Модель данных

### 3.1 Новая сущность `accounts`

```sql
CREATE TABLE accounts (
    id                  UUID           PRIMARY KEY DEFAULT gen_random_uuid(),
    name                VARCHAR(255)   NOT NULL,
    kind                VARCHAR(16)    NOT NULL
                        CHECK (kind IN ('DEBIT', 'CREDIT', 'DEPOSIT', 'CASH')),
    track_balance       BOOLEAN        NOT NULL,
    purpose_category_id UUID           REFERENCES categories(id),
    credit_limit        NUMERIC(19, 2),
    available_floor     NUMERIC(19, 2),
    is_default          BOOLEAN        NOT NULL DEFAULT FALSE,
    sort_order          INT            NOT NULL DEFAULT 100,
    created_at          TIMESTAMP      NOT NULL DEFAULT NOW(),
    updated_at          TIMESTAMP      NOT NULL DEFAULT NOW(),
    is_deleted          BOOLEAN        NOT NULL DEFAULT FALSE,

    -- кредитные поля только у кредитного счёта
    CONSTRAINT ck_accounts_credit_fields CHECK (
        kind = 'CREDIT' OR (credit_limit IS NULL AND available_floor IS NULL)),
    -- планка не выше лимита
    CONSTRAINT ck_accounts_floor_le_limit CHECK (
        available_floor IS NULL OR credit_limit IS NULL OR available_floor <= credit_limit),
    -- вклад всегда отслеживается: он полу-ликвид в капитале, без остатка бессмыслен
    CONSTRAINT ck_accounts_deposit_tracked CHECK (
        kind <> 'DEPOSIT' OR track_balance),
    -- счёт по умолчанию обязан быть отслеживаемым: он принимает безадресные операции
    CONSTRAINT ck_accounts_default_tracked CHECK (
        NOT is_default OR (track_balance AND kind IN ('DEBIT', 'CASH')))
);

-- не более одного счёта по умолчанию среди живых
CREATE UNIQUE INDEX uq_accounts_single_default
    ON accounts ((is_default)) WHERE is_default AND NOT is_deleted;
```

**Четыре оси и их смысл:**

1. **`kind` — природа.** Решает, куда деньги идут: `DEBIT`/`CASH` — в свободные, `DEPOSIT` — в капитал минуя свободные (полу-ликвид), `CREDIT` — в обязательства.
2. **`track_balance` — слежу за остатком.** Главный тумблер. Определяет и участие в свободных деньгах, и смысл пополнения (см. §5.2).
3. **`purpose_category_id` — зона ответственности.** Необязательная, мягкая, переназначаемая: карта заводится под «Бензин», потом её ответственность растёт до «Авто» и дальше до «Транспорт». Это одно поле, а не отдельная сущность.
4. **Кредитные поля** — `credit_limit` и `available_floor` (планка возврата).

Плюс служебное `is_default` — куда падают операции без адреса.

**Разумные дефолты при создании** (принцип «в начале настраивать нечего»):

| kind | track_balance по умолчанию | Можно изменить |
|---|---|---|
| DEBIT | да | да |
| CASH | нет («расход при снятии») | да |
| DEPOSIT | да | нет |
| CREDIT | да | да, но без остатка нет ни долга, ни второго числа |

**Планка (`available_floor`) по умолчанию `NULL`.** Пока пользователь её не назвал, приложение её не выдумывает: второе число просто не показывается. Решение автора — «ручная плюс подсказка».

### 3.2 Изменения в `balance_checkpoints`

```sql
ALTER TABLE balance_checkpoints ADD COLUMN account_id UUID REFERENCES accounts(id);
-- после заполнения (см. §7):
ALTER TABLE balance_checkpoints ALTER COLUMN account_id SET NOT NULL;
CREATE INDEX idx_checkpoints_account_date ON balance_checkpoints (account_id, date DESC);
```

Семантика `amount` зависит от природы счёта и это **единственное место, где она различается**:

- `DEBIT`, `CASH`, `DEPOSIT` — остаток на счёте.
- `CREDIT` — **доступный остаток**. Долг вычисляется как `credit_limit − amount`.

Существующий `CHECK (amount >= 0)` сохраняется и для кредитного смысла корректен.

Механика ре-якоря (ANO-15) не меняется: несколько чекпоинтов по датам, актуален последний. Расчёт дрейфа в `BalanceCheckpointService.findAll()` становится **пер-счётным** — цепочка строится внутри одного счёта, иначе дрейф считался бы между чекпоинтами разных карт.

### 3.3 Изменения в `target_funds`

```sql
ALTER TABLE target_funds ADD COLUMN account_id UUID REFERENCES accounts(id);
CREATE UNIQUE INDEX uq_funds_one_per_account
    ON target_funds (account_id) WHERE account_id IS NOT NULL AND NOT is_deleted;
```

Два режима копилки:

- **Без `account_id` — виртуальный конверт**, как сейчас. Пополняется переводом (`FUND_TRANSFER`), уменьшает кармашек, остаётся в ликвидном капитале. Не меняем ничего.
- **С `account_id` — цель, лежащая на реальном счёте.** `current_balance` перестаёт быть источником правды и **вычисляется** из баланса счёта. Копилка становится целью и датой поверх чужого остатка.

Уникальный индекс — сознательное ограничение: одна цель на счёт. Две цели на одной карте потребовали бы делить остаток между ними, то есть виртуальных подконвертов внутри счёта. Кому нужны две — оставляет их виртуальными.

## 4. Расчёты

### 4.1 Свободные деньги (кармашек)

Сейчас (`PocketEngine.calculate`, шаг 1):

```
currentBalance = checkpoint.amount + Σ signed(факты) в (checkpoint.date, asOf]
```

Становится:

```
участвует(a) = НЕ a.is_deleted
             И a.kind ∈ {DEBIT, CASH}
             И a.track_balance

currentBalance = Σ по участвующим a: balance(a, asOf)

balance(a, t) = last_checkpoint(a, ≤ t).amount
              + (a.is_default ? Σ signed(факты) в (checkpoint.date, t] : 0)
```

Правило отбора фактов не меняется: `factAmount != null`, `wishlistStatus == null`, дата `≤ asOf` и строго после даты чекпоинта своего счёта.

**Почему безадресные факты идут на счёт по умолчанию.** Транзакции адреса не имеют — это прямое следствие анти-требования. Значит разнести их по счетам физически нечем. Ровно один счёт объявлен приёмником, обычно основная карта, где у пользователя и правда всё происходит. Остальные отслеживаемые счета двигаются только чекпоинтами. Это же место, куда позже воткнётся импорт: у импортированной операции адрес будет, и она перестанет быть безадресной.

Всё остальное в движке (траектория, минимум, буфер, breakdown) не меняется. Кармашек по-прежнему `min траектории − буфер`.

### 4.2 Второе число: «свободно, если вернуть карты к планке»

```
доступно(a, t)  = last_checkpoint(a, ≤ t).amount        // кредитный чекпоинт = доступный остаток
резервВозврата  = Σ по CREDIT a с available_floor ≠ NULL: max(0, a.available_floor − доступно(a, asOf))
свободноПосле   = кармашек − резервВозврата
```

Показывается только когда `резервВозврата > 0`. В breakdown добавляется строка типа `CREDIT_RESTORE` — **информационная**, как `WISHLIST_INFO`: она не входит в инвариант основного числа и его не меняет.

Инвариант breakdown остаётся прежним:
`STARTING − OVERDUE − EXPENSES − CONTRIB + INCOME − FORECAST = MIN`, `MIN − BUFFER = POCKET`.

**Подсказка поднять планку.** Если `доступно > available_floor` на последнем чекпоинте, показать предложение «поднять планку до N». Одно сравнение, без статистики: пользователь сам решает, устойчив ли уровень. Это ровно его сценарий — «добью до 160 000 доступных, и это станет новой планкой».

### 4.3 Третье число: «свободно, если распечатать вклад»

```
полуЛиквид     = Σ по DEPOSIT a с track_balance: balance(a, asOf)
свободноСВкладом = кармашек + полуЛиквид
```

Показывается **мелким шрифтом**, ниже основного и второго числа, и только когда `полуЛиквид > 0`. Решение автора: «ну маленькой цифрой». Это не третий равноправный ответ, а сноска: вклад распечатывают в трудный момент, а не планируют им жить.

**Следствие, решённое отдельно (ANO-46, 2026-08-15).** Раз вклад не входит в основное число, он не входит и в прогнозы, которые на это число опираются: кассовый график стратегии и зоны риска хотелок считаются от `cashLiquidAt` — ликвида **без** вкладов. Иначе одна и та же сущность считалась бы по-разному на соседних экранах: человек, проедающий 10 000 в месяц при вкладе 1 500 000, не получал бы предупреждения о разрыве ближайшие 12 лет. Формулировка автора: «Вклад, конечно, может помочь пережить месяц, но это должно быть осознанным решением пользователя, а не предполагаемое действие». Вклад остаётся ровно в одном месте — на экране Капитала (§4.4), где он и есть имущество. Цена решения принята осознанно: «потолок кредита» в хотелках падает, хотя банк вклад учёл бы.

Порядок на экране: свободно (крупно) → свободно после возврата карт к планке (обычным) → свободно, если распечатать вклад (мелким).

### 4.4 Капитал

```
ликвид(t)        = Σ по a с track_balance И kind ∈ {DEBIT, CASH, DEPOSIT}: balance(a, t)
                 + Σ балансов копилок БЕЗ account_id
обязательства(t) = Σ по CREDIT a с чекпоинтом: max(0, a.credit_limit − доступно(a, t))
                 + Σ CapitalItem(LIABILITY)
активы(t)        = Σ CapitalItem(ASSET)
капитал(t)       = ликвид + активы − обязательства
```

Три отличия от нынешнего `CapitalService.liquidAt`:

1. Вклады входят в ликвид (сейчас их просто нет как сущности).
2. Копилки **с** `account_id` не прибавляются отдельно — их деньги уже внутри баланса счёта. Это и есть защита от задвоения.
3. Обязательство по кредитке считается из лимита и доступного, а не берётся вручную введённым числом.

## 5. Ввод: как счёт остаётся невидимым

### 5.1 Где счёт появляется, а где нет

| Место | Счёт виден? |
|---|---|
| Форма транзакции (трата, доход) | **Нет.** Поля счёта не существует |
| Журнал | Нет |
| Ре-якорь остатка | Да — выбираешь, чей остаток вводишь. Редкое действие |
| Экран счетов | Да — это и есть настройка |
| Кармашек | Косвенно: второе число по кредитке |

То есть в ежедневном цикле счетов нет вообще. Это не «мы их спрятали за дефолтом» — их там буквально нет.

### 5.2 Один тумблер, два поведения — ключевая механика

Пополнение счёта-конверта означает разное в зависимости от `track_balance`, и это снимает целый класс настроек:

- **Не слежу за остатком.** Деньги, ушедшие на конверт, считаются потраченными. Перевод на бензиновую карту — это обычная трата категории «Бензин», один ввод, как всегда. Счёт при этом не хранит денег в модели: он даёт смысл («эта категория обслуживается такой картой») и показывает выделенное за месяц (§5.3). Сколько реально осталось — видно в банке.
- **Слежу за остатком.** Тот же перевод становится переносом: деньги остались твоими и видны в свободных. Бюджет корзины — реальный остаток, обновляемый ре-якорем, а позже импортом.

Это разрешает кажущееся противоречие в требованиях («не слежу за конкретным балансом» против «бюджет на авто виден»): бюджет — это либо выделенная сумма, либо остаток, и выбирает тумблер.

### 5.3 Экран счетов

Список карточек. Каждая показывает имя, природу, зону ответственности и число, зависящее от тумблера:

- **Слежу за остатком** — остаток на последнем чекпоинте и его дата.
- **Не слежу** — **выделено за текущий месяц**: сумма записанных фактов по категории-зоне ответственности с начала месяца.

Второе число честно ровно настолько, насколько конверт используется по назначению: если внутрь него кидают одним переводом раз в неделю, сумма за месяц и есть выделенный бюджет. Если пользователь вдобавок записывает отдельные траты по той же категории с других карт, число смешает выделенное с потраченным мимо конверта. Подпись поэтому «Выделено за месяц» с пояснением «по категории такой-то», а не «Осталось» — обещать остаток мы не можем и не должны.

У кредитного счёта — доступно из лимита, планка и рассчитанный долг.

Создание счёта — имя плюс природа; всё остальное имеет дефолт и правится потом.

**Где живёт:** в Настройках, не в нижней навигации. Причина — лестница раскрытия (§5 продуктового дока): счета это продвинутый слой, большинство до него не доходит, а нижняя навигация и так спорная (ANO-31 про дублирование «Цели» и «Хотелки»). Пересмотреть, если раскладка дохода по корзинам станет регулярным ежемесячным действием — тогда ей в настройках тесно.

## 6. Границы первой версии

**Входит:** сущность счёта с четырьмя осями, адресация чекпоинтов, свободные деньги как сумма ликвидных отслеживаемых, кредитная планка и второе число, ссылка копилки на счёт, экран счетов, миграция.

**Не входит и почему:**

| Не делаем | Причина | Где живёт |
|---|---|---|
| `account_id` на транзакции | Ввод не усложняем; до импорта ценности ноль | вместе с ANO-10 |
| Перевод между счетами как операция | Нужен только при двух отслеживаемых ликвидных счетах; у автора этот случай пока не возник. Решено 2026-08-12 | вернуться, когда случай появится |
| Долг корзине, чекбокс «в долг» | Решение не принято | ANO-44 |
| Раскладка процентом от дохода | «15% на авто» — образ, не механика | — |
| Импорт выписки | Отдельный эпик | ANO-10 |
| Инъекция `Clock` | Техдолг, дизайна не требует | ANO-39 |
| Ревизия план/факт | Отдельная дизайн-сессия | ANO-42 |

**Известное ограничение.** Между чекпоинтами не-дефолтные отслеживаемые счета не двигаются: их баланс замирает до следующего ре-якоря. Для сценария автора (основная карта + конверты без слежения + вклад) это верно и незаметно — вклад меняется редко. Для двух активных дебетовых карт станет заметно, и тогда понадобится перевод как операция. Не выдумываем фиктивные траты, чтобы это обойти: лучше честно замерший остаток, чем мусор в аналитике.

## 7. Миграция и данные

### 7.1 Flyway `V20__add_accounts.sql`

1. Создать таблицу `accounts` и индексы.
2. Вставить счёт **«Основная карта»**: `kind = DEBIT`, `track_balance = true`, `is_default = true`.
3. `ALTER TABLE balance_checkpoints ADD COLUMN account_id`, проставить всем строкам id этого счёта, затем `SET NOT NULL`.
4. `ALTER TABLE target_funds ADD COLUMN account_id` (nullable, остаётся пустым).

**Инвариант миграции:** кармашек после неё обязан совпасть с прежним до копейки. Формула §4.1 при одном счёте, который одновременно дефолтный и отслеживаемый, схлопывается ровно в старую. Это проверяется тестом, а не на глаз (§9).

### 7.2 Кредитки в Капитале — переносим руками

В Капитале лежат `LIABILITY` «Кредитка ТБанк» = 98 000 на 12.05 и «Кредитка СБанк» = 69 000. По словам автора, реальный долг по ТБанку на ту дату был 62 000, а 98 000 — это **доступный остаток**. Если так, записи инвертированы и чистый капитал занижен примерно на 36 000; со СБанком вероятно то же.

Автоматическая миграция здесь запрещена: из данных невозможно установить, какое число записано, а ошибка изменит капитал в обе стороны на десятки тысяч.

Вместо этого при создании кредитного счёта UI показывает шаг: «В Капитале есть запись “Кредитка ТБанк” на 98 000. Если это доступный остаток, а не долг, заархивируй её — счёт теперь считает обязательство сам». Решение принимает человек, один раз.

### 7.3 Что остаётся в Капитале

Неденежное: недвижимость, автомобиль, вложения, а также займы вне карт. Капитал перестаёт быть местом, где вручную ведут остатки банковских продуктов.

## 8. Ошибки и края

| Ситуация | Поведение |
|---|---|
| Ни одного счёта | Невозможно: миграция создаёт «Основную карту» |
| Удаление счёта по умолчанию | 409, сначала назначь другой |
| Удаление счёта с чекпоинтами | Soft delete; чекпоинты остаются, счёт уходит из всех сумм |
| Планка выше лимита | 400 |
| Доступный остаток выше лимита (свои деньги на кредитке) | Разрешено; излишек **не** считается свободными деньгами (решено 2026-08-12) |
| У кредитного счёта нет чекпоинта | Ни долга, ни второго числа — счёт молчит, а не считает ноль |
| Попытка выключить слежение у вклада | 400 |
| Копилка ссылается на счёт, у которого нет чекпоинта | Баланс копилки = 0, прогресс не показывается |
| Категория с зоной ответственности удалена | Ссылка обнуляется, счёт остаётся |

**Дополнено по итогам реализации чанка 3 (2026-08-15).** Пять случаев, которых в исходной таблице не было, — все всплыли на ревью:

| Ситуация | Поведение | Почему |
|---|---|---|
| Цель (копилка) ссылается на кредитный счёт | 400 | Чекпоинт кредитки хранит доступный остаток: «накоплено» показало бы неизрасходованный лимит, то есть деньги, которых нет |
| Цель ссылается на счёт без слежения за остатком | 400 | Остаток такого счёта не входит ни в свободные деньги, ни в капитал — цель копила бы число, не подтверждённое ничем |
| Удаление счёта, на котором лежит цель | 409, сначала отвяжи цель | После удаления накопленное обнулилось бы, а восстановить его неоткуда: собственный баланс такой копилки давно нулевой |
| Отвязка цели от счёта | Накопленное переносится в собственное поле копилки | Иначе цель прыгнула бы к протухшему числу — обычно к нулю |
| Смена природы через границу «кредитная / некредитная» у счёта с чекпоинтами | 400 | Смысл сохранённых сумм переворачивается: карта с остатком 40 000, объявленная кредиткой с лимитом 200 000, мгновенно получила бы долг 160 000. Переходы DEBIT ↔ CASH ↔ DEPOSIT разрешены — там сумма означает одно и то же |

Отдельно уточнение к подсказке §4.2: предложенная планка равна `min(доступное, лимит)`. Строка «доступный остаток выше лимита разрешён» и требование «планка ≤ лимит» вместе означают, что без подрезки подсказка предлагала бы уровень, который валидация отвергнет.

## 9. Тестирование

Движок кармашка чистый (`PocketEngine`), поэтому основное покрывается юнитами без БД.

**Обязательные тесты:**

1. **Регрессия миграции.** Один счёт, дефолтный и отслеживаемый → кармашек, минимум, breakdown и все строки совпадают с эталоном до изменений. Это definition of done, а не приятное дополнение.
2. Сумма по двум отслеживаемым счетам; безадресные факты применяются только к дефолтному.
3. Конверт без слежения не участвует в свободных деньгах ни при каком остатке.
4. Вклад не входит в свободные деньги, но входит в ликвидный капитал.
5. Второе число: планка задана и доступно ниже → резерв; планка не задана → числа нет; доступно выше планки → резерв ноль, показывается подсказка.
6. Капитал не задваивает копилку, привязанную к счёту.
7. Дрейф чекпоинтов считается внутри счёта, а не между счетами.
8. Все ограничения из §8 — по одному тесту на строку.

Даты в тестах фиксировать нельзя, пока не сделан ANO-39 (`Clock`), — существующие тесты уже падали в последний день месяца. Тесты этой задачи писать так, чтобы граничный день существовал всегда (как в PR #28), либо дождаться `Clock`.

**Остаётся открытым один: как это называется на экране.**

«Счета» — точно, но звучит бухгалтерски и работает против идеи, которую продукт продаёт. «Кошельки», «Корзины», «Карты» ближе к тому, как автор про это думает вслух. Слово здесь не косметика: оно решает, читается идея или нет. Автор: «ещё подумаем, погоди пока».

До решения в коде и интерфейсе используется рабочее «Счета». Смена названия — правка UI-строк и заголовка экрана, доменные имена (`accounts`, `Account`) не трогает: технический термин и продуктовое слово могут не совпадать.
