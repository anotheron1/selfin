# Удалённая «Переводы в копилки» — продукт возвращает её сам (ANO-224)

Шаг 0 спринта 5 (`2026-10-11-sprint-5-plan.md`, раздел 3). Направление — в задаче и в плане спринта: по образцу «Цели» из #139, один помощник на четыре системные категории, старые базы — миграцией. Спека и план одним документом.

## Что на экране

* **Экземпляр владельца, 07.10.** Любой перевод в копилку отвергается: кнопка пополнения на карточке «Целей», «В копилку» в быстром вводе, план перевода. Быстрый ввод пишет «Не записалось — попробуйте ещё раз», повтор не помогает. В логах — два отказа на вставке категории, `POST /events` и `POST /funds/{id}/transfer`: `duplicate key … Key (name)=(Переводы в копилки) already exists` → 409. В его базе «Переводы в копилки» удалена — вместе с 17 другими категориями из 38; переводов с 07.10 нет ни одного.
* **Стенд `0632652`, 11.10.** До удаления проходят все три пути; копилка «кеке» 0 → 2 500. «Переводы в копилки» удалена в «Настройках» — и `POST /funds/{id}/transfer` отвечает 409 с той же ошибкой базы.

## Почему

* `TargetFundService.getOrCreateFundTransferCategory()` ищет категорию только среди живых (`findByNameAndDeletedFalse`) и, не найдя, заводит новую. Имя уникально во всей таблице, вместе с удалёнными (`categories_name_unique`), — вставка падает.
* Категория не системная (`is_system = false`) — «Настройки» дают её удалить.
* Через эту функцию идут все пути перевода: карточка и быстрый ввод фактом — `POST /funds/{id}/transfer` (`transferToPocket`), план из быстрого ввода — `POST /events` без категории (`createIdempotent`), правка плана без категории (`resolveCategoryForUpdate`).
* Та же схема поиска — у «Хотелок» (`FinancialEventService.createWishlistItem`) и «Кредита» (`CreditPaymentService.creditCategory`). Обе системные, «Настройки» их удалить не дают, но сервер удаляет любую категорию: `CategoryService.delete` признак не проверяет. «Цели» поправлены в #139 (`getOrCreateGoalSpendingCategory`) — поиск вместе с удалёнными.

## Решение

* **Один помощник** — `CategoryService.systemCategory(имя)`. Ищет по имени вместе с удалёнными. Живая категория берётся как есть — и своя категория человека с таким именем тоже, как у «Цели». Удалённая возвращается, отсутствующая заводится — системной категорией расходов без признака основного дохода и без прогноза, как «Цели» с #139. Через него идут все четыре: «Переводы в копилки», «Цели», «Хотелки», «Кредит». ANO-150 добавит владельца здесь — в одном месте.
* **Имена четырёх** — в `SystemCategory`: его описание уже говорит, что это системные категории.
* **«Переводы в копилки» — системная.** Новая заводится системной. Старые базы — миграцией `V30`: по имени — вернуть удалённую, пометить системной, тип расходов, без основного дохода (его держит `chk_primary_income_only_income`), прогноз выключить — выключателя у системной категории на экране нет. Категории нет — миграция её не заводит: продукт заведёт при первом переводе. «Настройки» перестают предлагать удаление и правку — как у трёх других.
* **Метка «меняет-данные»** — `V30` меняет живые данные намеренно.
* Переводы, отвергнутые 07.10, не записались — их повторяют руками (комментарий в задаче 11.10).

## Не закрывает

* **Сервер по-прежнему удаляет системную категорию** через `DELETE /categories/{id}`. «Настройки» этого не предлагают, а продукт вернёт её при следующей записи — для починки отказ сервера не нужен.
* **Что значит «системная»**, экран не объясняет — как и у трёх других. Подача — веха «5. Дизайн».
* **Владелец у категорий** — ANO-150.

## Как проверяется

| что | тест | мутация |
|---|---|---|
| удалённая «Переводы в копилки»: перевод в копилку — 200, та же строка вернулась системной категорией расходов, без основного дохода и прогноза | `FundMoneyFlowIT`, `POST /funds/{id}/transfer` | помощник ищет только среди живых; без признака системной; без снятия прогноза; `getOrCreateFundTransferCategory` — прежний |
| то же — план перевода без категории, как его шлёт быстрый ввод | `FundMoneyFlowIT`, `POST /events` | помощник ищет только среди живых |
| удалённая «Хотелки»: новая хотелка — 201, та же строка вернулась | `FinancialEventControllerIT`, `POST /events/wishlist` | «Хотелки» — прежним поиском |
| удалённая «Кредит»: «Зафиксировать» кредит в примерке ставит график, та же строка вернулась | `CreditPaymentsIT` | «Кредит» — прежним поиском |
| удалённая «Цели»: «потрачено» возвращает её | `FundMoneyFlowIT.delete_spent_revivesDeletedGoalsCategory`, есть с #139 | «Цели» — прежним поиском |
| миграция: удалённая «Переводы в копилки» возвращается системной, тип и признаки — как у продукта | `FundTransferCategoryMigrationIT` — исполняется сам файл `V30` | без возврата удалённой; без снятия прогноза |
| миграция: живая несистемная становится системной | там же | только удалённые |

Миграцию своим прогоном на Testcontainers не проверить: очередь `V30` наступает на пустой таблице. Данные заводятся в тесте, затем исполняется сам файл — как у `V28` и `V29`.

## План

1. Тесты — красные: два в `FundMoneyFlowIT`, по одному в `FinancialEventControllerIT` и `CreditPaymentsIT`, `FundTransferCategoryMigrationIT`.
2. `CategoryService.systemCategory`, имена в `SystemCategory`, четыре вызова через него; `V30__fund_transfer_category_system.sql`. Юниты, которые строят `TargetFundService` и `CreditPaymentService`, — под новый конструктор.
3. Мутации на итоговом коде; полный прогон бэка.
4. Стенд из дампа до `V29`: до — «Переводы в копилки» удалить в «Настройках», пополнить копилку тремя путями; после — сборка из ветки, `V30` на той же базе, «Настройки» и те же три пути; удаление через API и перевод. Стенд — обратно из дампа.

## Характер плановой строки

Не касается: характер переводов, хотелок и платежей по кредиту не меняется. Помощник меняет только то, в какой строке категорий они лежат.

## Как мерил

* **Экземпляр владельца** — `docker logs selfin-backend` и его база, только чтение: отказы 07.10, удалённые категории, переводы после 07.10.
* **Стенд** — `GET /api/v1/version` → `0632652`; удаление — в «Настройках» (`DELETE /categories/…` → 204), перевод — через API продукта (`POST /funds/{id}/transfer`), остаток копилки — ответом той же ручки. Через SQL — ничего.
