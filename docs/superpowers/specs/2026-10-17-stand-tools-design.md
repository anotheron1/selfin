# Инструменты стенда в `tools/`: второй человек, проверка изоляции, удаление человека

Шаг 1 плана спринта 6 (`2026-10-17-sprint-6-plan.md`), часть ANO-197. Решение владельца 17.10 (раздел 3 плана, решение 6): перенести в репозиторий то, чем во «Входе» проверяли изоляцию, — первым шагом вехи.

## Что было

Главная проверка вехи «Вход» — второй человек с настоящим токеном не видит ни одной строки первого — жила в черновиках сессий: временного `tester2` заводили и убирали скриптами из временных папок (ретро спринта 5, раздел 4). Замер 17.10: исходный `second-layer-stand.mjs` из временных папок пропал, единственная копия — `isolation-154.mjs`, 155 строк, во временной папке сессии приёмки ANO-154. На сервере эта проверка нужна сразу после переезда данных владельца (шаг 7 плана).

Второй повод — открытый вход (решение 4): человек вправе попросить удалить его данные, закон даёт на это 30 дней. Удаление со всеми строками — ровно то, чем убирали `tester2`.

## Как

Три команды и один список.

* **`tools/second-person.mjs`** — временный человек: учётная запись в реалме `selfin` через Admin API с **новым случайным паролем на каждый запуск**, токен Bearer через клиент скриптов. Первый запрос с токеном заводит человека со стартовым набором (`Registration`, ANO-151). Клиент скриптов заводится сам, без тестового человека `tester`: на сервере тестового человека быть не должно. Отсюда же — общие помощники: адреса, вход администратора, запрос к API, запрос к базе.
* **`tools/isolation-check.mjs`** — оракул `TwoPeopleIsolationIT` вживую, по копии `isolation-154.mjs`:
  1. чужих id нет ни в одном ответе второго — чужие id берутся из базы ролью владельца таблиц;
  2. по чужому id — 404 у каждой ручки с id в пути;
  3. ссылка на чужую строку в теле записи — отказ;
  4. **у хозяина данных ничего не изменилось** — отпечаток его строк в базе до и после ударов; если есть его токен (на стенде — тестовый человек), то и все его чтения.

  Отпечаток в базе — потому что на сервере хозяин данных — владелец, а его токена у скриптов нет: он входит через Telegram. Хозяин данных по умолчанию — тестовый человек стенда; на сервере — `--victim-sub`. В конце второй человек удаляется (шаг 3 этого списка); `--keep` оставляет его.
* **`tools/delete-person.mjs`** — человек со всеми строками, по `--sub` (id Keycloak) или `--username`:
  1. наши строки — одной транзакцией в порядке из `tools/person-tables.json`, последней — строка `users`;
  2. учётная запись Keycloak — через Admin API.

  Общей транзакции у двух систем нет (ревью Codex на #166): повторный запуск доделывает начатое, в конце команда проверяет оба условия — строк с `user_id` ноль, учётной записи нет — и печатает, что осталось; выход 1, если что-то осталось. `--ours-only` — только наши строки, учётную запись не трогает (ловушка шага 7 плана).
* **`tools/person-tables.json`** — таблицы с владельцем в порядке удаления, дочерние до родителей.

**Порядок удаления и цикл.** В схеме есть цикл: `financial_events.target_fund_id → target_funds` и `target_funds.converted_to_event_id → financial_events`. Простого порядка у цикла нет, но обратная ссылка объявлена `ON DELETE SET NULL` (`V33`), как и `converted_to_*` у событий и копилок. Значит, события удаляются раньше копилок, а ссылки на них из копилок Postgres обнуляет сам. Ссылки строк на свою же таблицу (`parent_event_id`) проверяются в конце оператора — одним `DELETE` по владельцу. Уборка из черновика шла в этом же порядке.

**Сторож порядка — в тесте на двух людей.** Новый тест в `TwoPeopleIsolationIT` заводит двух людей тем же набором, что и проверка изоляции (строки во всех 11 таблицах), и удаляет второго по `person-tables.json`. Проверяется: набор таблиц в списке совпадает с таблицами, где есть `user_id` (новая таблица без строки в списке роняет тест); удаление в этом порядке проходит без нарушения ключей; у второго ноль строк; чтения первого не изменились. Тем же списком команда проверяет схему перед удалением и отказывается работать, если набор таблиц другой: сервер может оказаться новее рабочей копии.

**Адреса — параметрами**, по умолчанию стенд:

| переменная | что | по умолчанию |
|---|---|---|
| `SELFIN_API` | API | `http://127.0.0.1:8081/api/v1` |
| `SELFIN_KC` | Keycloak — токены | `http://127.0.0.1:8180` |
| `SELFIN_KC_ADMIN` | Keycloak — Admin API; на сервере консоль закрыта, путь — через SSH-туннель (шаг 3 плана) | `SELFIN_KC` |
| `SELFIN_PSQL` | команда `psql` ролью владельца таблиц; SQL идёт через stdin, поэтому годится и `ssh … docker compose exec -T db psql …` | `docker exec -i selfin-test-db psql -U admin -d selfin` |

**Клиент скриптов на сервере** — только на время проверки: `isolation-check.mjs --remove-scripts-client` удаляет его в конце. На стенде клиент нужен скриптам и CI — там флаг не ставится.

## План

1. Список `person-tables.json` и сторож в `TwoPeopleIsolationIT` — тест красный на неполном списке и на неверном порядке.
2. Чистые функции с тестами `node --test`: SQL удаления по списку, сверка набора таблиц, поиск чужих id в ответах, сравнение чтений и отпечатков. Тесты — в шаг «Скрипты ворот» CI.
3. Три команды; `keycloak-token.mjs` отдаёт заведение клиента скриптов отдельной функцией.
4. Мутации на итоговом коде.
5. Стенд: второй человек, проверка числами, удаление — в Keycloak его нет, строк с его `user_id` ноль.

## Чего не делаем

* **Согласие** (шаг 4 плана) — его ещё нет. Когда появится, `second-person.mjs` до первого запроса с данными отправит тот же POST согласия.
* **Журнал удалений вне баз** (ANO-197, требование к шагу 5) — удаление печатает итог, журнал ведёт процедура копий.
* **Скрипты `ano50-*`** не трогаем — они под стенд ANO-50 и тестового человека.
