# Прокси на сервере: одна схема на nginx

Вопрос владельца 24.10 к пункту 4 разбора (`2026-10-24-server-questions-analysis.md`). Сервер друга — минимум на полгода, поэтому схема, принятая «на время», проживёт долго. Здесь — варианты с ценой, что говорят о цепочках прокси (со ссылками) и разбор nginx: `server` и `location`, порядок сверки адресов, заголовки за прокси, сертификат через certbot.

## Что сейчас

Путь А из разбора, как задуман:

| запрос | звенья | прокси |
|---|---|---|
| данные (`/api`, вход, выход) | nginx друга → Caddy → nginx экранов → приложение | 3 |
| Keycloak (`/auth`) | nginx друга → Caddy → Keycloak | 2 |
| экраны | nginx друга → Caddy → nginx экранов (файлы) | 2 |

Caddy в шаге 3 взяли ради двух вещей: он сам получает сертификат и сам ставит заголовок «пришло по https» (`2026-10-17-server-compose-design.md`). За nginx друга обе роли переходят к нему. У Caddy остаются раздача (`/auth` — Keycloak, остальное — экраны) и закрытие трёх адресов Keycloak. Это умеет и nginx экранов, который и так стоит на пути и уже передаёт приложению схему и порт.

Ловушка самого пути А: заголовки `X-Forwarded-*` от звена, которому Caddy не доверяет, он отбрасывает и ставит свои ([Caddy, reverse_proxy](https://caddyserver.com/docs/caddyfile/directives/reverse_proxy)). Запрос от nginx друга приходит к нему по http, и без строки `trusted_proxies` приложение и Keycloak получили бы «http». Это находка шага 3 в новом месте: адреса возврата `http`, cookie сеанса без `Secure`.

## Варианты

| вариант | где правила закрытия | файл у друга | звеньев до приложения | цена |
|---|---|---|---|---|
| А. Как задумано: Caddy за nginx друга | `Caddyfile` | маленький | 3 | полдня |
| 1. Правила — в файле nginx друга, Caddy убрать | в нашем файле на сервере друга, копия — в репозитории | большой, меняется вместе с правилами | 2 | день |
| **2. Правила — в nginx экранов, Caddy убрать** (рекомендую) | `frontend/nginx.conf`, в нашем образе | маленький, почти не меняется | 2 | день |
| 3. Как 2, плюс свой nginx с certbot в сборке для будущего своего сервера | как в 2 | как в 2 | 2 | полтора дня |

В цену входит одно и то же для всех: правка конфигов и compose, репетиция на машине стенда (nginx в контейнере перед нашей сборкой, сертификат самоподписанный), проверка закрытых адресов, круг ревью.

**Почему 2.**
* Одна технология раздачи вместо двух. nginx знать придётся в любом случае: дверь у друга — nginx.
* Меньше звеньев — меньше мест, где теряется заголовок или срабатывает чей-то предел (ниже — что говорят об этом).
* Файл у друга маленький и почти не меняется: правила живут в нашем образе, и чтобы их поменять, nginx друга перезагружать не нужно.
* Правила остаются в репозитории — под сторожем по исходнику, как заголовки кэша в `nginxCache.test.ts`, и под проверкой адресов при запуске.
* Переезд на свой сервер ничего не ломает: внутренняя раздача та же, впереди — такой же маленький файл nginx с certbot, как у друга.

**Почему не 1.** Правила безопасности — на чужом сервере. Каждая их правка — перезагрузка nginx, общего с сайтами друга. Две копии файла (в репозитории и на сервере) рано или поздно разойдутся, если кто-то поправит прямо на сервере.

**Почему не 3.** У друга порты 80 и 443 заняты, поэтому наш сертификат и certbot в сборке полгода простоят без дела. На своём сервере проще повторить схему друга: nginx и certbot на самом сервере, тот же маленький файл.

**Почему не А.** Он дешевле на полдня, но оставляет на полгода звено без собственной работы и вторую технологию со своим порядком правил (на нём шаг 3 уже споткнулся: `respond` срабатывал позже `handle`).

**Минус 2.** nginx экранов становится входом и для Keycloak. На стенде Keycloak открывается напрямую (порт 8180), поэтому правило `/auth` там не работает. Проверяет его серверная сборка на машине стенда — так же, как в шаге 3.

## В любом варианте

1. **Закрытые адреса — под автоматической проверкой.** `/auth/admin`, `/auth/realms/master`, `/auth/realms/selfin/account` отвечают 404; проверка — в `tools/keycloak-check.mjs`, к запуску. Плюс два варианта написания (`/auth//admin`, `/auth/%61dmin`): nginx сверяет адрес после раскодирования и склейки слешей, и проверка это подтвердит. Keycloak сам советует не выставлять наружу ещё и свой корень ([Keycloak, reverse proxy](https://www.keycloak.org/server/reverseproxy)) — `/auth/` стоит добавить четвёртым адресом.
2. **Заголовки https и порта.** Внешнее звено ставит `Host` и `X-Forwarded-Proto: https` и **перезаписывает** `X-Forwarded-For` адресом клиента; внутренние передают их дальше. Порт: на 443 его нет в адресе, заголовок порта не уходит, и Tomcat берёт порт схемы — так задумано в шаге 3.
3. **Предел размера запроса и тайм-ауты — явно на каждом звене.** В цепочке срабатывает самый маленький предел и самый короткий тайм-аут. У nginx по умолчанию тело запроса — до 1 МБ (иначе ответ 413), тайм-ауты — 60 секунд ([nginx, core](https://nginx.org/en/docs/http/ngx_http_core_module.html), [nginx, proxy](https://nginx.org/en/docs/http/ngx_http_proxy_module.html)). Нашим запросам 1 МБ хватает с запасом: загрузки файлов в приложении нет. Значения ставим явно, чтобы предел был решением, а не случайностью.

## Что говорят о цепочках прокси

* **У каждого звена свои умолчания.** nginx, если не сказать иначе, подменяет `Host` именем того, куда передаёт, и ставит свои тайм-ауты и предел тела ([nginx, proxy](https://nginx.org/en/docs/http/ngx_http_proxy_module.html)). Звено, которое никто не настраивал, меняет запрос молча.
* **Главное в цепочке — каким заголовкам верить.** Keycloak требует, чтобы прокси перезаписывал `X-Forwarded-*`, а не дописывал: иначе клиент подставит чужой IP или чужое имя хоста, и это ударит по журналам и защите от перебора ([Keycloak](https://www.keycloak.org/server/reverseproxy)). В `X-Forwarded-For` доверять можно только правой части — левую пишет сам клиент. А добавление или удаление звена молча меняет, какой адрес приложение считает настоящим ([Adam Pritchard, The perils of the "real" client IP](https://adam-p.ca/blog/2022/03/x-forwarded-for/)). Отсюда правило: внешнее звено перезаписывает, внутренние дописывают.
* **Недоверенному звену не верят вовсе.** Caddy по умолчанию отбрасывает `X-Forwarded-*` от того, кого не знает, и ставит свои ([Caddy](https://caddyserver.com/docs/caddyfile/directives/reverse_proxy)). Это защита, но в цепочке её надо настраивать: иначе https теряется посередине.
* **Наследование заголовков в nginx.** `proxy_set_header`, заданный в `location`, целиком отменяет все такие же директивы уровня выше — это одна из десяти частых ошибок в конфигах nginx ([F5 NGINX, Avoiding the Top 10 NGINX Configuration Mistakes](https://www.f5.com/company/blog/nginx/avoiding-top-10-nginx-configuration-mistakes)). В цепочке одна забытая строка ломает всё, что за ней.
* **Звено без своей работы — случайная сложность.** В книге Google SRE её отделяют от неизбежной: случайную можно убрать инженерным усилием, и каждая лишняя строка — обуза, а не актив ([Google SRE, Simplicity](https://sre.google/sre-book/simplicity/)).

Задержка от лишнего звена внутри одного сервера — доли миллисекунды, и довод не в ней. Довод — в местах, где можно ошибиться, и в том, что надо знать и чинить.

## nginx для владельца

### `server` — какой сайт

nginx смотрит, на какой адрес и порт пришёл запрос, и среди блоков `server`, которые их слушают, ищет имя из запроса (`server_name`). Порядок поиска: точное имя, потом имена со звёздочкой в начале и в конце, потом регулярные выражения по порядку в файле. Не нашлось — запрос получает сайт по умолчанию для этого порта: `default_server`, а если такого нет — первый блок ([nginx, core](https://nginx.org/en/docs/http/ngx_http_core_module.html)). По HTTPS имя приходит ещё до шифрования, и по нему же nginx выбирает сертификат. Поэтому наш блок с нашим именем стоит рядом с сайтами друга и им не мешает.

### `location` — какое правило внутри сайта

Порядок сверки адреса ([nginx, core](https://nginx.org/en/docs/http/ngx_http_core_module.html)):

1. `location = /путь` — точное совпадение: нашлось — сразу оно, дальше не ищут.
2. Обычные префиксы `location /путь` — запоминается самый длинный совпавший.
3. Если у него пометка `^~` — берётся он, регулярные выражения не проверяются.
4. Иначе проверяются регулярные выражения (`~`, `~*`) по порядку в файле: первое совпавшее побеждает.
5. Ни одно не совпало — работает запомненный префикс.

На наших адресах (вариант 2):

| адрес | что выберет nginx |
|---|---|
| `/auth/admin/master/console` | самый длинный префикс — `/auth/admin` с `^~`: ответ 404, регулярки не смотрим |
| `/auth/realms/selfin/protocol/openid-connect/auth` | самый длинный префикс — `/auth/`; регулярка про `/api` не совпала — значит, в Keycloak |
| `/api/v1/me` | префикс — только `/`; совпала регулярка `^/(api/\|oauth2/\|login/oauth2/\|logout$)` — значит, в приложение |

Зачем `^~` на закрытых адресах: без неё регулярка, добавленная когда-нибудь потом, могла бы перехватить закрытый адрес и отправить его в Keycloak. Это ровно та ошибка порядка, на которой шаг 3 споткнулся в Caddy.

Сверяется адрес после «нормализации»: `%61` раскодируется в `a`, `.` и `..` разрешаются, двойные слеши склеиваются. Поэтому `/auth//admin` и `/auth/%61dmin` попадают в то же закрытое правило.

### `proxy_pass` — куда передать

* Без пути (`proxy_pass http://keycloak:8080;`) адрес уходит дальше как есть: `/auth/realms/...`.
* С путём, даже с одним слешем (`proxy_pass http://keycloak:8080/;`), совпавшая с `location` часть заменяется. `/auth/` отрежется, а Keycloak живёт под `/auth` — и ответит 404. Классическая ошибка в один символ ([nginx, proxy](https://nginx.org/en/docs/http/ngx_http_proxy_module.html)).
* Имя в `proxy_pass` nginx ищет один раз, при старте. Через переменную и `resolver` — на каждый запрос. Так nginx экранов уже ходит к приложению (находка 15.10: без этого он падал, если приложение поднималось позже). Так же он будет ходить и к Keycloak.

### Заголовки за прокси

| заголовок | кто ставит | зачем |
|---|---|---|
| `Host` | каждое звено — явно | по умолчанию nginx подставит имя, куда передаёт (`keycloak:8080`), и приложение построит адреса от него |
| `X-Forwarded-Proto` | внешнее звено — `https`; внутренние передают дальше | только внешнее знает, что было шифрование; это делает `map $forwarded_proto` в nginx экранов |
| `X-Forwarded-Port` | никто, пока порт стандартный | на 443 порта в адресе нет, и Tomcat берёт порт схемы (шаг 3) |
| `X-Forwarded-For` | внешнее — перезаписывает адресом клиента (`$remote_addr`), внутренние дописывают (`$proxy_add_x_forwarded_for`) | иначе клиент впишет слева любой IP, и Keycloak ему поверит |

И ловушка наследования: один `proxy_set_header` внутри `location` отменяет все, заданные на уровне `server`. Поэтому в наших конфигах заголовки пишутся в каждом `location` целиком.

### Сертификат через certbot

1. В нашем файле — блок на порт 80: адрес `/.well-known/acme-challenge/` отдаётся из нашей папки, остальное перенаправляется на https.
2. `certbot certonly --webroot -w /var/www/selfin-acme -d <имя> --deploy-hook "nginx -t && systemctl reload nginx"`. Let's Encrypt просит выложить код по этому адресу; certbot кладёт файл в папку, nginx его отдаёт — сертификат выдан. Режим `certonly` ничего не настраивает в nginx, а хук срабатывает и при каждом продлении ([certbot](https://eff-certbot.readthedocs.io/en/stable/using.html)).
3. Только потом — блок на 443 со ссылками на файлы сертификата. Раньше нельзя: файлов ещё нет, и `nginx -t` не пройдёт.
4. Продлевает таймер certbot, который уже работает у друга: проверка дважды в сутки, продление — когда осталось меньше трети срока.
5. Срок сокращается: сейчас 90 дней, с февраля 2027 — 64, с февраля 2028 — 45 ([Let's Encrypt, сроки сертификатов](https://letsencrypt.org/docs/cert-lifetimes/)). Продлевать руками не выйдет, только автоматика. Писем об истечении Let's Encrypt с июня 2025 не присылает ([Let's Encrypt](https://letsencrypt.org/2025/06/26/expiration-notification-service-has-ended)) — за сертификатом следит проверка сайта из пункта 10.

## Как это выглядит в варианте 2

Наш единственный файл у друга — `/etc/nginx/conf.d/selfin.conf`, набросок:

```nginx
server {
    listen 80;
    server_name <имя>;
    location ^~ /.well-known/acme-challenge/ { root /var/www/selfin-acme; }   # проверка Let's Encrypt
    location / { return 301 https://$host$request_uri; }
}

server {
    listen 443 ssl;
    server_name <имя>;
    ssl_certificate     /etc/letsencrypt/live/<имя>/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/<имя>/privkey.pem;
    client_max_body_size 1m;

    location / {
        proxy_pass http://127.0.0.1:<порт>;              # nginx экранов, слушает только внутри сервера
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-Proto $scheme;      # https
        proxy_set_header X-Forwarded-For $remote_addr;   # перезаписать: клиенту не верим
        proxy_read_timeout 60s;
    }
}
```

В `frontend/nginx.conf` — правила, перенесённые из `Caddyfile`, набросок:

```nginx
client_max_body_size 1m;

# Keycloak снаружи — только вход, выход и возврат из Telegram. ^~ — регулярки закрытое не перехватят.
location ^~ /auth/admin                 { return 404; }
location ^~ /auth/realms/master         { return 404; }
location ^~ /auth/realms/selfin/account { return 404; }
location = /auth/                       { return 404; }   # корень — тоже не наружу (совет Keycloak)

location /auth/ {
    set $keycloak http://keycloak:8080;                    # имя — на каждый запрос, как у приложения
    proxy_pass $keycloak;                                  # без пути: Keycloak получает /auth/... как есть
    proxy_set_header Host $http_host;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $forwarded_proto;
    proxy_set_header X-Forwarded-Port $forwarded_port;
    proxy_read_timeout 60s;
}
```

Из compose уходят Caddy и `Caddyfile`, nginx экранов слушает `127.0.0.1:<порт>`. Порт — не 8000 (бот друга), не 8180 (консоль Keycloak) и не 8443 (занят).
