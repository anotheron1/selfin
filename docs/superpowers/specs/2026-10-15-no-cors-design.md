# CORS — убрать: экран и API на одном адресе (ANO-153)

Шаг 12 спринта 5 (`2026-10-11-sprint-5-plan.md`, раздел 3). Спека и план — одним документом. Факультатив — блок 5, вне git: раздел о CORS пишется здесь, остальное — с ANO-152.

Задача — снять открытый CORS: `allowedOrigins("*")` разрешает любой странице читать ответы нашего API.

## Что есть сейчас

* **`config/WebConfig`** — `allowedOrigins("*")` на `/**`, методы GET, POST, PUT, DELETE, OPTIONS, PATCH. Комментарий в коде: «In production change this to frontend url».
* **Spring Security подхватывает его сам:** при Spring MVC в контексте есть `CorsConfigurationSource` — `HandlerMappingIntrospector`, — и цепочки безопасности получают фильтр CORS с этими правилами. Предзапрос с чужого адреса отвечает 200 и `Access-Control-Allow-Origin: *` ещё до проверки входа.
* **По Р-1 = Б** (решение владельца 12.10) экран и API — на одном адресе: в докере nginx экрана проксирует `/api/`, вход и выход на бэк, в разработке — прокси Vite. Кросс-доменных запросов из браузера у нас нет.
* **Для сервера запросы экрана — однодоменные.** nginx передаёт `Host` с портом (`$http_host`), прокси Vite хост не меняет: `Origin` и адрес запроса совпадают, и Spring не считает их запросами CORS.

## Решение

**`WebConfig` удаляется целиком.** Правил CORS нет — нет и разрешений: на запрос с чужого адреса сервер не отдаёт `Access-Control-Allow-*`, и браузер не покажет ответ чужой странице; предзапрос с чужого адреса — без разрешений.

| | что | чем плохо |
|---|---|---|
| **А** | **убрать** | — |
| Б | сузить до адреса разработки | разработке он не нужен — прокси Vite однодоменный; а на сервере с HTTPS за прокси схема в `Origin` (https) и у запроса (http) расходится — Spring счёл бы запись экрана чужой и отказал 403 |
| В | сузить до адреса сервера | адрес — забота «Выкладки» (ANO-197), а нужды нет: запросы экрана однодоменные |

От подделки запросов чужой страницей CORS и не защищает — запрос уходит и без разрешения, браузер лишь не отдаёт ответ. Защищает CSRF (ANO-195): токен в cookie `XSRF-TOKEN`, которую чужая страница не прочтёт, и cookie сеанса `SameSite=Lax`.

## Как проверяется

`SignInIT` — граница браузера:

| что | проверка | мутация |
|---|---|---|
| чужой странице ответ не отдаётся | `GET /api/v1/version` с `Origin` чужого адреса — без `Access-Control-Allow-Origin` | вернуть `WebConfig` |
| предзапрос с чужого адреса — без разрешений | `OPTIONS` с `Origin` и `Access-Control-Request-Method` — без `Access-Control-Allow-Origin` | вернуть `WebConfig` |

На стенде — те же два запроса `curl` до и после, и вход целиком (`tools/keycloak-check.mjs`): экран с записью через прокси работает как прежде.

## Как мерил

* **Где CORS** — поиск `cors`, `allowedOrigins`, `CrossOrigin` по `backend/src`, `frontend/src`, `vite.config.ts`, `nginx.conf`: одна настройка — `WebConfig`.
* **Что видит сервер за прокси** — `frontend/nginx.conf` (`proxy_set_header Host $http_host`) и `frontend/vite.config.ts` (прокси без `changeOrigin`).
* **Как Spring решает, что запрос — CORS** — `CorsUtils.isCorsRequest`: заголовок `Origin` и несовпадение схемы, хоста или порта с адресом запроса; без правил `DefaultCorsProcessor` запрос не отвергает и разрешений не пишет.
