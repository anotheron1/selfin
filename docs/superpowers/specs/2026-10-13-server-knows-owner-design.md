# Сервер узнаёт владельца запроса: вход через наш сервер, Bearer для скриптов (ANO-195)

Шаг 4 спринта 5 (`2026-10-11-sprint-5-plan.md`, раздел 3). Р-1 решён владельцем 12.10: **Б** — сервер держит токены, у браузера только cookie сеанса. Уточнения по ревью Codex на #143 и #147 — комментарии в ANO-195 и ANO-152. Спека и план — одним документом. Факультатив — блок 4, вне git.

## Что есть сейчас

* **Входа нет.** В зависимостях нет даже `spring-boot-starter-security`; все 63 ручки открыты. CORS — `allowedOrigins("*")` (`WebConfig`, ANO-153).
* **Фронт** ходит в API одним `request()` (`frontend/src/api/client.ts`): в разработке — абсолютным `VITE_API_URL=http://localhost:8080/api/v1` из `.env.development`, в docker — относительным `/api/v1`, nginx проксирует на бэк только `/api/` и шлёт `Host` без порта.
* **Keycloak** — на стенде (#145): `http://127.0.0.1:8180`, реалм `selfin` из `keycloak/selfin-realm.json`, Telegram — провайдер. Клиента для нашего сервера в реалме нет. В реалме одна учётная запись — владельца, `sub` `a705ad03-…` (блок 2, раздел 6).
* **`users`** (#146, `V31`): синтетический владелец `00000000-0000-0000-0000-000000000001` с пустым `external_id`; у `user_id` во всех 11 таблицах значение по умолчанию — он. Запись пока владельца не знает.
* **Кто зовёт API без входа:** 30 IT — через `MockMvc`; сеятель CI `tools/seed-synthetic.mjs` и `tools/ci-migrations.sh`; скрипты стенда `tools/ano50-*.mjs`.

## Решение

### Две цепочки фильтров

* **Скрипты и CI — по Bearer**, своя цепочка: выбирается по заголовку `Authorization`, без сеанса и без CSRF. Токен проверяется полностью: подпись — по ключам реалма, срок, издатель и **аудитория `selfin`**. `aud = account` у токена консоли учётной записи (блок 3) — чужая аудитория: такой токен — 401.
* **Браузер — через наш сервер** (`oauth2Login`): конфиденциальный клиент `selfin`, код с PKCE S256 — Spring Security 7 шлёт PKCE и конфиденциальному клиенту. Токены остаются на сервере, у браузера — cookie сеанса `JSESSIONID`, `HttpOnly`, `SameSite=Lax`.
  * **CSRF** — `csrf.spa()` Spring Security 7: токен в cookie `XSRF-TOKEN`, которую читает JS; фронт возвращает его заголовком `X-XSRF-TOKEN` на каждый POST, PUT, PATCH и DELETE.
  * **Без сеанса:** `/api/**` — **401**, остальное — 302 на вход. Переадресацию `fetch` прошёл бы до Keycloak и упал бы на CORS, а 401 фронт так и не увидел бы (ревью Codex на #147, комментарий в ANO-195).
  * **После входа — на `/`**, без «сохранённого запроса»: иначе после входа браузер ушёл бы на `/api/v1/…`, с которого начался вход, и показал бы JSON.
* **Открыто без входа:** `/api/v1/version` — по нему ждут готовности и сверяют коммит сборки (ANO-194), и `/error` — страница ошибки Spring. Отдельной проверки здоровья у бэка нет.

### Два адреса Keycloak

Браузер видит Keycloak по адресу на машине — `http://127.0.0.1:8180`, от него же издатель в токенах. Сервер в docker по этому адресу Keycloak не достанет: `127.0.0.1` внутри контейнера — сам контейнер. Поэтому адресов два — `selfin.keycloak.url` и `selfin.keycloak.internal-url`; без docker они совпадают.

* Вход браузера — по внешнему адресу; обмен кода на токены и ключи реалма — по внутреннему.
* **Discovery не делаем:** Spring Boot идёт в discovery, только если задан `issuer-uri`, и требует, чтобы издатель из ответа совпал с адресом запроса, — а издатель внешний. Адреса заданы явно; сервер стартует и без поднятого Keycloak.
* **Bearer:** издатель сверяется строкой, ключи берутся по внутреннему адресу — Boot умеет это сам, `issuer-uri` вместе с `jwk-set-uri`.
* **Цена:** `iss` в ID token при входе браузера Spring не сверяет — без discovery он его не знает. ID token приходит прямым запросом сервера к Keycloak в обмен на код и секрет клиента, подпись проверяется по ключам реалма. Выходу через Keycloak (ANO-152) нужен `end_session_endpoint`, а его без discovery тоже нет — тогда регистрация клиента переедет в код, и издатель встанет туда же.

### Реалм

* **Клиент `selfin`** — в `keycloak/selfin-realm.json`, этот файл пойдёт и на сервер. Конфиденциальный, только код с PKCE S256: ни пароля, ни сервисной учётной записи. Адреса возврата — разработка и стенд: `127.0.0.1` и `localhost`, порты 5173 и 5174. `fullScopeAllowed: false`, области по умолчанию — только `basic`: в токенах `sub` без имени и почты — серверу больше не нужно (блок 2, раздел 6).
* **Секрет клиента — из окружения:** `${SELFIN_CLIENT_SECRET}`; compose стенда передаёт одно значение и Keycloak, и бэку, по умолчанию — `selfin-dev-secret`. На сервере — свой секрет, без значения по умолчанию (ANO-197).
* **Скриптам — клиент `selfin-scripts`**: сервисная учётная запись и маппер аудитории `selfin`. **Его нет в файле реалма:** на сервере он открыл бы API в обход Telegram любому, кто знает секрет из репозитория. Заводит его `tools/keycloak-token.mjs` — частичным импортом через Admin API, только на стенде и в CI, вместе с **тестовым человеком с паролем** для проверки входа без Telegram. Импорт не перезаписывает: чего нет — заводит, что есть — не трогает.
* `tools/keycloak-token.mjs` печатает токен скриптов: срок — час, на весь прогон CI.

### Владелец запроса

* **`sub` Keycloak → строка `users`** по `external_id`. Незнакомый `sub` — новая строка, свой id (заводится при первом обращении). До ограничителя (шаг 5) у таких строк нет данных: запись ставит владельца значением по умолчанию — синтетического.
* **Промежуток до шага 5 — однопользовательский** (ревью Codex на #143): кто бы ни вошёл, видит все данные, а записанное им достаётся синтетическому владельцу. Тестировщики приходят с «Выкладкой»; стенд и экземпляр — на машине владельца. Войти может любой с Telegram (ANO-197) — до «Выкладки» это не дыра.
* **Синтетический владелец — тому, чей `sub` в `SELFIN_OWNER_SUB`.** Когда этот `sub` пришёл впервые, а синтетический ещё ни с кем не связан, сервер связывает их — и человек видит свои нынешние данные. Связь — один раз: смена настройки данные не переносит. Если человек вошёл до настройки — у него уже своя пустая строка, и связи не будет: строку удалить (данных у неё нет до шага 8) и войти снова.
  * стенд — `sub` владельца из реалма стенда;
  * CI — `sub` сервисной учётной записи скриптов: сеятель пишет данные «как владелец», как и на настоящей базе.
* **`GET /api/v1/me`** → `{"id": "…"}` — чей это запрос. Нужен тестам и замеру на стенде: до шага 5 по экрану не отличить, связан ли вход с синтетическим владельцем. ANO-152 пригодится: «вошёл ли я».

### Фронт — минимальный вход

* `client.ts`: адрес API — всегда относительный `/api/v1`; на 401 — уход на `/oauth2/authorization/keycloak`; на POST, PUT, PATCH, DELETE — заголовок `X-XSRF-TOKEN` из cookie.
* Вход, возврат и выход — на сервер тем же адресом, что и экран, иначе cookie сеанса и CSRF останутся у другого адреса: прокси Vite и nginx — `/api/`, `/oauth2/`, `/login/oauth2/`, `/logout`.
* nginx — `Host` с портом (`$http_host`): от него Spring строит адрес возврата, без порта он ушёл бы на `http://127.0.0.1/…`.
* `VITE_API_URL` из `.env.development` убран: абсолютный адрес шёл мимо прокси — без cookie сеанса и CSRF.
* Экрана входа нет: Keycloak показывает свою страницу — кнопку Telegram и форму пароля. Свой экран, `kc_idp_hint`, выход — ANO-152.

### Тесты, сеятель, CI

* **30 IT — вошедшим человеком:** `MockMvc` по умолчанию добавляет к каждому запросу вход через Keycloak и CSRF (`testsupport`). Тесты денег о входе не знают — их предмет не меняется.
* **Поведение входа — свой IT** со своим `MockMvc`, без входа по умолчанию, и с настоящими подписанными токенами: ключи реалма отдаёт HTTP-сервер JDK в самом тесте. Так проверяется настройка Boot целиком — подпись, издатель, аудитория.
* **Сеятель и `ano50-invariants.mjs`** берут токен из `SELFIN_TOKEN` и шлют его заголовком. Этапные скрипты ANO-50 — история завершённого прохода, их не трогаем.
* **`ci-migrations.sh`** поднимает Keycloak с реалмом из PR, берёт токен через `tools/keycloak-token.mjs`, передаёт его сеятелю и всем запросам, а обоим образам — адреса Keycloak и `SELFIN_OWNER_SUB`. Образ `main` без входа их не замечает.
* **Сеятель ветки на образе ветки — до PR** (комментарий в ANO-135): `tools/ci-migrations.sh <образ ветки> <образ ветки> tools/seed-synthetic.mjs`. В CI этого PR сеятель — из `main`, он ещё без токена; правку сеятеля CI проверит только в следующем PR.

### Экземпляр владельца

**Решение владельца 13.10 — не пересобирать до «Выкладки».** Варианты были: свой Keycloak у экземпляра (второй адрес в Allowed URLs бота; настоящие данные — за недостроенным входом) и Keycloak стенда (экземпляр перестаёт пускать при каждой пересборке стенда).

* `docker-compose.yml` остаётся без Keycloak. Пересобранный из `main` после ANO-195 экземпляр уведёт экран на вход, а вход не пройдёт: обменять код на токены не с кем.
* Нужна правка у себя до «Выкладки» — пересобрать из `4f90947`, последнего `main` до ANO-195.
* Данные владельца переедут на сервер через ANO-154 и «Выкладку».
* Спека ANO-143 обещала Keycloak экземпляру «в ANO-195» — это обещание снято этим решением.

* **CORS** — ANO-153.
* **Владелец в транзакции и ограничитель** — ANO-144; владелец в ядре и запросах — ANO-149, ANO-147; стартовый набор новому человеку — ANO-151.
* **Кого пускать** — всех с Telegram или список — ANO-197; там же HTTPS, `Secure` у cookie, заголовки прокси, секрет и адреса возврата сервера.
* **Длина сеанса.** Сеанс Tomcat по умолчанию — 30 минут без действий, в памяти: перезапуск бэка — вход заново. Сеанс Keycloak ещё жив — вход пройдёт без подтверждения в Telegram. Решать с экраном входа (ANO-152).
* **Swagger** — за входом; через порт бэка напрямую вход не пройдёт: такого адреса возврата у клиента нет.
* **Скрипты от имени человека после шага 5.** Сервисная учётная запись скриптов — отдельный человек; после ограничителя она увидит только своё. Как скрипты стенда читают данные владельца — ANO-148 и ANO-154.

## Найдено по ходу

* **Вывод «`csrf.spa()` грузит токен лениво» — неверный, его сняла мутация.** Тест `sessionGivesCsrfCookie` краснел в полном прогоне класса и зеленел поодиночке. Я решил, что в 7.0.3 cookie на GET не выписывается, и дописал фильтр, грузящий токен на каждом запросе; одиночный прогон с фильтром «подтвердил», без фильтра я его не гонял. Мутация M7 — фильтр без тела — выжила: `spa()` в 7.0.3 сам отключает отложенную загрузку (`setCsrfRequestAttributeName(null)` у обработчика, видно в байткоде), cookie есть на каждом ответе. Краснел тест из-за `csrf()` в соседних тестах — следующий пункт. Фильтр убран.
* **`csrf()` из spring-security-test подменяет хранилище токенов в самом фильтре контекста**, и подмена переживает тест: проверка cookie краснела только в полном прогоне класса, поодиночке — зелёная. В `SignInIT` токен берётся у сервера, как его берёт экран.
* **Boot 4 не подставляет адрес возврата своему провайдеру** — без `redirect-uri` сервер не стартует: «redirectUri cannot be empty».
* **401 держала не только точка входа `/api/**`:** запасная точка входа — первая в списке, та же 401, и подмена шаблона выживала на запросе без `Accept`. Тест шлёт к API и `Accept: text/html`, как адресная строка браузера.
* **POST без сеанса и без CSRF — 403, а не 401:** CSRF проверяется раньше входа. У экрана cookie `XSRF-TOKEN` остаётся и после истёкшего сеанса — запись получит 401 и уйдёт на вход.
* **Частичный импорт не заводит сервисную учётную запись клиента** — client credentials отвечал 401 «service account … does not exist». Учётная запись передаётся среди людей, с `serviceAccountClientId`.
* **`tools/ano50-reset-stand.sh` ждал готовности по `/pocket`** — после входа там 401; ждёт `/version`.
