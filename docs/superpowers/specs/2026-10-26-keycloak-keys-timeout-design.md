# Ключи Keycloak — с запасом по времени (ANO-244)

Находка шага 6.1 плана спринта 6 (25.10): бэк стенда поднялся, и первый вход через 44 секунды упал — в журнале `Read timed out` на запросе ключей реалма (`…/protocol/openid-connect/certs`). Второй прогон через пару минут прошёл. На сервере бэк перезапускается при каждом обновлении, а Keycloak холодный после каждой перезагрузки у друга — первый вход человека после неё упал бы так же.

## Причина

Своего тайм-аута в проекте нет. Его задаёт Spring Security 7.0.3: `NimbusJwtDecoder.withJwkSetUri(…).build()` без своего клиента ходит за ключами через `RestTemplateWithNimbusDefaultTimeouts` — **соединение и чтение по 500 мс**. Так собраны оба декодера:

* **Bearer** (скрипты и CI) — декодер собирает Boot 4.0.3 по `spring.security.oauth2.resourceserver.jwt.*`;
* **вход через браузер** — ID token проверяет декодер из `OidcIdTokenDecoderFactory`.

Ключи декодер кэширует: падает только первый вход после старта бэка, если Keycloak в этот момент отвечает дольше полусекунды. На стенде Keycloak в режиме разработки простоял 43 часа; на сервере 26.10 бэк поднимался трижды при прогретом Keycloak — тайм-аутов нет. Опасный случай — холодный Keycloak: перезагрузка сервера (стартуют оба сразу) или перезапуск самого Keycloak.

## Решение

**Тайм-аут с запасом, а не повтор.** Один клиент для ключей обоих декодеров: соединение — 2 с, чтение — 5 с. Холодный Keycloak успевает ответить — первый вход подождёт, а не упадёт; мёртвый Keycloak — отказ через 5 с, а не вечное ожидание.

* **Bearer** — бин `JwkSetUriJwtDecoderBuilderCustomizer`: Boot сам применяет его к своему декодеру. Меняется только клиент; проверки — подпись, срок, издатель, аудитория `selfin` — остаются Boot.
* **Вход через браузер** — бин `JwtDecoderFactory<ClientRegistration>`: его берёт `oauth2Login` вместо `OidcIdTokenDecoderFactory`. У той в 7.0.3 настроек клиента нет (класс `final`), поэтому фабрика строит тот же декодер, что и она, — RS256, проверки `JwtTimestampValidator` и `OidcIdTokenValidator`, конвертер типов по умолчанию, — только со своим клиентом. Декодер — один на регистрацию, как у оригинала: иначе ключи запрашивались бы на каждый вход.
* **`keycloak-check`** — адрес из ответа сервера бывает относительным (выход без сеанса Keycloak отдаёт `/login`), и инструмент падал на нём, не дописав итог (25.10: `Failed to parse URL from /login`). Относительный адрес — от адреса экрана; провал входа — строками «НЕТ», а не падением.

## Чего не делаем

* **Повтор запроса ключей.** С теми же 500 мс на медленном Keycloak повтор падает так же; запас лечит обе причины одним местом.
* **Прогрев ключей при старте бэка.** Если Keycloak ещё не поднялся, прогрев упрётся в то же; а декодер входа заводится лениво, на первом входе.
* **Свой декодер Bearer целиком.** Проверки издателя и аудитории Boot собирает сам — настройщик трогает только клиента, и проверки не разъезжаются с конфигурацией.

## План

1. Тесты — красные на нынешнем коде: ключи отвечают за секунду — декодер библиотеки по умолчанию падает (контроль), наши декодеры обоих путей проходят; проверки ID token на месте (чужая аудитория, чужой издатель, истёкший — отказ); один декодер на регистрацию — ключи запрашиваются один раз; Keycloak молчит дольше запаса — отказ, а не ожидание. Контекст приложения: Bearer-декодер Boot и фабрика из контекста ждут ключи секунду.
2. Починка — `SecurityConfig`: клиент ключей, настройщик Bearer, фабрика декодеров входа; `tools/keycloak-check.mjs` — относительный адрес.
3. Мутации на итоговом коде — каждая правка своим тестом.
4. Стенд до и после: посредник между бэком и Keycloak задерживает ключи на 1,5 с.

## Как мерил

* **Тайм-аут библиотеки** — `javap` классов из `~/.m2`: `spring-security-oauth2-jose-7.0.3`, `NimbusJwtDecoder$RestTemplateWithNimbusDefaultTimeouts` — `sipush 500` в `setConnectTimeout` и `setReadTimeout`; `spring-security-oauth2-client-7.0.3`, `OidcIdTokenDecoderFactory.buildDecoder` — `withJwkSetUri(…).jwsAlgorithm(…).build()` без клиента, открытых настроек клиента у фабрики нет; `spring-security-config-7.0.3`, `OAuth2LoginConfigurer.getJwtDecoderFactoryBean` — бин `JwtDecoderFactory<ClientRegistration>` из контекста уходит в `OidcAuthorizationCodeAuthenticationProvider`; `spring-boot-security-oauth2-resource-server-4.0.3`, `JwtDecoderConfiguration` — `JwkSetUriJwtDecoderBuilderCustomizer` применяется в обоих путях сборки декодера.
* **Случаи** — журнал бэка стенда с 25.10: один — тот самый, 14:49:21 (`AuthenticationServiceException` ← `RemoteKeySourceException` ← `SocketTimeoutException: Read timed out`); журнал бэка сервера за 26.10 — ни одного.
* **Стенд до и после** — посредник в сети стенда отдаёт `/realms/selfin/protocol/openid-connect/certs` через 1,5 с, остальное — сразу; бэк стенда ходит в Keycloak через него и перед каждым прогоном перезапускается — ключей в кэше нет; прогон — `tools/keycloak-check.mjs`.

## Выполнено

26.10, ветка `fix/jwks-timeouts`.

1. **Тесты сначала красные.** `KeycloakKeysTimeoutTest` на заготовке, где декодеры ещё с клиентом библиотеки: оба «ключи за секунду» упали `Read timed out` через полсекунды — та же ошибка, что на стенде 25.10; контроль и остальные — зелёные. С клиентом — 6 из 6. `KeycloakKeysTimeoutIT` — декодеры из контекста приложения — 2 из 2.
2. **Мутации на итоговом коде — 8 из 8 красные**, каждая своим тестом: ключи ждём 500 мс; без тайм-аута чтения; вход без своего клиента; Bearer без своего клиента; ID token без проверок OIDC; декодер на каждый вход; настройщик Bearer — не бин; фабрика входа — не бин (две последние ловит интеграционный тест). Оба контрольных прогона — зелёные.
3. **Полный прогон бэка** — 510 модульных и 384 интеграционных, зелёный.
4. **Стенд до и после.** Посредник на машине отдаёт ключи реалма через 1,5 с, остальное — сразу; бэк стенда ходит в Keycloak через него.
   * **До — `main`** (образ `sha-d49d31e`; бэк после него не менялся): вход не открыл сеанс — обратный вызов увёл на экран входа (302), дальше 401; в журнале бэка — `Read timed out`. Прежний `keycloak-check` упал `TypeError: Failed to parse URL from /login`, не дописав итог; исправленный — «Итог: не сходится — 8».
   * **После — ветка** (`fad2acf`): `keycloak-check` — 41 из 41: сеанс открыт, Bearer скриптов — тот же человек; посредник отдал ключи обоим декодерам за 1,52 с — оба дождались; тайм-аутов в журнале нет.
   * Стенд возвращён: бэк ходит в Keycloak напрямую, бэк и фронт — `fad2acf`, `keycloak-check` — 41 из 41.
5. **Ловушка замера.** Первый посредник пересылал заголовки соединения как есть: клиент JDK предлагает HTTP/2 через `Upgrade: h2c`, Keycloak соглашался, а ответ 101 посредник не умел — обмен кода на токен висел минуту, и nginx экранов отдавал 504 и «до», и «после». Посредник, как положено прокси, теперь заголовков соединения не пересылает. Продукта это не касается: бэк ходит в Keycloak напрямую.

**Чего не ловит.** Проверка `keycloak-check` «Bearer скриптов — тот же человек, что вошёл формой» проходит и тогда, когда не вышло ни то, ни другое — оба `null` (так было «до»). Провал входа и так виден строками выше; поправить — при следующей правке инструмента.
