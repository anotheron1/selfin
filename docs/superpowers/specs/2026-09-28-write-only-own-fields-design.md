# «Что с капиталом» и форма журнала пишут только своё (ANO-162)

Блок A спринта 26.09, задача A7. Вариант А — решение владельца 28.09: каждый пишет только то, что меняет, три части одним PR.

## Что сломано

Задача заведена 16.09 по коду: «запись хотелки из «Что с капиталом» стирает поля, о которых не знает форма» — исходный текст суммы. Замер 28.09 на стенде `4ba189b` — код этих путей тот же, что в `main` `1b8e340`; раздел «Как мерил». Главное оказалось не там.

Корень один. `PUT /funds/{id}` и `PUT /events/{id}` переписывают запись целиком тем, что прислали: отсутствующий счёт копилки сервер читает как «отвязать» (ANO-158 — так отвязывает форма «Целей»), отсутствующую копилку и исходный текст события — как «пусто». А пишущие шлют только то, что знают: «Что с капиталом» (`persistTrial`) — параметры примерки, имя из ответа примерки, где пустое описание уже заменено категорией; форма журнала — свои поля, без копилки. Хотелка без срока не пишется вовсе: `PUT /events` требует дату.

Примерка на «Хотелках» так не ломается: она фиксирует через `POST /wishlist/items/{id}/fix` (`applyAndFix`), и сервер пишет только её параметры.

## Решение

* **Сервер — две узкие записи параметров примерки**, рядом с записями статуса хотелки (`…/wishlist-status`):
  * `PATCH /events/{id}/wishlist-params` — `plannedAmount` и необязательный `date`. Пишет сумму; срок — если прислан. Пересчитывает погашение плана, как правка (`resettlePlan`). Описание, исходный текст, категорию, характер, ссылку не трогает. Только хотелка — строка со статусом хотелки; иначе 404.
  * `PATCH /funds/{id}/wishlist-params` — `targetAmount`, необязательные `targetDate`, `creditRate`, `creditTermMonths`. Пишет цель; остальное — если прислано. Границы ставки и срока — те же, что у `TargetFundCreateDto`: от них считает `savable` диалог фиксации. Статус конверта пересчитывается по новой цели у копилки не на счёте — как правка (ANO-199). Счёт, имя, вид, приоритет не трогает. Только копилка-хотелка; иначе 404.
* **Сервер — правка плана перевода не снимает копилку.** `applyDto`: копилка не прислана, а строка остаётся переводом — остаётся прежняя. Прислана другая — пишется она. Строка перестала быть переводом — копилки нет, как было.
* **Экран — «Что с капиталом» пишет только параметры.** Что уходит — одна функция `trialParams(item, patch, explicitDate)` в `wishlistUtils.ts`; `persistTrial` зовёт новые записи, `updateEvent`/`updateFund` из блока уходят. Срок необязателен: у хотелки без срока пишется сумма.
* **Контракт `docs/specs/04-api-contract.yaml`:** две записи и правило копилки плана перевода.

Не касается. Запись параметров характер не трогает: хотелка остаётся «Хотелкой» (A6), план перевода — «Ожиданием».

## Как мерил

* **Стенд:** `GET /api/v1/version` → `4ba189b`; бандл в странице — `index-835b0435.js`, тот же, что отдаёт стенд. В `4ba189b` поверх `main` `1b8e340` — только A6: характер хотелки, этих путей он не касается.
* **Путь — экраном** в панели браузера: «Хотелки» → «Что с капиталом» (раздел «Отложено» → «Вернуть в обсуждение» для отложенной) → ползунок «Сумма» → «Зафиксировать» → «Зафиксировать без конверсии»; журнал → карточка ожиданий → «Записать факт» → «изменить ожидание» → «Сохранить», затем «Сохранить факт». Нажатия — `element.click()`, ползунок и поля — сеттер `value` и события `input`/`change`.
* **Тела запросов и ответы** — обёрткой `fetch` в странице.
* **Состояние** — `/funds`, `/events`, `/pocket`, `/wishlist/simulation`; карточка «Целей» — текстом страницы.
* **Пробы** заведены ручками экрана: план «В копилку» — как быстрый ввод (`POST /events`, «Ожидание»); хотелка без срока — `POST /events/wishlist`; хотелка без описания с исходным текстом — `POST /events` характера «Хотелка», затем `PATCH …/wishlist-status OPEN`, как хотелки из переноса V18. Все удалены; свободно −197 212 до и после.
* **«Первый взнос на ипотеку»** возвращён: привязка к «Эталону» — `PUT /funds/{id}` с `accountId`, затем статус «отложено». История привязок получила закрытую и новую строку с сегодняшней датой — капитал за прошлые даты от этого не меняется.

## Чего не делаем

* **Смысл `PUT` в целом** — вариант В владелец отверг: у копилки «счёт не прислан» значит «отвязать».
* **Примерка на «Хотелках»** (`applyAndFix`) — не меняется: у неё свой смысл суммы копилки — остаток, а не цель.
* **Уже сломанные записи.** Планы перевода без копилки — подсчёт: `SELECT count(*) FROM financial_events WHERE type = 'FUND_TRANSFER' AND event_kind = 'PLAN' AND target_fund_id IS NULL AND is_deleted = false`. Копилки, отвязанные фиксацией, от отвязанных нарочно не отличить: причина отвязки не хранится. Починка — отдельно, если подсчёт найдёт.

## Чего не ловит

* **Вкладка, открытая до выкладки:** старый бандл пишет через `PUT` — до перезагрузки страницы дефекты прежние. Правило копилки плана перевода — на сервере и работает сразу.
