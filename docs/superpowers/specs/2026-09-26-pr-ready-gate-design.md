* стоит в имени ветки;
* стоит в заголовке PR;
* идёт в описании после закрывающего слова: close, closes, closed, closing, fix, fixes, fixed, fixing, resolve, resolves, resolved, resolving, complete, completes, completed, completing, implement, implements, implemented, implementing.

После слов ref, references, part of, related to, contributes to, towards, updates задача связывается, но при вливании не закрывается. Номер в описании без таких слов не связывается вовсе.

## 2. Скрипт `tools/pr-ready.sh <N>`

Логика — в `tools/pr-ready.mjs`: Node без зависимостей, как остальные инструменты в `tools/`. Данные берёт через `gh`. `pr-ready.sh` — обёртка под имя, которое уже стоит в плане спринта и в ANO-194.

Печатает пять пунктов. Выход 0 — только если все пять чистые.

| пункт | что печатает | чисто, когда |
|---|---|---|
| CI | каждую проверку головы PR — по последнему прогону каждого имени | пришли проверки всех джоб каждого workflow, который запускается на `pull_request` в базе PR или в его merge-коммите; все прошли или пропущены; ни одной упавшей, отменённой или идущей |
| Codex | смотрит, молчит или вердикт — какой, когда и про какой коммит | смена головы записана; есть вердикт про коммит головы; 👀 нет |
| Замечания Codex | ветки обсуждения, где последнее слово за Codex: файл, строка, заголовок замечания | таких веток нет |
| База | базу PR и открытые PR, которые стоят на его ветке | база `main`, сверху никого |
| Linear | номера, которые Linear закроет при вливании, и номера, которые он только свяжет, — против строки «Закроет:» в описании | закроет ровно то, что объявлено |

**Вердикт Codex привязан к коммиту, а не ко времени.** Голова просмотрена, если есть вердикт про её коммит:

| вердикт | про какой коммит |
|---|---|
| ревью с заголовком «Codex Review» | свой коммит, `commit_id`. Ответ Codex в ветке GitHub заворачивает в ревью с пустым телом — это не вердикт |
| «Didn't find any major issues» | номер из строки «Reviewed commit»; не разобрался — не вердикт, а «прочитать» |
| 👍 на PR | голова на момент открытия PR: его Codex ставит при первом ревью, когда бы 👍 ни пришёл. Голова на открытии — только из прогона workflow «Ответы Codex» по `opened`: у workflow задан `run-name` с событием и действием, API отдаёт его как `display_title`, а сам workflow сверяется по пути файла. Заголовок прогона CI — название PR, и по одному заголовку его не отличить. Нет такого прогона — 👍 не к чему привязать, и он не вердикт |
| 👍 на запросе `@codex review` | не вердикт. К голове его надёжно не привязать: запрос может уйти раньше, чем записан прогон нового пуша. И Codex так не отвечает: на запрос — ревью или «замечаний нет», оба с номером коммита |

**Смотрит** — 👀 на PR или на последнем запросе `@codex review`.

**История голов** — прогоны workflow по событию `pull_request` на ветке PR — вместе с репозиторием головы, у PR из форков ветки называются одинаково, — после его открытия. Каждый несёт коммит головы на момент события, по ним видно, какая голова была в любой момент. Ветка, а не номер PR: GitHub считает список PR у прогона в момент запроса, и у влитого PR он пуст. Прогоны до открытия PR — прошлый PR с той же веткой, они не в счёт.

**При `--at`** голова — та, что была на тот момент по истории, а не нынешняя.

**Пока смена головы не записана — ворота закрыты.** Если последний прогон в истории не про нынешнюю голову — прогон по пушу ещё не пришёл, — вердикты к голове не привязать, и пункт красный: «смена головы не записана».

Сравнение времён — «вердикт после пуша» — было в первых редакциях и пять раз оказывалось дырой: раздел 10.

**Любой другой комментарий Codex в ленте — не вердикт.** Все такие комментарии в истории — «упёрся в лимит», ревью при них не было. Если он пришёл после последнего вердикта, пункт красный: «лимит — ревью не было», а любой другой текст — «прочитать». Засчитать его за вердикт значило бы пропускать непросмотренные PR — ровно то, против чего ворота. В лимите пункт остаётся красным, пока владелец не решит: `/code-review ultra` или вливание под его ответственность.

**Почему вердикт нужен про голову, а не какой-нибудь.** Правка по замечаниям — это код, которого ревьюер не видел. Единственный повторный запрос за спринт (#84) нашёл новое замечание. Правило «после пуша попросить `@codex review`» уже стоит в плане спринта, раздел 6; скрипт делает его проверкой. Цена — после каждого пуша около десяти минут ожидания.

**PR, открытые до `run-name`,** не имеют прогона по `opened` с нужным заголовком — 👍 на PR у них не к чему привязать, и скрипт просит `@codex review`. Для новых PR это не касается.

**Строка «Закроет:»** — в описании PR: `Закроет: ANO-100, ANO-101` или `Закроет: —`. Linear её не читает — слово не из его списка. Скрипт сравнивает её с тем, что Linear закроет на самом деле. Под этой проверкой #65 покраснел бы: объявлено ANO-100, а закрылись бы ANO-100 и ANO-76. HTML-комментарии шаблона при разборе выбрасываются. Строка без номеров и без «—» — например, неправленая `ANO-…` из шаблона — считается незаполненной.

**Режимы:**

* `--only codex-replies` — только пункт «Замечания Codex». Его гоняет джоба CI (раздел 3).
* `--at <время>` — пункты Codex на момент в прошлом: всё, что появилось позже, не учитывается. Нужен, чтобы проверить скрипт на истории — например, #53 на момент вливания. CI в этом режиме не проверяется: прошлых прогонов в нужном виде GitHub не хранит. Когда Codex ставил и снимал 👀, по истории тоже не видно, поэтому «смотрит» при `--at` не определяется.

## 3. Джоба «Codex — замечания отвечены»

Отдельный workflow `.github/workflows/codex-replies.yml`. Запускается на два события:

* `pull_request` — открытие и пуш;
* `pull_request_review` — ревью Codex и наш ответ: ответ в ветке тоже создаёт ревью.

**Почему без `pull_request_review_comment`.** Проверено на этом PR: на один комментарий в строке приходят оба события сразу. Прогон по `pull_request_review_comment` в проверках PR не встаёт. А пока в workflow была группа `concurrency` с отменой, она отменяла прогон по `pull_request_review`, и в проверках PR вставал отменённый — красный. Поэтому событие ревью оставлено одно, а группы с отменой нет: джоба идёт секунды. Удаление замечания событием ревью не считается — счёт обновится на следующем пуше или ответе.

**Две джобы, код PR — только с правами на чтение.** Джоба проверки выгружает код из ветки PR и запускает `tools/pr-ready.sh` с правами `contents: read` и `pull-requests: read`. Право `actions: write` есть только у джобы перезапуска (ниже), и кода PR в ней нет: только `gh` с постоянными аргументами. Иначе автор PR из этого же репозитория мог бы подменить скрипт и с правом на запись запускать чужие workflow, вплоть до публикации образов с `packages: write` (десятое ревью Codex). Сторож в `tools/pr-ready.test.mjs` краснеет, если `actions: write` окажется на уровне всего workflow или у джобы с `actions/checkout` или `tools/`.

**Модель угроз шага перезапуска.** Сам шаг лежит в YAML из ветки PR: для событий `pull_request_review` GitHub берёт workflow из merge-коммита PR. Автор PR из этого же репозитория может переписать шаг — но он и без того может запушить в свою ветку workflow на событие `push` с `permissions: actions: write`: в личном репозитории права токена задаёт сам workflow. Шаг не даёт ему ничего сверх права пуша. Автору из форка GitHub права на запись через `permissions` не выдаёт: «you can use the permissions key to add and remove read permissions for forked repositories, but typically you can't grant write access» (документация GitHub, синтаксис workflow). Если появятся соавторы без полного доверия или включат запись для PR из форков — перенести перезапуск в workflow на `workflow_run` из `main`: его определение из ветки PR не подменить.

**Красный прогон по пушу перезапускается.** Обычный ход: Codex оставил замечание, я пушу правку, потом отвечаю в ветке. Прогон по пушу красный, по ответу — зелёный, и в проверках PR стоят оба. Скрипт берёт последний, а страница PR показывала бы красный крестик на каждом таком PR. Поэтому зелёный прогон по событию ревью перезапускает красные прогоны этого workflow по пушу на той же голове. Они читают текущие ответы и зеленеют. Это отдельная джоба с правом `actions: write` и без кода PR.

Джоба гоняет `tools/pr-ready.sh <N> --only codex-replies` и краснеет, пока есть ветка, где последнее слово за Codex.

**Почему только этот пункт.** Остальные по событиям не посчитать. 👍 — реакция, а реакции workflow не запускают. Джоба, требующая вердикта, после 👍 осталась бы красной навсегда. Вердикт и остальное проверяет скрипт перед «ждёт ок».

**Почему без `issue_comment`.** Прогон по этому событию привязывается к последнему коммиту `main`, а не к голове PR, и в проверках PR не встаёт — это вопрос из плана спринта, раздел 3.0. По существу Codex в ленту не пишет — только о лимите, а лимит скрипт ловит сам.

**Почему отдельным файлом, а не джобой в `ci.yml`.** Группа `concurrency` в `ci.yml` задана по `github.ref`, а у событий ревью ref тот же — `refs/pull/N/merge`. Каждый ответ в ветке отменял бы идущую сборку бэка.

Сделать джобу обязательной в правилах ветки — настройка репозитория, решает владелец. Сейчас у `main` правил нет вовсе.

## 4. Шаблон PR

`.github/pull_request_template.md` — чек-лист цикла. PR несёт историю, а не список файлов:

* что было — замер, а не описание задачи;
* почему так;
* спека — путь; в ней есть раздел «Правила продукта — сверка»;
* тесты красные до правки;
* мутации на итоговом коде;
* стенд до и после;
* замечания Codex отвечены в ветках; после последнего пуша Codex смотрел голову;
* что правка не закрывает;
* строка «Закроет:».

В комментарии шаблона — как связать задачу без закрытия: `Part of ANO-N` в описании.

## 5. Чего ворота не ловят

* **Замечание в теле ревью, а не в строке кода.** Скрипт считает только ветки обсуждения. За 32 PR Codex так не писал ни разу.
* **Вопросы людей.** Владелец и я пишем с одного аккаунта GitHub, по имени вопрос от ответа не отличить. Считаются только ветки Codex. По той же причине скрипт не видит замечаний `/code-review` — они приходят от того же аккаунта.
* **Закрывающие слова в сообщениях коммитов** — не разбираются.
* **Качество ответа.** Ворота проверяют, что ответ есть, а не что он по существу. Правило «ответ — с доказательством на мутации» остаётся на мне.
* **Верность самой строки «Закроет:».** Она делает закрытие видимым и осознанным, но может ошибаться вместе с автором.
* **Имя джобы с выражением** — `name: Тесты ${{ matrix.os }}` — со своей проверкой не сопоставляется: имя проверки вычисляется при прогоне. Джобы с матрицей без выражения в имени сопоставляются по «имя (значения)». Сейчас ни матриц, ни выражений в именах джоб нет.
* **Состав матрицы.** Проверка «имя (значения)» засчитывает всю джобу, поэтому PR, убравший из матрицы ногу, пройдёт на оставшихся. Чтобы сверять состав, надо разбирать `strategy.matrix` с `include` и `exclude` — это не делается, пока матриц в CI нет.

## 6. Правила продукта — сверка

Правка — инструмент разработки: скрипт, workflow, шаблон PR. Экранов, расчёта и данных пользователя не касается.

| правило | как соблюдено |
|---|---|
| 1–4, запреты | не затрагиваются: ни бюджетов, ни отчётов план-факт, ни обещаний, ни пейволла |
| 5–9, требования | не затрагиваются: поведение продукта не меняется |
| 10–13, тексты на экране | не затрагиваются: тексты скрипта и шаблона видят разработчики, не пользователи. Сторож словаря `productRules.test.ts` читает фронт и сообщения бэка — `tools/` и `.github/` ему не нужны |
| характер плановой строки | не затрагивается |
| данные респондентов | не затрагиваются. В тестах — номера, логины и время из публичной истории PR этого репозитория, без текста замечаний |
