* стоит в имени ветки;
* стоит в заголовке PR;

## 2. Скрипт `tools/pr-ready.sh <N>`

Логика — в `tools/pr-ready.mjs`: Node без зависимостей, как остальные инструменты в `tools/`. Данные берёт через `gh`. `pr-ready.sh` — обёртка под имя, которое уже стоит в плане спринта и в ANO-194.

Печатает пять пунктов. Выход 0 — только если все пять чистые.

| пункт | что печатает | чисто, когда |
|---|---|---|
| CI | каждую проверку головы PR — по последнему прогону каждого имени | пришли проверки каждого workflow, который запускается на `pull_request` в merge-коммите PR; все прошли или пропущены; ни одной упавшей, отменённой или идущей |
| Codex | смотрит, молчит или вердикт — какой и когда | есть вердикт, вынесенный после пуша головы; 👀 нет |
| Замечания Codex | ветки обсуждения, где последнее слово за Codex: файл, строка, заголовок замечания | таких веток нет |
| База | базу PR и открытые PR, которые стоят на его ветке | база `main`, сверху никого |
| Linear | номера, которые Linear закроет при вливании, и номера, которые он только свяжет, — против строки «Закроет:» в описании | закроет ровно то, что объявлено |

**Вердикт Codex** — ревью, 👍 на PR, 👍 на запросе `@codex review`, комментарий «Didn't find any major issues». У ревью и у этого комментария есть номер просмотренного коммита, и голова считается просмотренной **только** по нему: ревью прошлой головы может прийти уже после пуша новой. По времени пуша сверяются лишь реакции — номера у них нет. **Смотрит** — 👀 на PR или на последнем запросе `@codex review`.

**Любой другой комментарий Codex в ленте — не вердикт.** Все такие комментарии в истории — «упёрся в лимит», ревью при них не было. Если он пришёл после последнего вердикта, пункт красный: «лимит — ревью не было», а любой другой текст — «прочитать». Засчитать его за вердикт значило бы пропускать непросмотренные PR — ровно то, против чего ворота. В лимите пункт остаётся красным, пока владелец не решит: `/code-review ultra` или вливание под его ответственность.

**Почему вердикт нужен после пуша головы, а не какой-нибудь.** Правка по замечаниям — это код, которого ревьюер не видел. Единственный повторный запрос за спринт (#84) нашёл новое замечание. Правило «после пуша попросить `@codex review`» уже стоит в плане спринта, раздел 6; скрипт делает его проверкой. Цена — после каждого пуша около десяти минут ожидания.

**Время пуша головы** — создание первого набора проверок на её коммит: набор создаёт сам пуш. Дата коммита не годится: коммит, сделанный до вердикта и запушенный после, выглядел бы уже просмотренным. Если наборов нет — берётся дата коммита, и скрипт говорит об этом.

**Строка «Закроет:»** — в описании PR: `Закроет: ANO-100, ANO-101` или `Закроет: —`. Linear её не читает — слово не из его списка. Скрипт сравнивает её с тем, что Linear закроет на самом деле. Под этой проверкой #65 покраснел бы: объявлено ANO-100, а закрылись бы ANO-100 и ANO-76. HTML-комментарии шаблона при разборе выбрасываются. Строка без номеров и без «—» — например, неправленая `ANO-…` из шаблона — считается незаполненной.

**Режимы:**

* `--only codex-replies` — только пункт «Замечания Codex». Его гоняет джоба CI (раздел 3).
* `--at <время>` — пункты Codex на момент в прошлом: всё, что появилось позже, не учитывается. Нужен, чтобы проверить скрипт на истории — например, #53 на момент вливания. CI в этом режиме не проверяется: прошлых прогонов в нужном виде GitHub не хранит. Когда Codex ставил и снимал 👀, по истории тоже не видно, поэтому «смотрит» при `--at` не определяется.

## 3. Джоба «Codex — замечания отвечены»

Отдельный workflow `.github/workflows/codex-replies.yml`. Запускается на два события:

* `pull_request` — открытие и пуш;
* `pull_request_review` — ревью Codex и наш ответ: ответ в ветке тоже создаёт ревью.

**Почему без `pull_request_review_comment`.** Проверено на этом PR: на один комментарий в строке приходят оба события сразу. Прогон по `pull_request_review_comment` в проверках PR не встаёт. А пока в workflow была группа `concurrency` с отменой, она отменяла прогон по `pull_request_review`, и в проверках PR вставал отменённый — красный. Поэтому событие ревью оставлено одно, а группы с отменой нет: джоба идёт секунды. Удаление замечания событием ревью не считается — счёт обновится на следующем пуше или ответе.

**Красный прогон по пушу перезапускается.** Обычный ход: Codex оставил замечание, я пушу правку, потом отвечаю в ветке. Прогон по пушу красный, по ответу — зелёный, и в проверках PR стоят оба. Скрипт берёт последний, а страница PR показывала бы красный крестик на каждом таком PR. Поэтому зелёный прогон по событию ревью перезапускает красные прогоны этого workflow по пушу на той же голове. Они читают текущие ответы и зеленеют. Для этого у джобы право `actions: write`.

Джоба гоняет `tools/pr-ready.sh <N> --only codex-replies` и краснеет, пока есть ветка, где последнее слово за Codex.

**Почему только этот пункт.** Остальные по событиям не посчитать. 👍 — реакция, а реакции workflow не запускают. Джоба, требующая вердикта, после 👍 осталась бы красной навсегда. Вердикт и остальное проверяет скрипт перед «ждёт ок».

**Почему без `issue_comment`.** Прогон по этому событию привязывается к последнему коммиту `main`, а не к голове PR, и в проверках PR не встаёт — это вопрос из плана спринта, раздел 3.0. По существу Codex в ленту не пишет — только о лимите, а лимит скрипт ловит сам.

**Почему отдельным файлом, а не джобой в `ci.yml`.** Группа `concurrency` в `ci.yml` задана по `github.ref`, а у событий ревью ref тот же — `refs/pull/N/merge`. Каждый ответ в ветке отменял бы идущую сборку бэка.

Сделать джобу обязательной в правилах ветки — настройка репозитория, решает владелец. Сейчас у `main` правил нет вовсе.

## 4. Шаблон PR

`.github/pull_request_template.md` — чек-лист цикла. PR несёт историю, а не список файлов:

* что было — замер, а не описание задачи;
* почему так;
* спека — путь; в ней есть раздел «Правила продукта — сверка»;
* тесты красные до правки;
* мутации на итоговом коде;
* стенд до и после;
* замечания Codex отвечены в ветках; после последнего пуша Codex смотрел голову;
* что правка не закрывает;
* строка «Закроет:».

В комментарии шаблона — как связать задачу без закрытия: `Part of ANO-N` в описании.

## 5. Чего ворота не ловят

* **Замечание в теле ревью, а не в строке кода.** Скрипт считает только ветки обсуждения. За 32 PR Codex так не писал ни разу.
* **Вопросы людей.** Владелец и я пишем с одного аккаунта GitHub, по имени вопрос от ответа не отличить. Считаются только ветки Codex. По той же причине скрипт не видит замечаний `/code-review` — они приходят от того же аккаунта.
* **Закрывающие слова в сообщениях коммитов** — не разбираются.
* **Качество ответа.** Ворота проверяют, что ответ есть, а не что он по существу. Правило «ответ — с доказательством на мутации» остаётся на мне.
* **Верность самой строки «Закроет:».** Она делает закрытие видимым и осознанным, но может ошибаться вместе с автором.

## 6. Правила продукта — сверка

Правка — инструмент разработки: скрипт, workflow, шаблон PR. Экранов, расчёта и данных пользователя не касается.

| правило | как соблюдено |
|---|---|
| 1–4, запреты | не затрагиваются: ни бюджетов, ни отчётов план-факт, ни обещаний, ни пейволла |
| 5–9, требования | не затрагиваются: поведение продукта не меняется |
| 10–13, тексты на экране | не затрагиваются: тексты скрипта и шаблона видят разработчики, не пользователи. Сторож словаря `productRules.test.ts` читает фронт и сообщения бэка — `tools/` и `.github/` ему не нужны |
| характер плановой строки | не затрагивается |
| данные респондентов | не затрагиваются. В тестах — номера, логины и время из публичной истории PR этого репозитория, без текста замечаний |

```bash
BOT='chatgpt-codex-connector[bot]'

  gh api repos/anotheron1/selfin/pulls/$n/comments --paginate --jq "[.[] | select(.user.login==\"$BOT\" and .in_reply_to_id==null) | .id] as \$roots | [.[] | select(.user.type!=\"Bot\" and .in_reply_to_id!=null) | .in_reply_to_id] as \$replied | \"bot-roots=\(\$roots|length) unanswered=\([\$roots[] | select(. as \$r | \$replied | index(\$r) | not)] | length)\""

  gh api repos/anotheron1/selfin/issues/$n/comments --jq "[.[] | select(.user.login==\"$BOT\")] | length"
  gh api repos/anotheron1/selfin/pulls/$n/reviews --jq "[.[] | select(.user.login==\"$BOT\")] | length"

```

```bash
gh api repos/anotheron1/selfin/pulls/$n/comments --paginate --jq "[.[] | select(.user.login==\"$BOT\" and .in_reply_to_id==null)] as \$roots | [.[] | select(.user.type!=\"Bot\" and .in_reply_to_id!=null)] as \$reps | \$roots[] | . as \$r | ([\$reps[] | select(.in_reply_to_id==\$r.id) | .created_at] | min) as \$first | \"\(\$r.id) \(\$r.created_at) \(\$first)\""
```

Проходы мутаций поймали три дыры в самой проверке:

* **Тест HTML-комментария проходил вхолостую.** В нём «Закроет:» стояла не в начале строки, и строка не находилась и без вырезания комментариев. Переписан на настоящий случай — многострочный комментарий, где «Закроет: —» стоит отдельной строкой, как в шаблоне.
* Место одной мутации встречалось в коде дважды — сужено.
* **Тест на настоящие файлы workflow краснел в каждой мутации** — не от подмены, а оттого, что в папке мутанта не было `.github/workflows`. Мутация «workflow без `pull_request` тоже ожидается» выглядела пойманной вхолостую. Обвязка исправлена, добавлен контрольный прогон без подмены.
* **Мутация «время пуша не учитывается» перестала применяться** — строку, которую она подменяла, переписала правка про «замечаний нет». Переведена на итоговый код.

**Ревью Codex на #86 — одно замечание, P1, подтвердилось.** Если основной workflow не запустился — например, из-за ошибки в самом файле, — в проверках PR одна зелёная джоба ответов Codex, и пункт CI был бы чистым без фронта, бэка, образа и миграций. Исправлено: скрипт читает `.github/workflows`, берёт workflow, которые запускаются на `pull_request`, и краснеет «не запускались: CI», если у какого-то нет ни одной проверки. Тесты — на сам случай и на разбор настоящих файлов; мутации 24–27.

**Первая редакция починки дала ложный красный на #85:** «не запускались: Ответы Codex». Файлы workflow читались из рабочей копии, где «Ответы Codex» уже есть, а в `main` и в ветке #85 его нет, и на #85 он не запускался. На PR GitHub гоняет workflow из merge-коммита PR. Теперь скрипт читает их оттуда — `refs/pull/N/merge` через API, а для влитого PR, где этой ссылки может не быть, — из головы. Проверено прогоном: #85 — «CI: прошли 4», #86 — ждёт обе.

**Повторное ревью Codex на `6d660ad` — ещё одно P1, подтвердилось.** Вердикт с номером коммита засчитывался и по времени. Если Codex начал смотреть прошлую голову, а его ревью пришло уже после пуша новой, номер не совпадает, а время проходит — скрипт засчитал бы ревью, которого у новой головы не было. В этом же PR так чуть не вышло: 👀 в 14:02, ревью в 14:05. Исправлено: вердикт с номером засчитывается только по номеру, по времени — только реакции. Тесты — на ревью и на «замечаний нет» про прошлый коммит, пришедшие после пуша; мутации 30–31.

**Сверх плана.**

* **Комментарий Codex в ленте — не вердикт.** Первая редакция спеки засчитывала его. Замер по #20–#50 показал 18 PR, где этим комментарием было «упёрся в лимит». Правило переписано до кода, тесты на него — «лимит» и «прочитать».
* **Heredoc в bash съел обратные слэши:** `'ANO-\\d+'` стало `'ANO-\d+'`, регулярки перестали находить номера. Семь тестов покраснели сразу. Это случай 12 ретро в новом виде: код и текст со слэшами и бэктиками пишутся инструментом записи файлов, а не строкой в bash. Регулярки из строк теперь собираются через `String.raw` — экранирование видно как есть.
* **Прогоны по событиям ревью в проверках PR — ответ на вопрос плана спринта (раздел 3.0).** Служебный комментарий в строке на этом PR дал два прогона на голову 3a64877: по `pull_request_review` и по `pull_request_review_comment`. Первый встал в проверки PR, второй — нет, хотя прошёл успешно. Группа `concurrency` отменила первый, и скрипт увидел в CI «упали: Codex — все замечания отвечены» — ложный красный. Исправлено до вливания: одно событие ревью, без отмены (раздел 3).
* **CRLF в обёртке проверен и не мешает.** Опасение было, что на Windows `pr-ready.sh` выгрузится с CRLF и символ возврата каретки попадёт в аргументы. Прогон копии с CRLF: Git Bash разобрал номер и флаги без ошибки. В CI файл берётся из индекса, там LF. Настройки окончаний строк не понадобились.
