## 2. Цель

**Продукт не теряет введённое, не выдумывает лишнего и не показывает неверных чисел — до того, как в нём появятся деньги четырёх человек.** Каждый PR проходит механические ворота, а не память.

Готово, когда:

* ворота ANO-194 работают на каждом PR;
* три задачи с паузы воспроизведены — починены или закрыты замером;
* правки блоков A и B и три из C — C5, C8, C11 — закрыты или перенесены с причиной и «ок» владельца. C1–C4, C6, C7, C9 — второй спринт вехи, раздел 7;
* так же — каждая задача, добавленная в веху по ходу спринта. Список с датами ведётся в одном месте — раздел 1: перечень здесь отставал от него уже дважды.

## 6. Как проверяется готовность задачи

Цикл прежний, этапы не пропускать (владелец 26.09):

разбор inline → спека со сверкой по каждому правилу канона → план → TDD → мутации на итоговом коде → стенд до и после → PR → ворота → «ждёт ок» → вливание → Linear с комментарием.

**План — раздел той же спеки, если шагов немного;** иначе — отдельный файл в `docs/superpowers/plans/`. Решение 23.09: ретро шага А, 9.5; план спринта 23.09, раздел 7. В раздел плана пишутся шаги, а не только список проверок.

Новое в этом спринте:

* **Ворота.** После ANO-194 «ждёт ок» и вливание — только при чистом `tools/pr-ready.sh <N>`. До неё — те же проверки руками, по списку ANO-194.
* **Codex** ставит 👀 при открытии PR, минут через десять — замечания или 👍. После пуша правок сам не смотрит: попросить комментарием `@codex review`. В ответах в ветках бота через @ не упоминать: на #86 он принял цитату за задачу и ответил в ветке «create an environment».
* **Кто вливает.** Вывод или решение — после «ок» владельца. Механическое — тесты, сторожа, документы без выводов — вливаю сам после CI и Codex.
* **Стенд** — пробой `GET /api/v1/version`, не памятью.
* **Тест — там, где дефект.** Правка трогает сохранение или расчёт на сервере — интеграционный тест на Testcontainers обязателен: юниты на моках не видят транзакций. Дефект только в интерфейсе — тест фронта на поведение: так в A5 (ANO-107 — по API переход уже работает, нет пути назад в интерфейсе) и в C8 (ANO-105 — обработчик ползунка). Правка на обеих сторонах — оба.
* **Правка в N местах — N тестов**, у каждого своя мутация.
* **Замер** — через продукт, не через SQL. Поиск — по значению, выдачу не обрезать. `grep -i` здесь не складывает регистр кириллицы.
* **Стопка PR** — перед вливанием нижнего перенацелить верхний на `main` и обновить ветку.
* **Метка «меняет-данные»** — на PR, где миграция намеренно меняет живые данные.

**Правила из локальной памяти, которых нет в разделе 6:**

* Вывод или продуктовое решение — сначала разбор с владельцем в чате, по вопросу за раз, потом PR. Задачу не закрывать, пока владелец не видел вывод.
* Вопрос владельцу — постановка задачи: одна тема в сообщении, что на экране, развилка таблицей, рекомендация. Коротко, простыми словами, по-русски, без эмодзи.
* Прежде чем спрашивать — прочитать спеки и связанные задачи в Linear: трижды «развилка» оказывалась уже решённой.
* Узкая проверка — не широкий вывод. Искать по значению (`Priority.HIGH`), а не по списку классов; корень числа — от экрана к формуле; выдачу не обрезать; «решения не было» — только после поиска по всем планам спринтов и ретро.
* Знать грань: основной путь работает — остановиться; на третьем-четвёртом убывающем круге ревью самому спросить «останавливаемся?».
* Объяснение, которое понадобилось в чате, — в справку «?» в интерфейсе, в той же задаче.
* Имена экранов — из навигации, `BottomNav.tsx`: «Хотелки», а не «Крупные решения».
* Linear: заводить с замером, закрывать с комментарием, находки — отдельными задачами сразу; поправленный замер — комментарием в исходную задачу.
* Макет владелец смотрит файлом, артефактом или снимком стенда.
* Мягкое удаление: в Java поле `deleted`, в схеме столбец `is_deleted` — SQL по `deleted` падает или молча считает удалённое живым.
* Агенты — только на проверку готового диффа; разбор и чтение — самому.
* Мутации скриптом: сначала та же команда на чистом коде — зелёная; «красно» засчитывается только с именем упавшего теста; ошибка компиляции — не «красно». 28.09 без этого набор бэка дважды «покраснел» вхолостую.
