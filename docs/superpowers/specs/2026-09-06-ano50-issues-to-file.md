Причина, почему они здесь, а не в Linear: 6 сентября коннектор Linear отвечал `connection invalidated` и на запись, и на чтение, включая попытки после переподключения. Сессия держит старое соединение.

Отдельно, не задача: **в ANO-25 нужен комментарий** — она жива, текст в конце документа.

## 1. Ползунок «когда» не может двигать график: пересчёт для него не вызывается

**Приоритет: высокий.** Блок 8.14, наблюдение владельца: «при двигании ползунка суммы график меняется, а при двигании ползунка "когда" — нет».

Подтверждено по коду, причина точная.

`WishlistItemCard` вызывает `onParamsRecompute` ровно в двух местах: строка 260 (ставка) и строка 275 (срок кредита). Для ползунка даты — **никогда**. Он делает только `onDateChange` и `persist()`.

А `effectiveDelta` в `CapitalWhatIf` умеет ровно два случая:

```ts
function effectiveDelta(item, override) {
    if (override?.delta != null) return override.delta;          // пересчитанная дельта
    if (override?.amount != null) return scaleDelta(item.delta, item.amount, override.amount);
    return item.delta;
}
```

`targetDate` в расчёт не входит вообще. Поэтому ползунок суммы двигает график мгновенно — через локальное масштабирование `scaleDelta`, — а ползунок даты не может сдвинуть его в принципе.

Это же объясняет третье замечание владельца из 8.2: отток стоит в месяце сохранённого срока хотелки, и «когда» его не двигает.

**Что тронуть.** `WishlistItemCard.tsx`, обработчик ползунка даты — вызывать `onParamsRecompute(buildRecomputeReq({}))` по `onMouseUp`, как это уже сделано для ставки и срока. Проверить, что `applyRecomputedDelta` кладёт результат в `overrideMap` и `effectiveDelta` его подхватывает.

## 2. Журнал показывает две неотличимые копии после конверсии хотелки

**Приоритет: высокий.** Блок 8.6, наблюдение владельца: «сейчас в журнале почему-то аж две копии этой транзакции».

Воспроизведено на стенде. После конверсии `GET /events` за дату отдаёт:

```
6643631d LOW PLAN PLANNED 180000 | Проверка двух копий
abcc2ef8 LOW PLAN PLANNED 180000 | Проверка двух копий
```

Одинаковые сумма, дата, приоритет, вид, статус и описание. Первая строка — исходная хотелка, помеченная сконвертированной; вторая — созданное событие.

**Различить их нельзя даже теоретически:** поля `wishlistStatus` в `FinancialEventDto` нет вовсе, `convertedToEventId` тоже не отдаётся. Фронту нечем отфильтровать одну из них.

Кармашек при этом считает трату один раз — исходная строка исключена из траектории по `allowedInTrajectory`. То есть **расчёт прав, врёт экран**.

**Что решить.** Либо журнал скрывает сконвертированные хотелки (для этого нужно отдать `wishlistStatus`/`convertedTo` в DTO), либо показывает их иначе — приглушённо, с пометкой «перенесено в план». Второе честнее: строка не исчезает бесследно.

## 3. «Отложить» — дорога в один конец, и хотелка остаётся на экране «Цели»

**Приоритет: высокий.** Блок 8.14, наблюдение владельца: «кнопка "отложить" вовсе убирает хотелку из всех списков, хотелка остаётся на экране "цели" и обратно её не вернуть».

Два дефекта в одном действии:

1. **Возврата нет.** Отклонённая хотелка уходит из примерки и из списка, и вернуть её в обсуждение из интерфейса нечем. По API переход `DISMISSED → OPEN` для несконвертированной хотелки работает — значит это дыра в интерфейсе, а не в модели.
2. **Экраны расходятся.** Из хотелок она исчезла, на «Целях» осталась. Один объект, два экрана, разные ответы — семейство ANO-89.

Смежно с ANO-103: там из `FIXED` нет выхода вообще из-за ограничения схемы. Здесь выход есть в API, но не выведен.

## 4. Две кнопки «зафиксировать» делают разное — ANO-38 жив в интерфейсе

**Приоритет: средний.** Блоки 8.4 и 8.14, наблюдение владельца.

Из списка хотелок: «нажал зафиксировать, ежемесячная сумма зафиксировалась, тумблер активировался и остался, график поменялся, **но кармашек остался и в план в журнале хотелка не добавилась**».

Из блока «что с капиталом»: «если отсюда нажать зафиксировать — хотелка переносится в план, огонь».

То есть одна и та же по названию кнопка в двух местах экрана делает разное: одна пишет только параметры (`artifactKind: EVENT_PARAMS`), другая доводит до конверсии в плановое событие.

По API оба пути дают одинаковое состояние — это проверено блоком 8.5, ANO-38 на уровне эндпоинтов не воспроизвёлся. Расхождение живёт в том, **какой эндпоинт зовёт каждая кнопка**.

Связать с ANO-38 и ANO-30 (фиксация неотличима от примерки).

## 5. Фиксация из списка не даёт видимого результата

**Приоритет: средний.** Блок 8.4.

Продолжение предыдущей задачи, но самостоятельное: после фиксации из списка кармашек не меняется, в журнале ничего не появляется. Владелец сам объяснил почему — «оно и не знает, на какую дату фиксировать», — и объяснение верное: без даты конверсия невозможна.

Но человек нажал кнопку с сильным словом «зафиксировать» и не получил ни результата, ни объяснения. Либо кнопка должна спрашивать дату, либо говорить, что именно она сделала.

## 6. График примерки подвисает при движении ползунка

**Приоритет: средний.** Блок 8.2, наблюдение владельца: «график прогружается с подвисанием — понятно, что он рендерится, но хотелось бы побыстрее».

Важно, что это не сеть: пересчёт суммы идёт локально через `scaleDelta`, без обращения к бэку. Значит узкое место — рендер.

Стоит померить честно: сколько точек в графике примерки, сколько раз он перерисовывается за одно движение ползунка, есть ли троттлинг. Отдельно от этого проверен дашборд — там всё быстро: `DOMContentLoaded` 125 мс, все пять запросов укладываются в 330 мс.

Материал этапа 11 «Объём и отзывчивость».

## 10. Потолок ползунка суммы ничем не объяснён

**Приоритет: низкий.** Блок 8.3, наблюдение владельца: «почему у хотелки с указанной суммой можно сдвинуть ползунок до одного ляма, непонятно. Да и вообще откуда лям».

## 12. Стратегия считает зафиксированную хотелку дважды

**Приоритет: высокий.** Блок 9.6, первый проход по API.

Текст целиком — в `2026-09-06-ano50-stage9-findings.md`, раздел «Расхождение 1». Коротко:

```
до создания хотелки            −712 868
хотелка создана, статус OPEN   −762 868    сдвиг −50 000
хотелка зафиксирована, FIXED   −812 868    сдвиг ещё −50 000
```

Хотелка на 50 000 съедает 100 000. Причина — допущение в комментарии `computeDeltaForFixedItems`: «WISHLIST LOW events contribute nothing to the baseline». Оно неверно, хотелка это обычное `PLAN/PLANNED` событие, и наложение ложится вторым слоем.

Вторая половина: хотелка в статусе «обсуждается» стратегию уже уменьшает, при том что кармашек её сознательно не считает. Продолжение ANO-89.

# Комментарий в ANO-25

Задача жива, проверено 6 сентября 2026 в блоке 9.9 плана ANO-50.

Два одинаковых факта по 4 400 в одну категорию и один день, записанных разными путями. Затем каждый снят, и замерено, на сколько просели отчёты:

```
                                        аналитика   стратегия
факт напрямую, POST /events/facts          −4 400      −4 400
факт через PATCH /events/{id}/fact         −4 400           0
```

В журнале оба факта видны и равноправны. В аналитике оба учтены одинаково. **В стратегию факт через PATCH не попадает вовсе.**

Способ записи определяет, попадёт ли трата в разбор длинного горизонта. Причина известна и записана как открытый вопрос в ANO-12: в разбор стратегии попадают только события с `eventKind = FACT`, а `factAmount`, проставленный на PLAN-строке, туда не доезжает.

Заодно снято соседнее подозрение: **ANO-47 не воспроизводится** — мультимесячная таблица сходится с журналом во всех проверенных клетках. Шесть расхождений, которые сначала показал прогон, оказались ошибкой инструмента: `new Date(y, m, 0)` плюс `toISOString()` в московской зоне теряют последний день месяца.
