## 1. Как работать

**Ветка.** Тестирование жило в `docs/ano50-testing-plan` — там только документы и `tools/`, продуктового кода она не трогает, кроме одной правки (V21, см. ниже). Починку разумно вести отдельными ветками от `main`.

**Стенд.** Тестовый, боевая база не участвует и не участвовала.

```bash
COMPOSE_PROJECT_NAME=selfin-test docker compose -f docker-compose.yml -f docker-compose.test.yml start
```

Фронт `http://localhost:5174`, API `http://localhost:8081`, БД `localhost:5433`. Контейнеры падают сами примерно раз в сутки — поднимать той же командой.

Рабочий слепок: `C:\Users\Kirill\selfin-backups\ano50-clean-stand-2026-09-06.sql`. Восстановить одной командой:

```bash
bash tools/ano50-reset-stand.sh C:/Users/Kirill/selfin-backups/ano50-clean-stand-2026-09-06.sql
```

Без аргумента тот же скрипт поднимает **пустую** базу — состояние нового пользователя.

**Проверка после каждой починки.** В `tools/` девять скриптов, все на Node без зависимостей. Главный:

```bash
node tools/ano50-invariants.mjs --json прогон.json --baseline прошлый.json
```

20 инвариантов по семи скоупам, только GET, ничего не меняет. Умеет сравнивать с прошлым прогоном — так в своё время нашлось, что V21 сдвигает минимум траектории.

Скрипты этапов (`ano50-stage5.mjs`, `stage8`, `stage9`, `stage10-tails`, `stage11`, `stage12-settings`) гоняют сценарии и убирают за собой. После починки любого дефекта прогнать тот этап, к которому он относится, — он проверит, что не сломалось соседнее.

**Грабли оснастки, стоившие времени:**

* `Idempotency-Key` на `POST /events` обязан быть UUID, иначе 500. На `POST /events/facts` — любая строка.
* `recurring.startDate` и `recurring.dayOfMonth` обязательны, хотя в DTO не помечены `@NotNull`.
* `DELETE /events/{id}?scope=ALL` на неповторяющемся событии даёт 400 — удалять без скоупа, с повтором через `scope=ALL`.
* `GET /funds` отдаёт объект `{funds: [...]}`, а не массив.
* **Стенд живёт в UTC, машина в MSK.** После 21:00 по Москве локальная дата уходит на сутки вперёд: ре-якорь падает с 400, факт создаётся за окном кармашка. Брать «сегодня» у сервера — это `trajectory[0].date` в ответе `/pocket`.
* Кириллица в `curl` из bash бьётся. Слать JSON через `node --eval` с `fetch`.

## 2. Порядок починки

Предлагаемый, не обязательный. Обоснование каждой группы — ниже.

### Группа 1. Продукт теряет и выдумывает деньги — 6 срочных

Это то, из-за чего нельзя показывать продукт людям. Все шесть про одно: **введённое пропадает или появляется само, и продукт об этом молчит.**

**Важное про эту группу.** Три из шести (ANO-91, ANO-103, ANO-125) живут в **схеме базы**, а не в коде: уникальный индекс V16 и check-ограничения V18. Поэтому `mvnw verify` при них зелёный и останется зелёным, если чинить только код. Каждую починку проверять на стенде, не тестами.

Ещё важнее: ANO-82 и ANO-125 — **одна причина**. Семантика «якорь содержит всё до себя» (ANO-15 §5) выбрасывает операции дня якоря из остатка, а другие подсистемы их считают. Чинить стоит вместе, одним решением, иначе поймаете третий вариант того же.

## 3. Что чинить не надо

> **ПОПРАВКА 11.09.2026.** Этот раздел проверен адверсариально при структуризации бэклога, и два его утверждения оказались неверными. Ниже они зачёркнуты по смыслу; подробности — в комментариях к самим задачам и в `2026-09-12-backlog-map.md` §3.
>
> **ANO-80 не починен.** Коммит `67fc923` живёт только на ветке `docs/ano50-testing-plan` — в main нет ни `V21__forecast_disabled_by_default.sql`, ни `ForecastDisabledByDefaultIT`. И сама миграция это лишь `UPDATE` данных: механизм `PredictionService` (темп = `факт / номер дня месяца`) не тронут, прогноз возвращается одним чекбоксом на экране категорий. Верная формулировка: **смягчено миграцией на ветке тестирования, механизм жив, в main правки нет.**
>
> **ANO-47 не «не воспроизвелось», а «не проверялось».** Блок 9.7 проверял `/analytics/multi-month`, который `calcStartBalance` / `effectiveNetSum` не вызывает вообще. Все три расхождения мостика живы. Строку про ANO-47 в таблице ниже читать как недействительную.
>
> **ANO-48 и ANO-49 сняты по API, но не разобраны до конца.** Из трёх описанных механизмов ANO-48 преемниками был покрыт один; недостающие заведены как ANO-138 и ANO-141. По ANO-49 основание «примерка в базу не пишет» неверно для интерфейса — заведено как ANO-139. Обе задачи переформулированы в приёмочные.

**Уже починено по ходу**, единственное осознанное исключение из правила: [ANO-80](https://linear.app/anotherspace1/issue/ANO-80/pervaya-trata-novogo-polzovatelya-obvalivaet-karmashek-v-shest-raz) — миграция `V21__forecast_disabled_by_default.sql` плюс `ForecastDisabledByDefaultIT`. Прогнано: 339 юнитов + 111 интеграционных, ноль падений.

**Не воспроизвелось — проверять заново не нужно:**

| | |
|---|---|
| ANO-48 | «хотелка не переводится в план» — путь по API отрабатывает целиком, задвоения нет |
| ANO-49 | «примерка работает не так» — все три примерки чистые, аннуитет сходится с формулой |
| ANO-46 | вклад в кассовый график не протекает |
| ANO-47 | мультимесячная таблица сходится с журналом |
| ANO-34 | фиксация переносит параметры |
| ANO-38 | на уровне эндпоинтов не воспроизводится (но живёт в интерфейсе — ANO-109) |

Разбор с числами записан комментариями в ANO-48, ANO-49 и ANO-25.

**Жива и подтверждена замером:** [ANO-25](https://linear.app/anotherspace1/issue/ANO-25) — факт через PATCH не попадает в разбор стратегии. Замер в комментарии.

**Невыполнимо по построению, зафиксировано:** блок 10.4 заблокирован ANO-82; блоки 3.14 и 3.15 упираются в ANO-83 (у события нет счёта); блок 4.10 невыразим — частоты только месячная и годовая; блок 12.2 упирается в ANO-121 (содержимое снимка не отдаёт ни одна ручка).

## 4. Что осталось непроверенным

Честный список — чтобы никто не думал, что покрыто всё.

**Не проверялось глазами:** свободные исследования экранов счетов (1.14), журнала (3.16), правил (4.11); слои и синхронное наведение на Стратегии (9.2, 9.5); калькулятор в поле суммы (3.7); длинная цепочка повторяющегося правила (4.9); обход экранов без перезагрузки страницы (часть 10.7).

**Проверено только по API, не глазами:** блок 5.18 (сценарий провала — числа сошлись, экран владелец видел раньше и остался доволен).

**Ограничение метода, о котором нельзя забывать.** Прогон по API воспроизводит ровно ту дыру, из-за которой заведён ANO-50: числовые дефекты он находит, а «не понял, куда нажать» — никогда. Больше того, один раз он выдал **ложное подтверждение**: на этапе 9 проверка искала в ответе поля вида `planFact`, не нашла и сообщила, что запрет 2 соблюдён. Поле называется `progressBars`, и запрет нарушен. Нашлось это только глазами, на мобильном проходе.
