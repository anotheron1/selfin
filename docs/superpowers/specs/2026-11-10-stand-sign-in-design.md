# Вход на стенде без Telegram

Шаг 1 этапа 0 «Опора» спринта 8 (`2026-11-10-sprint-8-plan.md`, раздел 6; решение владельца 13). Спека и план — одним документом. Задачи в Linear нет: до конца этапа 1 Linear не трогаем.

Зачем: владелец и тестировщик проходят путь нового человека с нуля на стенде. Сейчас руками на стенд можно войти только через Telegram, то есть только собой.

## Что есть сейчас

Замер 10.11 — код `main` (`6d369fb`), стенд `3e23174`.

* **Экран входа** (`SignIn.tsx`): галочка согласия и «Войти через Telegram». Кнопка шлёт согласие и ведёт на `/oauth2/authorization/keycloak?provider=telegram`; сервер превращает `provider` в `kc_idp_hint`, и Keycloak сразу уводит в Telegram, своей страницы не показывает.
* **Тот же адрес без `provider`** показывает страницу Keycloak с формой имени и пароля. Но сервер пускает на него только после галочки (`ConsentBeforeKeycloak`), а галочка — это `POST /api/v1/consent` с CSRF. Набрать адрес руками мало: без отметки сервер вернёт на экран входа. Путь есть только у скриптов (`tools/keycloak-check.mjs`).
* **Тестовый человек** в реалме стенда есть: людей двое, один — `tester`. Заводит его `tools/keycloak-token.mjs`.
* **Регистрации на странице Keycloak нет:** настройка реалма `registrationAllowed` — `false`, ссылки «Регистрация» на странице входа нет.
* **Новый человек с нуля** на стенде заводится только через Telegram или скриптом `tools/second-person.mjs` — руками, как настоящий новый человек, не пройти.

## Граница «стенд против сервера»

Главный вопрос шага: чем стенд отличается от сервера, чтобы включить вход на одном и не включить на другом.

| что | стенд | сервер |
|---|---|---|
| файлы compose | `docker-compose.yml` + `docker-compose.test.yml`, проект `selfin-test` | `deploy/docker-compose.yml`, проект `selfin-server` |
| образы бэка и фронта | собираются на машине из `backend/Dockerfile` и `frontend/Dockerfile` | те же `Dockerfile`, собирает `publish-images.yml` при вливании в `main`, сервер тянет из GHCR |
| аргументы сборки | один — `GIT_COMMIT` | один — `GIT_COMMIT` |
| бэкенд | профилей Spring нет; разница только в окружении: адреса Keycloak, секреты | то же |
| фронт | бандл без флагов окружения | тот же бандл |
| файл реалма | `keycloak/selfin-realm.json` | **тот же файл** (`deploy/docker-compose.yml`, том Keycloak) |
| когда файл реалма читается | только при первом старте Keycloak; дальше реалм живёт в базе Keycloak | так же |
| Keycloak | `start-dev`, `http://127.0.0.1:8180` | `start`, под `/auth` публичного адреса |
| тестовый человек и клиент скриптов | заводит `tools/keycloak-token.mjs` через Admin API | не заводятся: инструмент отказывает, если издатель реалма — не адрес этой машины (`ownIssuer`; ревью Codex на #171) |
| адрес экрана | `http://127.0.0.1:5174` | публичное имя |

Что из этого следует.

* **Файл реалма общий.** Постановка шага считала, что его подключает только стенд. Это не так: `deploy/docker-compose.yml` монтирует тот же файл. Включить регистрацию правкой файла — значит включить её серверу при следующем пересоздании реалма.
* **Сборка у стенда и сервера одна**, отличий в сборке фронта и в профиле бэка нет. Любой флаг пришлось бы заводить заново.
* **Одна граница уже есть и закрыта тестом — «адрес этой машины».** По ней инструменты решают, можно ли заводить тестового человека (`ownIssuer`: `127.0.0.1`, `localhost`, `[::1]`), по ней же сторож реалма различает адреса стенда и сервера. У сервера адрес — его имя, и настройкой это не изменить.

## Решение

### 1. Кнопка «Войти без Telegram» — только с адреса этой машины

* На экране входа под неактивными «Яндекс ID» и «VK ID» — кнопка **«Войти без Telegram»** и подпись **«Только на стенде: тестовый человек или регистрация нового.»**
* Экран показывает их, только когда открыт с адреса этой машины: `127.0.0.1`, `localhost`, `[::1]` — тот же список, что у `ownIssuer`. Признак — `isOwnMachine` в `frontend/src/lib/stand.ts`.
* Кнопка работает как «Войти через Telegram»: без галочки неактивна, по нажатию шлёт согласие и только потом уходит. Адрес — `/oauth2/authorization/keycloak` без `provider`: Keycloak показывает свою страницу.
* На странице Keycloak: форма имени и пароля — ею входит тестовый человек (`TESTER` в `tools/keycloak-token.mjs`), кнопка Telegram и ссылка «Регистрация».

На сервере кнопки нет при любой сборке и любой настройке: его экран открыт с публичного имени.

### 2. Регистрация — настройка реалма, которую включает инструмент стенда

* `tools/keycloak-token.mjs` уже заводит в своём Keycloak то, чего нет в файле реалма и не должно быть на сервере. К тестовому человеку и клиенту скриптов добавляется третье: `registrationAllowed: true`.
* Правка — одним полем: `PUT /admin/realms/selfin` с телом `{"registrationAllowed": true}`. Остальные настройки реалма не меняются — замер ниже. Весь файл реалма не отправляем: реалм стенда давно правился через Admin API и с файлом расходится.
* Защита та же, что у тестового человека: инструмент сначала читает издателя реалма и отказывает, если это не адрес этой машины.
* Файл реалма не меняется. Сторож требует, чтобы регистрации и людей в нём не было.

Включается одной командой — `node tools/keycloak-token.mjs`; её же зовут `keycloak-check` и скрипты стенда, так что на стенде регистрация появляется вместе с тестовым человеком.

### 3. Путь нового человека на стенде

Экран входа → галочка → «Войти без Telegram» → страница Keycloak → «Регистрация» → имя, пароль, подтверждение пароля (почта, имя и фамилия необязательны) → Keycloak возвращает на наш сервер → сервер заводит человека с отметкой согласия и стартовым набором → главный экран.

Наш код на этом пути — тот же, что у настоящего нового человека: галочка, `POST /api/v1/consent`, адрес входа, возврат из Keycloak, `Registration`. Отличается один шаг — как человек называет себя Keycloak: форма регистрации вместо подтверждения в Telegram.

Сменить человека — «Выйти» в «Настройках»: выход гасит и сеанс Keycloak. Пока сеанс Keycloak жив, вход впускает прежнего человека без страницы — как на сервере (вход держится 30 дней).

### 4. Бэкенд не меняется

Адрес входа без `provider` и возврат из Keycloak уже работают: ими ходит живая проверка. Новых адресов, флагов и профилей нет.

### 5. Что отвергнуто

| вариант | почему нет |
|---|---|
| флаг сборки фронта, включённый в `docker-compose.test.yml` | появляется выключатель, который можно включить и в серверной сборке; адрес сервера включить нельзя. Заодно — правки `Dockerfile`, compose и сторожа на `publish-images.yml` |
| флаг окружения бэка и ручка «какие входы доступны» | новый открытый адрес и правка `SecurityConfig` ради одной ссылки; выключатель на самом сервере |
| `registrationAllowed` в файле реалма | файл общий с сервером |
| подстановка `${…:false}` в файле реалма | выключатель в серверной настройке; работающий реалм стенда её всё равно не прочтёт — файл читается один раз |
| отдельный контейнер настройки в compose стенда | ещё одна деталь стенда ради одного запроса; инструмент уже есть и уже защищён |
| вход одним нажатием, без страницы Keycloak | серверу понадобился бы вход по паролю в обход Keycloak — это и есть чёрный ход |

## Не входит

* **Вход по паролю и регистрация на сервере.** Там вход только через Telegram: решение 11.10 и 406-ФЗ; смена входа — перед публичным запуском.
* **Стенд по сети или через туннель.** С чужого адреса кнопки не будет. Понадобится показать стенд человеку снаружи — отдельное решение: вместе с кнопкой наружу ушли бы открытая регистрация и пароль тестового человека из репозитория.
* **Страница Keycloak всегда, даже при живом сеансе** (`prompt=login`) — правка сервера; хватает «Выйти».
* **Вид страницы Keycloak:** тема, перевод «or Sign in with Telegram».
* **Уборка людей, заведённых на стенде,** — как раньше, `tools/delete-person.mjs`.
