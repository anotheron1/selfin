# Изоляция как инвариант: тест на двух людей по всем ручкам (ANO-148)

Шаг 6 спринта 5 (`2026-10-11-sprint-5-plan.md`, раздел 3). Спека и план — одним документом. Факультатив — блок 7, вне git.

Задача — тест, который заводит двух людей с пересекающимися данными и проверяет, что **ни одна ручка API не отдаёт и не меняет чужое**. Людей различает сервер — путём из шага 4, а не подменой владельца в тесте. Мутации обязательны: убрать политику или фильтр — тест краснеет.

## Что есть сейчас

* **Ограничитель** (#151, `V32`): RLS на 11 таблицах, приложение — ролью `selfin_app`, владелец — на каждой выдаче соединения из пула (`OwnerFilter` → `OwnerContext`).
* **`RowLevelSecurityIT`** проверяет механизм: политики на каждой таблице с `user_id`, роль пула, второй человек и категории — одна ручка из 64.
* **Ручек 64** в 14 контроллерах: 63 из плана и `/api/v1/me` из #149. Из них 30 — с id в пути, 22 чтения без id, 2 расчёта `POST` без записи (примерка и пересчёт хотелки), 10 записей без id в пути — заводят строки и настройки.
* **Ссылки в теле запроса** читаются через RLS: `categoryId` события и факта, `purposeCategoryId` счёта, `accountId` отметки остатка и копилки — `findById`, чужое — 404. **Вслепую пишется одна** — `targetFundId` перевода в копилку (`FinancialEventService`, ветка `FUND_TRANSFER`): проверка внешнего ключа RLS обходит. Это шаг 8, ANO-147.
* **Чтения пишут.** `extendIndefiniteRules` достраивает бессрочные повторы на `GET /pocket` и `GET /funds/planner` — своей транзакцией, владельцем запроса.
* **IT с чисткой таблиц** — 28 классов: `deleteAll()` репозиториев (ролью приложения — только строки синтетического владельца) или `DELETE FROM` ролью владельца таблиц (всё). Изоляцию они не держат и не проверяют: в них один человек.

## Решение

### Два человека с пересекающимися данными

`TwoPeopleIsolationIT`. Кроме синтетического владельца со стартовыми строками `V2` и `V20` — два новых человека, `first-person` и `second-person`. Каждый входит своим `sub` (`oidcLogin`, как браузер после входа); владельца находит `OwnerFilter`, строку `users` заводит `OwnerService` при первом запросе.

Оба заводят одно и то же **через API**: категории «Продукты» и «Зарплата», счёт «Карта» по умолчанию, отметку остатка, капитал с переоценкой, план, доход, повторяющийся план, факт к плану, факт без плана, хотелку, копилку с переводом, копилку на счёте, кредит-хотелку и её фиксацию, копилку, потраченную на цель, обе настройки. Так данные есть во всех 11 таблицах. Пересекаются имена, даты, виды строк и **ключи идемпотентности** — замки схемы по владельцу (ANO-146) обязаны пропустить второго, а повтор чужого ключа — не вернуть чужую запись. Суммы у второго вдвое больше: чужая строка в итогах меняет число.

**Системные категории** — «Хотелки», «Переводы в копилки», «Кредит», «Цели» — заводятся у каждого своими: помощник ищет их по имени, и ANO-150 опасается, что человек получит чужую. Тест требует все четыре у обоих, а чужую в ответе выдало бы правило 1.

### Оракул — один на все ручки

Ожиданий по каждой ручке нет — три правила на всех:

1. **Ни в одном ответе человеку нет чужого id.** Чужие — id всех строк других владельцев во всех таблицах с `user_id` и чужие строки `users`; берутся из базы ролью владельца таблиц. Проверяются ответы на записи и на чтения.
2. **Чтения первого не меняются** от того, что второй завёл те же данные и бил по его id. Так видна чужая сумма в итогах, где id нет. Сравнение — JSON без лишних полей, порядок в массивах не важен. Второй сверяется так же — до и после ударов первого.
3. **Запись и чтение по чужому id — 404:** чужого не существует. Исключение — история переоценок: на неизвестный предмет ручка отвечает пустым списком, и на чужой — так же.

Перед первым снимком — прогон чтений вхолостую: они достраивают повторы, и снимок до достройки отличался бы от снимка после.

Направление проверки сумм — одно: первый снят, когда второго ещё нет, а второй — уже при первом. Механизм утечки симметричен — тот же запрос без фильтра, — а утечку строкой ловит правило 1 в обе стороны.

### Сторож полноты

Тест записывает шаблон каждой вызванной ручки (`BEST_MATCHING_PATTERN_ATTRIBUTE`) по роли вызова и сверяет с картой Spring (`RequestMappingHandlerMapping`):

* ручка с id в пути — обязана получить удар чужим id;
* `GET` без id — обязана быть в чтениях;
* запись без id — вызвана хоть раз.

Новая ручка без проверки изоляции тест краснит. Пустая карта — тоже: сторож не холостой.

### IT с чисткой таблиц — пересмотр

Не трогаем. Их предмет — деньги одного человека; `deleteAll()` в них — чистый лист, а не изоляция. Изоляцию держит RLS, а проверяет этот тест: в нём база не пуста, людей трое, данные пересекаются. Опасение задачи — «тест с одним человеком в пустой базе не заметит отсутствия фильтра» — было о фильтре в каждом запросе, до решения ANO-144.

### Людей различает сервер

Оба человека — браузерной цепочкой. Скриптовая (Bearer) приходит к тому же `OwnerFilter` и `OwnerService.current()`; что Bearer даёт владельца по `sub`, проверяет `SignInIT` настоящими токенами.

## Не входит

* **Ссылки по владельцу в теле запроса** — шаг 8, ANO-147: составной внешний ключ или проверка при записи; там же тест дополняется записью с id другого человека — по плану спринта.
* **Явный фильтр по владельцу в запросах** — ANO-147. Пока RLS включён, этот тест пропуска явного фильтра не видит: база отфильтрует сама. Проверить второй слой отдельно — забота ANO-147, например тем же тестом с пулом в обход RLS.
* **Стартовый набор новому человеку** — ANO-151: здесь каждый заводит своё сам.

## Как проверяется

| что | проверка | мутация |
|---|---|---|
| чужой строки нет в ответах | правило 1, по каждой ручке | RLS выключен на одной таблице — по каждой из 11 |
| чужая сумма не входит в итоги | правило 2 | то же |
| по чужому id — 404 | правило 3 | политики открыты на всех таблицах: `USING (true) WITH CHECK (true)` |
| сервер различает людей | весь тест | `OwnerService.resolve` отдаёт второму владельца первого |
| владелец запроса ставится | весь тест | `OwnerFilter` не ставит владельца |
| ни одна ручка не забыта | сторож полноты | удар по одной ручке убран |

## Найдено по ходу

* **Ключи идемпотентности сработали дважды.** Без RLS на `financial_events` и `fund_transactions` повтор чужого ключа находил чужую запись — сценарий падал при заведении данных. Общие ключи у двух людей — не украшение, а проверка.
* **Моё первое объяснение мутации `balance_checkpoints` было неверным.** Решил, что удачный удар удаляет чужую отметку и её id выпадает из списка чужих, — и стал снимать список и до ударов. Повторный прогон показал: чтением чужие отметки не видны вовсе, их прячет соединение со счётом. Снимок до ударов оставлен страховкой — удар на сломанном коде может удалить строку, видную в чтении.
* **Защита `recurring_rule` от достройки — случайная:** чужое правило не достраивается только потому, что его дни уже есть. Под рабочим RLS запрос видит только свои правила; без него помешала бы только уникальность.
* **Чтения пишут** — `extendIndefiniteRules` на `GET /pocket` и `/funds/planner`; отсюда прогон вхолостую перед снимком.
* **Индекс работает без явного фильтра** — замер на стенде ролью `selfin_app`, перебор таблицы выключен: условие политики база кладёт в индекс `idx_financial_events_owner_date` вместе с диапазоном дат. Довод к объёму шага 8.
