## Три вещи, которые надо знать до первого блока

### 1. Прогноз незапланированных экстраполируется за текущий месяц

Это же расхождение независимо назвали **четыре зоны из семи** — самый надёжный результат прогона.

§3.5 говорит «за пределами текущего месяца прогноз не экстраполируется». Код (ANO-36) считает прогноз
на **каждый** будущий месяц горизонта: по категориям с историей ≥3 месяцев берётся медиана за 6 месяцев,
вычитается план месяца, остаток размазывается по дням. Видно на стенде живьём:

```
до дохода       −37 161 ₽
3 мес           −37 161 ₽
12 мес       −1 028 583 ₽
36 мес       −3 978 303 ₽
```

Считать ожидаемый кармашек на длинном скоупе как «остаток − плановые расходы» нельзя: разойдётся
на десятки тысяч, и это не баг.

### 2. Отклонение 5.4 получило точный адрес — и план надо поправить

`PocketEngine.java:326-338`, `spreadEvenly` раскладывает **весь** месячный прогноз по окну
`[asOfDate+1 .. min(конец месяца, конец горизонта)]`. Сумма не пропорционируется длине окна.
Значит короткий горизонт вычитает тот же прогноз за меньшее число дней, и на одну и ту же дату
короткий скоуп даёт баланс **ниже** длинного. Это следствие правила спеки, а не ошибка.

Две поправки к блоку 5.4 плана:

* снимать **две** даты — одну внутри текущего месяца, одну в следующем: механизмы там разные;
* скоупа «12 месяцев» в интерфейсе нет. Пилюли только «До дохода», «2-й доход», «3 мес», «6 мес»
  (`PocketCard.tsx:11-16`). MONTHS:12 достаётся лишь запросом `GET /api/v1/pocket?scope=MONTHS:12`.

### 3. «Последний якорь» — это якорь дефолтного счёта

§3.4 (врезка ANO-28) обещает «строго после последнего якоря». В коде
(`PocketInputAssembler.java:144-146`) берётся чекпоинт **дефолтного** счёта с датой ≤ сегодня.
Ре-якорь любого другого счёта окно просрочки не двигает, а если у дефолтного счёта чекпоинта нет —
нижней границы фактически нет (EPOCH = 2000-01-01) и резервируется вся историческая просрочка.

Это прямо влияет на этап 2 «Якорь и остаток»: блоки 2.2 и 2.5 иначе прочитаются как регрессия ANO-28.

## Подозрения на код — проверить руками, не править спеку

Таких 11. Это не подтверждённые баги: спека и код расходятся, и по смыслу правой выглядит спека.
Каждое воспроизводится руками в своём блоке этапа — до тех пор это гипотеза.

### К1. Факт с датой позже asOfDate не учитывается нигде — обещание «вклад уже учтён FACT-ребёнком» не выполняется

*Зона: Кармашек §3.1–§3.3 — вход, эффективная сумма, алгоритм*

**Спека** — docs/superpowers/specs/2026-07-02-pocket-core-design.md:54

> - `PLAN(EXECUTED)` без factAmount → **пропуск** (вклад уже учтён FACT-ребёнком).

**Код** — backend/src/main/java/ru/selfin/backend/service/PocketEngine.java:63 и 202-205

```java

...

    return e.factAmount() == null
            && e.eventKind() == EventKind.PLAN && e.status() == EventStatus.PLANNED;
```

**Чем грозит.** Родительский PLAN после записи факта становится EXECUTED и выпадает из траектории (isPendingPlan), а сам факт с датой > asOfDate не попадает в баланс (отсечка по asOfDate). Итог: расход исчезает из расчёта целиком, кармашек РАСТЁТ на plannedAmount. Сценарий достижим из UI: FAB «плановая транзакция» с будущей датой и сразу заполненной фактической суммой создаёт FACT с date = form.date (frontend/src/components/Fab.tsx:101-107), а в FactCreateSheet поле даты редактируемое (frontend/src/components/FactCreateSheet.tsx:77-78). Тестировщик, сверившись со спекой, поверит «вклад уже учтён» и пропустит настоящий баг. Юнит-тестов на факт с будущей датой в backend/src/test/java/ru/selfin/backend/service/PocketEngineTest.java нет.

**Что делать.** Руками: создать событие будущей датой с заполненным фактом (или добавить факт к будущему плану датой этого плана) и сравнить кармашек до/после — по коду он вырастет на сумму плана. Записать как кандидата в баги ANO-50; чинить в этой сессии не нужно.
