# Ограничитель изоляции: RLS в Postgres и своя роль приложения (ANO-144)

Шаг 5 спринта 5 (`2026-10-11-sprint-5-plan.md`, раздел 3). Спека и план — одним документом. Факультатив — блок 7, вне git.

Задача — поставить слой, при котором забытый фильтр по владельцу **падает, а не отдаёт чужое**, до того как тронут хоть один запрос (шаг 8, ANO-147). Рекомендация задачи и плана — row-level security в Postgres: ловит и `nativeQuery` (`CapitalRevaluationRepository.snapshotAt`), и любой будущий обход JPA. Hibernate-фильтр `nativeQuery` не покрывает.

## Что есть сейчас

* **Владелец в данных** (`V31`): `user_id` в 11 таблицах, значение по умолчанию — синтетический владелец. **Владелец запроса** (`OwnerService.current()`, #149): `sub` Keycloak → строка `users`.
* **Приложение ходит в базу пользователем `admin`** (`application.properties`, оба compose, `ci-migrations.sh`). Образ Postgres заводит его суперпользователем, а суперпользователь обходит RLS всегда: политики были бы, а защиты — нет.
* **IT ходят суперпользователем `test`** контейнера: тест изоляции был бы зелёным вхолостую.
* **Ленивые связи** — 7 `@ManyToOne(fetch = LAZY)`; `open-in-view` не выключен, то есть включён. Ленивая загрузка после транзакции идёт на соединении вне транзакции.
* **IT готовят данные и правят схему «сырым» SQL:** `JdbcTemplate` — в 27 классах, миграционные IT исполняют файлы миграций им же; `OwnerInDataLegacyNamesIT` поднимает схему только до `V30`.

## Решение

### Политики

* **На каждой из 11 таблиц** — `ENABLE ROW LEVEL SECURITY` и политика `owner_rows`: `USING` и `WITH CHECK` — `user_id = current_owner()`. Чтение видит только строки владельца, запись не может положить строку чужому.
* **`current_owner()`** — SQL-функция в базе: владелец из переменной сеанса `selfin.user_id`, пустая строка — `NULL`. Нет владельца — нет строк: `NULL` ни с чем не совпадает. Запрос без владельца получает пустоту, запись — отказ. Это и есть «пропуск падает»: забытый фильтр не отдаст чужое.
* `users` без RLS: в ней сервер ищет владельца, ещё не зная его. `budget_snapshots` — ничья и не используется: ни политики, ни доступа у роли приложения.
* `FORCE ROW LEVEL SECURITY` не ставим: владелец таблиц — роль миграций — должен видеть всё. С `FORCE` будущая миграция данных молча не нашла бы ни одной строки.

### Роль приложения

* **`selfin_app`** — `LOGIN`, не суперпользователь, без `BYPASSRLS`, не владелец таблиц; права — `SELECT, INSERT, UPDATE, DELETE` на 11 таблиц и `users`. Новым таблицам права дают `ALTER DEFAULT PRIVILEGES`, а политику — нет: её требует сторож (ниже).
* **Миграции — прежней ролью** (`spring.datasource.*`, она же владелец таблиц), **приложение — `selfin_app`**. Пароль роли — `selfin-app-dev` в миграции и в `selfin.db.app-password`; на сервере — свой (ANO-197): `ALTER ROLE` и переменная окружения.
* **Подвох Boot 4, проверен по байткоду:** `JdbcConnectionDetailsBeanPostProcessor` (порядок +2) ставит пулу пользователя из connection details после привязки свойств (+1), если детали — не из свойств, то есть у контейнеров тестов. `spring.datasource.hikari.username` там тихо проиграл бы, и IT остались бы суперпользователем. Поэтому роль ставит свой пост-процессор, после всех Boot. Flyway — свой источник данных из тех же connection details (`@FlywayDataSource`, не кандидат по умолчанию): ему нужна роль владельца, а не `selfin_app`.

### Владелец — на каждое соединение

* **Сервер ставит `selfin.user_id` на каждое соединение, которое выдаёт пул:** владельца запроса, без него — пустую строку. Каждая выдача перезаписывает прежнее значение, поэтому соединение из пула не унесёт чужого владельца в следующий запрос — опасение плана снято.
* **Почему не на транзакцию, как предлагал план:** заметная часть кода ходит в базу вне транзакции. Объявленные методы репозиториев Spring Data без транзакции по умолчанию; чтения в сервисах — без `@Transactional`; ленивые загрузки после транзакции — 7 связей, `open-in-view`. Владелец «на транзакцию» туда не дошёл бы, и RLS вернул бы пустоту. На выдаче соединения покрыто всё, включая `JdbcTemplate`. Проверено вариантом плана — мутация M7 в «Выполнено».
* **Владелец запроса** — `OwnerContext`, на поток. Его ставит фильтр после авторизации в обеих цепочках, из `OwnerService.current()`, и снимает в конце запроса. `/api/v1/me` отдаёт его же.

### Значение по умолчанию у `user_id`

`COALESCE(current_owner(), синтетический)` — переход до шага 8 из плана, теперь безопасный:

* роль приложения без владельца получит синтетического — и `WITH CHECK` отвергнет запись: строка не своя;
* роль владельца таблиц — миграции, исправления руками, подготовка данных в IT — RLS обходит, без владельца пишет синтетическому, как до сих пор.

Снимается в шаге 8, когда владельца ставит сама запись.

### Тесты

* **Приложение в IT — `selfin_app`, как в проде**: так 300 IT проверяют, что ни одна ручка не ходит в базу без владельца.
* **Данные IT готовят ролью владельца таблиц**: `JdbcTemplate` тестов — на источнике данных Flyway. Миграционные IT исполняют DDL — нужна роль владельца.
* **Поток теста — от имени синтетического владельца:** слушатель контекста ставит `OwnerContext` перед каждым тестом. Пользователь `MockMvc` по умолчанию (`user`, #149) связан с ним же — `selfin.owner-sub=user` для тестов. IT видят те же данные, что видели.
* `OwnerInDataLegacyNamesIT` поднимает схему до `V30`, где роли ещё нет: приложение в нём — пользователем контейнера.

### Новый человек — пустое приложение

До шага 10 (ANO-151, стартовый набор) у нового человека нет ни категорий, ни счёта: сиды `V2` и `V20` — синтетического владельца. План это предвидел. Тестировщики приходят с «Выкладкой» — промежуток однопользовательский.

### Стенд

Кто хозяин копии данных на стенде — ждёт решения владельца (вопрос 14.10): тестовый человек, учётная запись владельца с паролем на стенде или как сейчас. Коду ограничителя это не мешает — только замеру «владелец видит своё».

## Не входит

* **Явный фильтр по владельцу в запросах** и проверка ссылок на чужие строки — шаг 8 (ANO-147). Проверки внешних ключей RLS обходят: событие можно привязать к чужой копилке по её id.
* **Тест на двух людей по всем 63 ручкам** — шаг 6 (ANO-148). Здесь — сторож схемы и проверки механизма на нескольких ручках.
* **Стартовый набор новому человеку** — ANO-151.
* **Пароль роли и роль миграций на сервере**, миграции отдельной задачей без прав владельца у работающего приложения — «Выкладка» (ANO-197).

## Как проверяется

| что | проверка | мутация |
|---|---|---|
| у каждой таблицы с `user_id` — RLS и политика | IT, по `pg_class` и `pg_policies` | одна таблица без политики |
| пул приложения — `selfin_app`: не суперпользователь, не владелец таблиц | IT, `current_user` через пул | пост-процессор роли не применяется |
| второй человек не видит строк первого и пишет своё | IT через `MockMvc`, людей различает сервер | политика без `USING` |
| писать чужому нельзя | IT, `INSERT` чужого `user_id` через пул | политика без `WITH CHECK` |
| соединение без владельца — пусто, запись — отказ | IT, пул вне запроса | — |
| пул не уносит владельца прошлого запроса | IT: запрос второго человека, затем пул без владельца | выдача соединения не очищает владельца |
| запрос ставит владельца | весь набор IT — от имени вошедшего | фильтр не ставит `OwnerContext` |
| 300 IT денег проходят ролью приложения | полный прогон | — |
| стенд: числа те же, второй человек пуст | замер через экран | — |

## Найдено по ходу

* **Вариант плана «владелец на транзакцию» ломает продукт** (M7). Поиск удалённой категории «Хотелки» идёт вне транзакции, не находит её, и вставка новой падает на `uq_categories_owner_name`; `Optional.get()` на пустом ответе репозитория — `AccountControllerIT`; сиды `V2` не видны — `ForecastDisabledByDefaultIT`. Причина — запросы вне транзакции, а не только ленивые загрузки. Поэтому владелец — на выдаче соединения.

* **`OwnerInDataLegacyNamesIT` откатывал «сырой» SQL транзакцией JPA.** С ANO-144 `JdbcTemplate` тестов — на источнике данных Flyway, мимо пула приложения, и транзакция JPA его соединение не охватывала: индекс первого теста не откатился, и второй увидел замок. Транзакция теперь — на источнике данных самого `JdbcTemplate`. Других IT, где «сырой» SQL полагается на откат транзакцией, нет: у `StrategyFromCoreIT` в транзакции — JPA.
* **Отказ политики Spring называет `BadSqlGrammarException`**: Postgres отвечает кодом 42501, «недостаточно прав». Текст «violates row-level security policy» — в корневой причине.
