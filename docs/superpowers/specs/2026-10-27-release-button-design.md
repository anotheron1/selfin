# ANO-246: выкатка на сервер кнопкой — сервер сам забирает версию из ветки release

Шаг 1 плана спринта 7 (`2026-10-26-sprint-7-plan.md`). Решения владельца 26.10: пайплайн обновления сервера (решение 2); тестовой копии на сервере нет — правки проверяются на стенде, боевой сервер обновляется кнопкой в конце вехи (решение 3). Уточнение того же дня: под «тестом» владелец имел в виду ветку, как «дев — тест — прод»: дев — ветки PR, тест — `main` на стенде, прод — `release` на сервере. Опасение владельца — «надеюсь, он не сломается».

## Что было

Обновление — руками по SSH, каждый раз с «да» владельца: `git pull --ff-only` в `/opt/selfin`, `SELFIN_TAG=sha-<коммит>` в `.env` сервера, `./update.sh` — копия обеих баз, новые образы, перезапуск. Образы публикует `publish-images.yml` на каждое вливание в `main`: `sha-<7 знаков>` и `latest`, бэк и фронт — двумя независимыми задачами, так что пара `latest` может разъехаться (ревью Codex на #171). Что поднялось после обновления, проверялось глазами: `/api/v1/version` на сервере отвечает полным коммитом сборки — `1cf67531bf93…` на 26.10.

## Как

Три части, ключей в GitHub нет ни у одной: сервер сам читает открытый репозиторий и открытые образы. Так требуют правила владельца — «секреты — только владелец» и «ключ сервера никуда не переносится»; вариант «GitHub заходит на сервер по SSH» отпал по ним же.

### Кнопка — `.github/workflows/release.yml`, «Выкатить на сервер»

Запуск вручную (`workflow_dispatch`), коммит — по умолчанию голова `main`. Логика — `tools/release.mjs`, у неё тесты:

1. Коммит есть в `main` — иначе отказ.
2. Ветка `release` идёт только вперёд: коммит — её потомок или она сама. Назад кнопка не ходит: откат — забота сервера (ниже) или копии.
3. Коммит не старше того, чем отвечает сервер: первая кнопка или ручное обновление могли увести сервер вперёд `release`. Найдено сухим прогоном (раздел «Выполнено»): пока ветки `release` нет, кнопка пустила бы `d49d31e` на сервер с `1cf6753`. Сервер не отвечает — сверять не с чем, выкатка его и поднимет.
4. Оба образа `sha-<7 знаков>` опубликованы (`docker manifest inspect`). Нет хоть одного — отказ «подожди публикации», `release` не двигается.
5. `release` переводится на коммит (`git push`, только вперёд).
6. Кнопка ждёт, пока публичный `/api/v1/version` ответит этим коммитом, — до 15 минут, раз в 15 секунд. Итог прогона — зелёный или красный — виден в GitHub, и с телефона. Адрес сервера — секрет репозитория `SELFIN_PUBLIC_URL`: репозиторий и журналы прогонов открытые, а секрет в журнале замазан.

### Сервер — `deploy/release.sh` и таймер systemd

Таймер (`deploy/systemd/selfin-release.timer`) раз в 2 минуты запускает `deploy/release.sh`:

1. Коммит `release` — `git ls-remote`, без скачивания. Ветки ещё нет — «жду кнопку», выход без ошибки.
2. **Что работает — спрашиваем у самого сервера:** версия бэка через nginx экранов (`127.0.0.1:<SELFIN_HTTP_PORT>/api/v1/version`), как её видит человек. Совпала с `release` — дела нет. Не файл с «последней выкаткой»: восстановление из копии или ручное обновление его бы обманули.
3. Коммит уже не вставал (`.release-failed`) — дела нет: каждый повтор снимал бы копию, а сломанная версия сама не починится.
4. `git fetch`, checkout этого коммита в `/opt/selfin` — файлы `deploy/` той же версии, что образы; `SELFIN_TAG` в `.env`; `./update.sh` — копия, образы, перезапуск. `update.sh` не меняется.
5. Новая версия ответила за 5 минут — по часам, а не по числу попыток: пока бэка нет, nginx экранов тянет каждую попытку ещё на 5 секунд (раздел «Выполнено»). Бэк поднимается около 40 секунд. Ответила — готово, `.release-failed` убран.

**Скрипт живёт вне выкачанного дерева** — `/usr/local/lib/selfin/release.sh`, таймер зовёт его с `SELFIN_DEPLOY=/opt/selfin/deploy`. Ревью Codex на #202 (P1): первая выкатка уходит с `1cf6753`, а там скрипта ещё нет. Если она не встанет, возврат выкачает дерево `1cf6753` без `deploy/release.sh`, и таймер дальше звал бы несуществующий файл — исправленный коммит кнопкой было бы уже не выкатить. Новую версию себя копия берёт из дерева только после вставшей выкатки: копией рядом и переименованием, а не поверх, — оборвись копирование, таймеру останется прежний целый файл, а не половина нового. Тело скрипта — внутри функции, вызов — одной строкой: перепишут запущенный файл на месте (установка через `cp` поверх) — функцию оболочка уже прочла целиком.

### Не встала — что дальше

* Коммит записывается в `.release-failed` и больше не пробуется — до следующего сдвига `release`.
* **Миграций между прежней версией и новой нет** — сервер возвращается на прежнюю тем же путём: checkout, `SELFIN_TAG`, `./update.sh`, проверка версии. Сайт снова работает на прежней версии.
* **Миграции есть — сервер назад не идёт.** Flyway 11.14 старый бэк на новой схеме поднял бы: по умолчанию он пропускает «будущие» миграции (`ignoreMigrationPatterns = *:future`). Но старый код может не сойтись с новой схемой — например, с новым обязательным столбцом. Поэтому откат через миграции — только из копии (`deploy/RESTORE.md`, копия снята перед обновлением). План спринта 7 (шаг 1) писал, что Flyway старый бэк «не поднимет», — это не так; поправка — в срезе.
* Что работало до обновления, неизвестно (сервер не отвечал), — назад тоже не идёт.
* Кнопка в любом из этих случаев не дождётся новой версии и через 15 минут станет красной; причина — в журнале сервера: `journalctl -u selfin-release`.

### Установка — после вливания, с «да» владельца

1. Секрет `SELFIN_PUBLIC_URL` в репозитории — заводит владелец или я по его «да»: это адрес, а не ключ, но настройка его репозитория.
2. На сервере: `git -C /opt/selfin fetch origin` и checkout `main` с этой правкой — файлы появятся, контейнеры не тронутся; скрипт — `install -D -m 755 /opt/selfin/deploy/release.sh /usr/local/lib/selfin/release.sh`; файлы таймера — в `/etc/systemd/system/`, `systemd-analyze verify`, `systemctl daemon-reload`, `systemctl enable --now selfin-release.timer`. Файлы друга не трогаем.
3. Первый настоящий прогон — кнопкой, на коммит, который по коду фронта и бэка не отличается от работающего `1cf6753`: после него в `main` — только документы, инструменты и эта правка, а образы публикуются на каждое вливание. Миграций между ними нет — не встанет, сервер вернётся сам.

## Чего не делаем

* **Тестовую копию на сервере** — решение владельца 3.
* **Откат кнопкой назад.** Кнопка ходит только вперёд: откат без миграций сервер делает сам, с миграциями — только из копии. Понадобится чаще — отдельной правкой, со сторожем миграций в кнопке.
* **Watchtower и подобное.** Он обновляет контейнеры без копии перед обновлением и без файлов `deploy/` той же версии.
* **Замок `flock`.** Таймер systemd не запускает службу, пока прежний запуск не кончился; вручную — тоже через systemd: `systemctl start selfin-release`.
* **Уведомление об итоге на сервере.** Итог виден в прогоне кнопки; сайт целиком сторожит UptimeRobot (раздел 6 плана).

## Как мерил

* Код — на `main` `61e11a1`: `deploy/update.sh`, `deploy/docker-compose.yml`, `deploy/.env.example`, `.github/workflows/publish-images.yml`, `VersionController` — версия отдаётся как есть, из аргумента сборки `GIT_COMMIT`: у образов GHCR это полный коммит (`github.sha`), у стенда — тот, с которым его собрали (сейчас `fad2acf`).
* Сервер 26.10, только чтение: `free -m` — доступно 1 864 МБ из 3 911; контейнеры Selfin — около 1,1 ГБ; `/api/v1/version` по публичному адресу — `1cf67531bf93b9d5bc489fbace99fa3a4bac4049`.
* Flyway — 11.14.1 из зависимостей бэка: умолчание `*:future` — в `FlywayModel` (строка в классе); в `application.properties` шаблоны пропуска не заданы.
* Сухой прогон кнопки — `release()` с настоящими git (рабочая копия), `docker manifest inspect` и запросом к публичному `/api/v1/version`; `push` — заглушка, ожидание — один вопрос (`waitMs: 0`).
* Репетиция — сценарий в черновиках сессии: «origin» — голый репозиторий рядом, реестр `registry:2` на `127.0.0.1:5000`; compose — свой проект, образы из своего реестра, без Keycloak; поддельный бэк — `nginx:alpine`, который отвечает версией, сломанный — `CMD ["false"]`; экраны — настоящий образ `sha-1cf6753`. Время прохода — `date +%s` до и после, копии — каталоги в томе `backups`, версия — `curl` на порт экранов.

## Выполнено

**Тесты.** Инструменты — 190 из 190, из них 27 новых: 13 — кнопка (`tools/release.test.mjs`: подделки git, реестра и сервера), 14 — скрипт сервера (`tools/release-server.test.mjs`: заглушки `git`, `curl`, `sleep`, `date` и `update.sh`, запуск bash — как у тестов копий). Оба — в задаче CI «Инструменты — тесты».

**Мутации на итоговом коде** — 28 из 28 красные по имени теста, контроль зелёный.

* Кнопка, B1–B11: без проверки «из main»; `release` назад; проверяется один образ из двух; тег по полному коммиту; push и без сдвига; не ждёт сервер; молчание сервера — провал; голова не `origin/main`; без проверки адреса; ждёт бесконечно; сервер впереди — пускает.
* Сервер, S1–S17: нет ветки — идёт дальше; не сверяет работающую версию; повторяет не вставший коммит; без проверки `SELFIN_TAG`; тег не пишется; без проверки версии; не запоминает провал; без возврата; возврат и с миграциями; возврат без тега; провал не забывается; ждёт 2,5 минуты; порт зашит; возврат, когда прежняя неизвестна; тело не в функции; ждёт по числу попыток; ошибки curl в журнал.
* «Тело не в функции» первой редакцией теста выжила бы: подмена файла в 20 байт короче места, откуда оболочка читает дальше, — и оболочка просто дочитывала файл до конца. Подмена длиннее скрипта (7 200 байт против 4 400) — красная.
* B2 после проверки сервера выжила: её тест отказывал уже проверкой сервера. Тест разведён: сервер в нём отвечает старым коммитом.

**Сухой прогон кнопки, 27.10** — настоящие git, GHCR и публичная ручка версии, `push` — заглушка:

* голова `main` `61e11a1` — оба образа есть, `release` сдвинулась бы; сервер отвечает `1cf6753`;
* `966588d` (эта ветка) — «не из main», образы не спрашивались;
* `d49d31e` — **до правки кнопка её пустила бы:** ветки `release` ещё нет, а сервер уже на `1cf6753` — это откат сервера назад. После правки — «сервер уже на 1cf6753, а d49d31e старше». Отсюда проверка 3 раздела «Кнопка», тест и мутация B11.

**Репетиция на машине стенда, 27.10** — настоящие `deploy/release.sh` и `update.sh`, настоящий `docker compose` (как мерил — выше). Версии: C1 и C2 — рабочие, C3 — бэк не встаёт, C4 — не встаёт и между ней и C2 есть миграция.

Каждое обновление и каждый возврат — с копией перед ним; повтор не вставшего коммита копии не снимает.

**Нашлось на репетиции.** Ожидание «5 минут» длилось 9,5: пока бэка нет, nginx экранов ждёт его ещё 5 секунд на каждую попытку (`proxy_connect_timeout 5s`), и 60 попыток растянулись. Плюс 120 строк ошибок curl в выводе. Поправлено: ожидание — по часам, ошибки curl молчат. Тесты — поддельные часы и «медленный» curl, оба красные на прежнем скрипте. Итоговый скрипт на той же репетиции: C2 — руками, сломанная C5 без миграций — 340 секунд, «вернулся на C2», от скрипта ни одной строки curl. Одна строка — от копии перед возвратом: манифест спрашивает версию у бэка, которого нет, и пишет `unknown`; так копия вела себя и раньше.

**Чего не проверено.** Workflow на GitHub до вливания не запустить: `workflow_dispatch` видит файл только в ветке по умолчанию. systemd — только на сервере: при установке — `systemd-analyze verify`. Первый настоящий прогон — после вливания, с «да» владельца (раздел «Установка»).

**Ревью Codex на #202, первый круг (P1): возврат убирал скрипт из дерева.** Первая выкатка уходит с `1cf6753`, где `deploy/release.sh` ещё нет; не встань она — возврат выкачал бы дерево без скрипта, и таймер звал бы несуществующий файл. Codex проверил это `git ls-tree`. Поправлено: таймер зовёт копию вне дерева (`/usr/local/lib/selfin/release.sh`), а новую версию себя она берёт только после вставшей выкатки — переименованием. Тесты запускают скрипт копией вне дерева и относительным путём, как сам себя он и должен найти. Два новых теста — красные на прежнем скрипте: удачная выкатка заменяет скрипт версией из дерева; возврат на коммит без скрипта не мешает следующей выкатке. Тест подмены на ходу теперь переписывает сам запущенный файл — так бывает при установке через `cp` поверх.
