# ANO-232: просрочка и строки впереди — по дате, порядок не прыгает

Шаг 3 плана спринта 7 (`2026-10-26-sprint-7-plan.md`). Задача найдена 17.10 на живой проверке изоляции (шаг 1 спринта 6); в веху «4. Мелочи» её взял владелец 26.10 (решение 1).

## Что было

Главный экран, список «Осталось потратить», группа «раньше по плану» (в задаче она названа «Просрочено» — на экране имя другое). Стенд, 26.10: 14 строк просрочки, и идут они не по дате — 21.09, 21.10, 10.10, 31.08, 14.09… Два чтения подряд одинаковы, а после чужой записи порядок меняется: 17.10 «Ипотека» на 21.09 переехала с первого места на шестое, когда второй человек открыл свой `/pocket` (ANO-232).

Причины две, обе — выборки без порядка:

* **просрочка** — `FinancialEventRepository.findOverdueMandatoryExpenses` без `ORDER BY`: Postgres отдаёт строки в порядке хранения, а правка переписывает строку в конец таблицы. Тот же запрос даёт и «удержанную» просрочку (ANO-79), и имена в расшифровке строки просрочки;
* **строки впереди** — из `findAllByDeletedFalseAndDateBetween`, тоже без порядка; движок сортирует их только по дате (`futurePending`), а сегодняшние — никак. Одинаковые даты идут в порядке выборки.

Фронт не пересортировывает: `lib/upcoming.ts` полагается на то, что «движок отдаёт просрочку, затем даты по возрастанию». Для просрочки это было неправдой.

## Как

* **Просрочка:** `ORDER BY e.date, e.id` в самом запросе — одно место, через которое идут и просрочка, и удержанная просрочка, и расшифровка.
* **Строки впереди:** движок сортирует их одним разом перед списком (`PocketEngine.AHEAD_ORDER`): дата, потом `id`, а у взносов кармашка `id` нет — их имя.
* `id` — не смысловой порядок, а устойчивый: тот же набор строк всегда в том же порядке. Смысловой порядок внутри дня — подача, веха «5. Дизайн».

## Чего не делаем

* **Порядок дня по смыслу** (крупные первыми, по категориям) — подача, «5. Дизайн».
* **`ORDER BY` в выборке строк впереди** (`findAllByDeletedFalseAndDateBetween`): её зовут и другие места, а порядок нужен только списку движка — там он и задан.
* **Один порядок `uuid` у базы и движка.** Postgres сравнивает `uuid` по байтам без знака, `UUID.compareTo` в Java — половинками со знаком. Просрочку упорядочивает база, строки впереди — движок; это два разных списка, и каждый устойчив сам по себе.

## Как мерил

* Стенд 26.10 (`fad2acf`, по коду — `main` `a2e9c01`): `GET /api/v1/pocket` дважды подряд токеном тестового человека, строки `upcoming` с `overdue: true` — даты по порядку ответа.
* Код — на `main` `917ca42`: `findOverdueMandatoryExpenses`, `PocketInputAssembler.build` (выборки просрочки и строк впереди), `PocketEngine` (`todayPending`, `futurePending`, список `upcoming`), `lib/upcoming.ts`.
* Порядок `uuid` — по IT на настоящем Postgres: база вернула `02…`, `08…`, `09…`, `8a…`, `f1…`, а проверка через `UUID.compareTo` назвала это «не по порядку».
