# Категория в архиве видна в форме правки (ANO-178)

Блок B спринта 26.09, задача B3. Проявится при смене набора категорий (ANO-151): у всех событий убранных категорий форма правки станет показывать пустой выбор.

## Что сломано

Замер — раздел «Как мерил». Форма «Редактировать план» у события, чья категория удалена, показывает в поле «Категория» пустой выбор с подсказкой «Выберите категорию». Какая категория стоит — из формы не узнать.

Причина по коду: `EditEventSheet` берёт список через `fetchCategories()`, а `GET /categories` отдаёт только живые (`findAllByDeletedFalse`). Выбор получает `value = event.categoryId`, которого в списке нет, — Radix `Select` не находит элемент, и поле пустое.

При продолжении 27.09 проверено и сохранение: `PUT /events/{id}` с прежней архивной категорией возвращает **404 Category not found** на стенде `329fbe3`. В `resolveCategoryForUpdate` есть фильтр `!c.isDeleted()`. Первоначальное предположение о сохранении было неверным: нужно исправить и чтение, и запись.

## Решение

* **В выбор добавляется категория самого события, если её нет среди живых,** с пометкой «(в архиве)». Слово — из требования 4.4 (`2026-09-18-journal-categories-requirements.md`): категория не удаляется, а уходит в архив — исчезает из выбора при вводе, привязка старых записей не рвётся.
* Она стоит последней: выбрать её снова можно — это просто «оставить как было», — но новые записи в неё не попадут, быстрый ввод её не видит.
* Правило — в `lib/categoryChoices.ts`, форма его только рисует.
* До успешной загрузки списка категорий показывается текущее имя без пометки: отсутствие ответа не доказывает архивирование.
* При `scope=THIS` сервер разрешает оставить собственную архивную категорию события. Новая запись и переход на другую архивную категорию остаются запрещены. Для `FOLLOWING/ALL` категория правила уже сохраняется; это покрывается проверкой через HTTP и PostgreSQL.

Других форм с выбором категории у существующей записи нет: быстрый ввод создаёт новые записи, ему нужны только живые; экран категорий в «Настройках» работает со списком, а не с записью.

## Как мерил

* **Стенд** — `docker-compose.test.yml`, коммит — пробой `GET /api/v1/version`, в «Выполнено».
* **До и после — глазами**, экран стенда (5174): журнал → план с архивной категорией → «Редактировать план», поле «Категория».
* **Данные пробы — ручками экрана:** `POST /categories`, `POST /events`, `DELETE /categories/{id}` (в «Настройках» это «Удалить»). Возврат — удаление пробного плана ручкой; пробная категория остаётся в архиве, как любая удалённая.

## Чего не делаем

* **Переименование действия «Удалить» в «В архив»** на экране категорий — это требование 4.4, отдельная задача при смене набора категорий (ANO-151).
* **Имя категории на момент события** в отчётах (требование 4.5, пункт 1) — не эта задача.

## План

1. **Тест `lib/categoryChoices.test.ts`**, сначала красный: живая категория события — список как есть; категории события нет среди живых — она добавлена последней с пометкой; у события нет категории — список как есть; загрузка списка не выдаётся за архивирование. `ArchivedCategoryEditIT`: сохранение суммы и даты; запрет новых назначений архивной категории; переход на живую; повторения THIS/FOLLOWING/ALL.
2. **Код:** `lib/categoryChoices.ts`; `EditEventSheet` — выбор из него; `resolveCategoryForUpdate` — разрешение сохранить прежний id.
3. **Мутации** — по одной на каждое условие.
4. **Фронт целиком** — `npm test`, `npm run build`. **Сервер** — `mvnw verify`, включая Testcontainers.
5. **Стенд до и после**, глазами; возврат ручками.

## Продолжение 27.09 (Codex)

* Ruling: исправление охватывает сохранение собственного архивного id — воспроизведённый 404 не позволяет выполнить обещание формы «оставить как было». Ошибка решения могла бы разрешить новые назначения в архив, поэтому отдельный IT проверяет их запрет.
* Ruling: исходниковый сторож заменён тестами поведения списка и проверкой реальной формы в браузере — поиск имени функции в тексте не доказывает отображение. Связь формы с правилом дополнительно проверяется на стенде.
* Ruling: план Клода в этой спецификации ведётся здесь же, без нового плана и дублирующего журнала — сохраняем единую точку передачи для спринта. Результаты каждого этапа добавляются ниже.
* До: тестовый стенд `329fbe3c13fece5a9dccc62ca1de8d313670a8f4`; создан собственный пробный план 178 ₽, категория архивирована через API; изменение суммы на 179 ₽ вернуло 404. Данные пробы сохранены локально до очистки.
* Экран до: у пробного плана поле «Категория» пусто, хотя в записи осталось имя «Проба ANO-178»; подтверждено в браузере на 5174.
* RED: фронт — 3 проверки упали без дополнения списка; IT — 2 из 6 упали с 404 (обычный план и scope THIS у повторения). Ошибки уникальности имён тестовых категорий и сравнения JSON decimal в тесте исправлены до финального прогона.
* Код и тесты: фронт — 7 новых проверок; сервер — 6 HTTP-сценариев на PostgreSQL. `mvnw verify` exit 0: 451 unit + 204 IT, ошибок/провалов/пропусков 0. В конце JVM тестов принудительно завершилась после задержки shutdown 30 секунд; failsafe `timeout=false`, все результаты сохранены, это не пропуск тестов.
* Мутации: MF1 убрать дополнение — 3 провала; MF2 дублировать живую категорию — 1; MF3 добавить пустой id — 4; MF4 называть незагруженную категорию архивной — 1. Исходный фильтр сервера (MB1) — 2 провала; MB2 разрешить чужой архивный id — 1 провал (`rejectsNewAssignmentsToArchivedCategory`, 200 вместо 404). После мутаций исходники восстановлены.
* Фронт: 298 тестов зелёные, TypeScript и production-сборка прошли; образ тестового фронта собран.
* Независимое ревью итогового диффа (`c58bb2a`): подтверждённых дефектов нет. Первый запуск ревью упёрся в лимит; после команды владельца «продолжай» тот же ревьюер завершил проверку.
* Ограничение новых IT: для FOLLOWING/ALL проверяется ответ редактируемого события, а не каждый экземпляр серии; механизм регенерации не менялся, его отдельные тесты входят в полный `verify`.
* Ruling по ревью: прежнюю семантику исключений I10 и смену категории/даты всей серии не расширяем в ANO-178 — здесь сохраняется привязка к собственной архивной категории. Ошибка разграничения оставила бы отдельный дефект массовой правки; это ограничение явно передаётся дальше. Реальное отображение Radix и запись спринта проверяет основная сессия, а не статический ревьюер.
