# Цель копилки необязательна (ANO-199)

Блок A спринта 26.09, задача A0b. Ещё одна дорога к жалобе «не могу перевести в копилку» — поэтому сразу после A0a, решение владельца 27.09.

## Что сломано

Замер 27.09 на стенде `81323bf`, раздел «Как мерил»:

| шаг | что делает человек | что происходит |
|---|---|---|
| 1 | «Новый фонд», поле «Целевая сумма, ₽ (необязательно)» пустое | под формой «API error: 400 /funds — Validation failed», копилка не создана |
| 2 | копилка с целью 0 и без денег (на стенде «цукцку») | карточка «100%», под ним отдельный «0», «Накоплено 0 ₽ / 0 ₽» |
| 3 | цель 0, пополнить на 1 ₽ | «Цель достигнута», «100%», «0», «1 ₽ / 0 ₽»; из кнопок только «Редактировать» — пополнить больше нельзя |
| 4 | цель 100, накоплено 100, поднять цель до 200 | «Цель достигнута» при 50%, «100 ₽ / 200 ₽», кнопки пополнения нет |
| 5 | правка: стереть цель | 400 «targetAmount: must not be null» |

Шаг 4 найден при разборе: та же жалоба, другая дорога. Замер — комментарий в ANO-199.

Причины по коду:

* шаги 1 и 5 — `TargetFundCreateDto:25`: `@NotNull` стоит с первого коммита, 08.03 (`7715438`);
* шаг 2 — `Funds.tsx`, карточка: процент `fund.targetAmount ? … : 100` — пустая цель читается как полная; `{fund.targetAmount && <Progress/>}` при нуле рисует «0»;
* шаг 3 — `TargetFundService.applyStatusByBalance`: «достигнута», когда накоплено ≥ цели, а 1 ≥ 0;
* шаг 4 — `TargetFundService.update` меняет цель, а статус пересчитывает только при отвязке от счёта. Правило ANO-87 — статус выводится из накопленного и пересчитывается в обе стороны — правка цели обходит.

## Решение уже принято — в спеках

Развилка задачи — «цель действительно необязательна» или «поле перестаёт так называться». Ответ есть в документах:

* подпись «(необязательно)» появилась 16.03 (`cd71825`) вместе со спекой планировщика `2026-03-17-savings-strategy-planner-design.md`, где копилка без цели описана явно: «SAVINGS с `targetAmount = null` — никогда не завершается, нет маркера» (строки 67 и 191);
* модель данных `docs/specs/03-data-model.md:41` допускает `null`;
* остальной код копилку без цели поддерживает: статус (`applyStatusByBalance`), прогноз срока (`calcEstimatedCompletion`), резерв свободных денег (`PocketInputAssembler` берёт только копилки с целью и сроком).

Сервер просто не догнали: `@NotNull` старше подписи на восемь дней.

## Что делаем

| что делает человек | после правки |
|---|---|
| «Новый фонд» без цели | копилка создаётся без цели |
| цель 0 | то же, что без цели: «Цель достигнута» не бывает |
| пополнить копилку без цели | принимает деньги всегда |
| карточка копилки без цели | ни процента, ни полосы; строка «Накоплено 1 000 ₽» без «/ …» |
| поднять цель выше накопленного | статус снова «копится», кнопка пополнения возвращается |
| опустить цель до накопленного или ниже | «Цель достигнута» |
| стереть цель правкой | копилка остаётся без цели |

### Решено по ходу разбора

* **Ноль — «без цели», а не отказ.** В задаче названы обе дороги. Отказ сказал бы человеку «ноль нельзя», а ноль вводят как раз те, кто хотел копилку без цели: так её и обходили. Это правило 5. Хранится как ввели: ноль и пусто читаются одинаково.
* **Правило в одном месте — там, где выводится статус.** `applyStatusByBalance` считает цель заданной, только если она больше нуля. Тогда правило держат все пути, которыми копилка получает цель: форма, ручка, конверсия хотелки (`WishlistConversionService.buildSavingsFund` берёт цель из суммы хотелки, а она бывает 0), и старые записи.
* **Статус при правке пересчитывается у конверта, у копилки на счёте — нет.** У копилки на счёте поле баланса — не её деньги: остаток берётся со счёта (§3.3), а статус по балансу для неё не ведётся нигде — переводов в неё нет. Вывести его из поля значило бы решать по чужому числу. Как ей показывать «достигнута» — C11 (ANO-164, ANO-174).

## Как мерил

* **Стенд:** `docker-compose.test.yml`, `GET /api/v1/version` → `81323bf`. Это ветка A0a; по диффу с `main` она не трогает ни `TargetFundCreateDto`, ни `Funds.tsx`, ни `create`, `update` и `applyStatusByBalance` — поведение то же, что в `main`.
* **Шаги 1 и 2 — глазами**, экран стенда (5174): форма «Новый фонд» с пустой целью; карточка «цукцку» на «Целях».
* **Шаги 3–5 — ручками экрана:** `POST /funds`, `POST /funds/{id}/transfer`, `PUT /funds/{id}`; карточки — глазами после перезагрузки «Целей».
* **Возврат стенда — продуктом:** пробы удалены ручкой удаления с возвратом денег (`DELETE /funds/{id}?money=RETURN`). Свободно −1 600, капитал 2 668 277, копилок 11 — как до. В журнале остались пары «положил / вернул»: так продукт записывает удаление с возвратом.
* **Старые записи** — копилки с целью 0 в статусе «достигнута» — подсчёт запросом к базе, только число:

```sql
select count(*) from target_funds
where is_deleted = false and target_amount = 0 and status = 'REACHED';
```

На стенде — 0: единственная такая проба удалена. Боевая база остановлена с 25.09, не запускал.

## Чего не делаем

* **Старые копилки с целью 0 в статусе «достигнута».** После правки такая копилка оживает от любого сохранения: правка теперь пересчитывает статус. Массово — миграция, меняющая данные; сначала подсчёт запросом выше, решение — владельца.
* **Статус копилки на счёте** — C11 (ANO-164, ANO-174).
* **Остальные отказы форм «Целей»** — ставка и срок кредита вне границ по-прежнему покажут «API error: 400 /funds — Validation failed». Заведено отдельно: ANO-203.
* **Подачу карточки** не трогаю: без цели убирается то, что врёт, — процент, полоса, «/ 0 ₽» и «/ ∞». Новых элементов нет.
