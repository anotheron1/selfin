## Расхождение 1. Стратегия считает зафиксированную хотелку дважды

**Приоритет: высокий. Новая задача.**

### Измерено

Хотелка на 50 000 с датой через 45 дней. Баланс стратегии в её месяце:

```
до создания хотелки            −712 868
хотелка создана, статус OPEN   −762 868    сдвиг −50 000
хотелка зафиксирована, FIXED   −812 868    сдвиг ещё −50 000
```

Зафиксированная хотелка на 50 000 уменьшает стратегию на 100 000. И ещё до фиксации, в статусе «обсуждается», она уже учтена полностью.

### Корневая причина

`StrategyTimelineService` накладывает дельты зафиксированных хотелок поверх базовой линии:

```java
List<MonthDeltaDto> fixedDeltas = wishlistSimulationService.computeDeltaForFixedItems(...);
List<StrategyTimelinePointDto> overlaid = applyDeltas(snap.points(), snap.currentMonth(), fixedDeltas);
```

Наложение опирается на допущение, записанное прямо в комментарии `WishlistSimulationService.computeDeltaForFixedItems`:

```java
// WISHLIST LOW events contribute nothing to the baseline
// (no planned event/FACT), so only they are overlaid here.
```

**Допущение неверно.** Хотелка — обычный `FinancialEvent`: `eventKind = PLAN`, `status = PLANNED`, `priority = LOW`, с датой. В базовую линию она попадает как любое плановое событие, и наложение ложится вторым слоем.

Комментарий боялся задвоения для копилок и правильно их исключил — а для самих хотелок ошибся в обратную сторону.

### Вторая половина: два экрана спорят об одной хотелке

Кармашек хотелку в статусе «обсуждается» **не считает** — проверено блоком 8.1: создание не двигает кармашек ни на копейку, сумма уходит в информационную строку «хотелки-кандидаты (не вычтены)». Правило простое: намерение не есть трата.

Стратегия то же намерение вычитает полностью. Про одну хотелку два экрана отвечают по-разному, и оба молчат. Прямое продолжение ANO-89.

### Что решить

Развилка продуктовая:

1. Базовая линия исключает LOW-хотелки — как это делает кармашек через `allowedInTrajectory`, — наложение остаётся. «Обсуждается» перестанет влиять на стратегию, «зафиксировано» будет считаться один раз. Ближе всего к тому, что задумывал комментарий.
2. Наложение убирается, базовая линия остаётся. Тогда стратегия считает любую хотелку, включая необсуждённую, и расходится с кармашком навсегда.

Первый вариант согласует стратегию с кармашком. При починке проверить оба статуса и конверсию: сейчас конверсия ведёт себя правильно, сломать её легко.

### Не ловится тестами

Прогон зелёный. Проверка требует сравнить одно число до и после смены статуса — юнит-тесты на отдельные сервисы этого не делают.

## Расхождение 2. Факт через PATCH не доходит до стратегии — ANO-25 жив

**Комментарий в существующую задачу ANO-25.**

### Измерено

Два одинаковых факта по 4 400 в одну категорию и один день, записанных разными путями. Затем каждый снят, и замерено, на сколько просели отчёты:

```
                          аналитика   стратегия
факт напрямую (POST /events/facts)      −4 400      −4 400
факт через PATCH /events/{id}/fact      −4 400           0
```

Аналитика видит оба факта одинаково. **Стратегия факт через PATCH не видит вовсе.**

### Что это значит

В журнале факты равноправны: оба показаны, оба с суммой. В аналитике равноправны. В стратегии — нет. Способ записи определяет, попадёт ли трата в разбор длинного горизонта.

Это ровно ANO-25 и ровно то, что записано в памяти проекта как открытый вопрос ANO-12: в разбор стратегии попадают только события с `eventKind = FACT`, а `factAmount`, проставленный на PLAN-строке, туда не доезжает.

## Грабли прохода

`new Date(y, m, 0)` даёт локальную полночь последнего дня месяца, а `toISOString()` уводит её на день назад в MSK. Последний день месяца выпадал из сравнения, и это дало **шесть ложных расхождений** в блоке 9.7 — я едва не записал их в ANO-47. Дату надо собирать из локальных компонент:

```js
const iso = (d) => `${d.getFullYear()}-${String(d.getMonth() + 1).padStart(2, '0')}-${String(d.getDate()).padStart(2, '0')}`;
```

Проверено: после правки 9.7 сходится полностью.
