# Виновник узкого дня — категория, когда нет описания (ANO-95)

Блок C спринта 26.09, задача C10. Развязка — владельца, записана в задаче: описание → название категории → ничего.

## Что сломано

Замер 27.09 на стенде `329fbe3`, раздел «Как мерил»:

* **Дашборд, плашка разрыва** (горизонт «до 2-го дохода»): «Кассовый разрыв! 12 октября — ожидается дефицит 122 212 ₽». Из-за чего — не сказано.
* **День минимума, 12.10**, два плановых расхода: без описания на 8 000 (категория «Продукты») и «Бензин» на 3 300 (категория «Авто»). Крупнейший — без описания, `minPoint.drivenBy = null`.

То есть сценарий задачи от 5 сентября воспроизводится как есть: названный расход в этот день есть, а виновник не назван вовсе.

Причина по коду. `PocketEngine` берёт виновником описание крупнейшего планового расхода дня минимума (`dayTopExpense = e.description()`). Имени категории в снимке события нет — сознательно: имена категорий подставляет `PocketService.withCategoryNames` уже после расчёта, по id строк (ANO-119), чтобы не трогать ленивую связь на всей траектории.

**Где виновник на экране** — три места, все из `GET /pocket`: фраза карточки свободных денег (`lib/pocketPhrase.ts`), подпись минимума на графике (`buildMinAnnotation`), плашка разрыва на дашборде (`lib/watchdogAlert.ts`). Примерка его не показывает.

## Решение

Порядок подстановки — описание → категория того же расхода → ничего.

* **Движок запоминает id строки-виновника** — у главного минимума и у прогнозного: поле `drivenByEventId` в точке минимума. У синтетики (взносы копилок) id нет — она остаётся со своим описанием, именем копилки.
* **Сервис подставляет категорию**, если у виновника нет описания — пустого или из пробелов, — тем же приёмом, что имена в «осталось потратить»: один запрос по одному-двум id.
* **`drivenByEventId` виден в ответе** — как `id` у строк «осталось потратить»; фронт его не читает.
* **Фронт не меняется:** все три места уже показывают `drivenBy` в кавычках, если он есть: «12 октября — ожидается дефицит 122 212 ₽ («Продукты»)».

## Характер плановой строки

Не меняется: виновник выбирается, как раньше, — крупнейший плановый расход дня минимума любого характера.

## Как мерил

* **Стенд:** `docker-compose.test.yml`, `GET /api/v1/version` → `329fbe3` (ветка ANO-199). Кармашек в ней считается как в `main`: по диффу она не трогает ни `PocketEngine`, ни `PocketService`, ни `PocketInputAssembler`.
* **Числа — ручками, которые читает экран:** `GET /pocket?scope=SECOND_INCOME` (горизонт плашки разрыва) → `minPoint`; `GET /events` за день минимума — какие строки в нём.
* **Экран — текст дашборда**: плашка «Кассовый разрыв!».
* Данные стенда не трогал: пример есть в них самих.
* **До и после правки** (27.09, вторая сессия) — ответ `GET /pocket` целиком на всех четырёх горизонтах экрана: без `scope`, `SECOND_INCOME`, `MONTHS:3`, `MONTHS:6`. Сравнивался весь ответ, кроме `drivenBy` и нового `drivenByEventId`, — чтобы подстановка не сдвинула ни одно другое число. Экран — текст плашки на дашборде и подписи минимума на графике «2-й доход».

## Чего не делаем

* **Примерка** виновника не показывает — подстановку туда не несу.
* **Меньший названный расход не выбирается вместо крупнейшего безымянного:** порядок владельца — описание, потом категория того же расхода. «Продукты» на 8 000 объясняют разрыв лучше, чем «Бензин» на 3 300.
* **Текст фразы** не меняется: категория стоит в тех же кавычках, что описание.
* **День целиком не называем.** В комментарии задачи от 15.09 записана развилка: когда крупных расходов в дне несколько, называть день, а не один расход. Порядок владельца в описании задачи называет один расход — его и держу. Состав дня — ANO-98, тап по дню в календаре.
* **Справку «?» не трогаю.** Скобки с виновником были на экране и раньше, справка их не объясняла. Нового понятия или режима правка не вводит: меняется только, откуда берётся имя, когда описания нет.

## План

Шаги — тесты раньше кода; каждый тест красный до своей правки.

1. **Юнит `PocketEngineTest`:** день минимума с безымянным крупнейшим расходом — у главного минимума id этой строки, описания нет; то же у прогнозного минимума.
2. **Юнит `PocketServiceTest`:** через `getPocket` — безымянный крупнейший расход → виновник «Продукты»; с описанием — описание; описание из пробелов — категория. Подстановка у прогнозного минимума — отдельным тестом метода подстановки на готовом ответе: прогноз в сервисном тесте поднимать дорого.
3. **IT `PocketCulpritIT`:** `GET /pocket` на своём горизонте — безымянный крупнейший расход дня минимума → `drivenBy` = имя категории; с описанием — описание.
4. **Код:** `MinPoint.drivenByEventId` (старая сигнатура из трёх полей сохранена для примерки и тестов); движок — id рядом с описанием; `PocketService` — подстановка категории в обе точки.
5. **Мутации** на итоговом коде — по одной на каждое место.
6. **Прогон целиком**, стенд до и после.
