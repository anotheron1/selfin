## 2. Решения по шагам: зачем, почему так, как ещё было можно

### Шаг 1. Выкатка кнопкой

**Зачем.** Твои решения 2 и 3: обновлять сервер в конце вехи, без тестовой копии на нём. Ветки: дев — ветки PR, тест — `main` на стенде, прод — `release`.

**Как.** Кнопка двигает `release` только вперёд и только к коммиту из `main`, когда опубликованы оба образа. Сервер раз в 2 минуты сверяет `release` со своей версией и сам переходит на новую — сначала копия, потом обновление. Не встал — возврат, если между версиями нет миграций; есть — откат только из копии. Codex за четыре круга нашёл три вещи: скрипт должен жить вне выкачанного дерева (P1); восстановление ждёт идущий проход (P2); проход виден по `ActiveState`, а не по `is-active` (P2).

**Как ещё.** Пушить на сервер из GitHub по SSH — ключ к серверу ушёл бы в GitHub, а твоё правило — ключ никуда не переносить. Вебхук на сервере — открытый порт и лишняя поверхность. Руками, `update.sh` — как раньше: от этого и уходили.

### Шаги 2–4. Вкладка и порядок

Просрочка — по дате и `id`, копилки — по приоритету, времени заведения и `id`. Именно время заведения, а не имя: имя перетасовало бы весь список. Ручной порядок и порядок по сроку — подача, «5. Дизайн».

### Шаги 5–6. Слова вместо текста сервера

**Как.** Запись — `writeFailure`: «Не записалось — попробуйте ещё раз». Где повтор не поможет — свои слова. Что экран знает сам, он говорит до отправки: занятый счёт, планка выше лимита, природа приёмника. Остальное — после ответа, по статусу и по тому, что отправили: смена природы через кредитку, удаление счёта с копилкой. Текст сервера не разбираем. Сторож по исходнику: `.message` и `String(e)` — только в `api/client.ts`.

**Как ещё.** Код отказа в `details` у каждого ответа сервера — правка бэка в десятке мест; отложено, пока слов экрана хватает. Переводить английский текст сервера — нет: текст не договор, его поменяют, и перевод тихо сломается.

**Найдено.** Мест 20, а не 17: греп по `.message` не видел `reason(e)` и `String(e)`. «Новая хотелка» отправляла ставку 0 и срок 500 — кнопка стояла вне формы, браузер границы не проверял. Это и были примеры из описания ANO-203: до сервера они доходили не с «Целей», а с «Хотелок».

### Шаг 7. Даты восточнее Москвы

`latestAllowedIso` — местная дата, но не позже даты сервера. У журнала два «сегодня»: подпись дня — местная, кружок записи — по серверу. Пояс человека на сервере — эпик ANO-135, твоё решение 26.10. Замер — новым способом: часы страницы сдвинуты, а её местный календарь — по Екатеринбургу, сервер при этом живёт по настоящей Москве.

### Шаг 8. Четыре подписи

«Когда» у хотелки — «прошёл», «этот месяц», «через N мес» и строка «В расчёт не входит…». Сервер считает со следующего месяца, так что не входит и текущий — это нашлось при разборе. Сторож словаря научился основам с учётом регистра: «Budget» и «cash» ловятся, путь `/budget` и вид счёта `CASH` — нет. Другой путь — целые слова или исключения по виду строки — сложнее и ловит меньше.

### Шаг 9. Примерка с прошедшей датой

На 1-е следующего месяца, как карточка подставляет срок хотелке без срока. Подставляется только в запросе — в черновике дата своя, и «Зафиксировать» ждёт, пока её поставят в параметрах. Так держится смысл плана «подставленную дату молча не писать». Две посылки плана не подтвердились: у этой кнопки нет диалога, а на «Хотелках» нет справки «?». Codex нашёл, что срок «до реализации» шёл по исходным датам.

**Как ещё.** Переписать дату хотелки — запись без спроса. Отказать словами — правило 5 требует ответа и на устаревших данных.

### Шаг 10. «Вернуть в обсуждение»

Одна кнопка; дальше — прежний обработчик ANO-226, с вопросом, если есть созданное.

### Шаг 11. Копилка на месте

Зеркально «Кредиту»: ветка `FUND` копию не заводит. У хотелки-кредита копилка становится накоплением, а график снимается. Codex нашёл, что снимать нужно **до** смены вида: правило графика ищется у копилок-кредитов, и Hibernate сбрасывает смену вида в базу перед этим запросом. Юнит на моках это пропустил, IT на настоящей базе — красный на первой редакции. Копию с пометкой у исходной ты отверг 26.10 (решение 4).

## 3. Как работали

Тем же циклом: разбор → спека со сверкой по правилам → красные тесты → правка → мутации → стенд до и после → PR → Codex → ворота → вливание по одному «ок» на веху → комментарий в Linear → срез.

**Срезы — внутри PR следующей задачи** (твоё решение 27.10). Отдельных PR со срезом после #203 не было, и ожидания Codex на них — тоже.

**Замер через продукт без входа формой.** Прокси замера: страница — со стенда как есть, к API прокси сам добавляет токен тестового человека; пароль в форму не вводился. Обрыв связи — подменой `fetch`. Временные данные на стенде (ожидание «Бензин», «Проба ANO-237», копия «Горнолыжки») заводились под замер и сразу убирались; что стенд вернулся, проверялось запросом.

**Codex.** #202 — четыре круга (P1 и два P2, четвёртый чистый); #211 и #213 — по одному P2, исправлено, второй круг чистый; #201, #204–#210, #212 — 👍 с первого раза; #203 влит без Codex по твоему решению. Самый долгий круг — 84 минуты на #202; 08.11 круги шли по 10–15 минут. Новую голову Codex сам не смотрит — нужен `@codex review`, ворота подсказывают.

## 4. Что было трудно

* **Пауза в 11 дней посреди спринта.** Машина перезагружалась: контейнеры стенда стояли, scratchpad очистился, прокси замера пришлось написать заново. Дата ушла вперёд — на стенде прошёл срок ещё у одной хотелки.
* **Страница в скрытой панели.** Выпадающие списки — клавишами, анимации заморожены, графики не рисуются: подсказки графиков сверял по бандлу.
* **CRLF в рабочей копии.** Многострочные замены скриптом молча не ложились (хук «Что с капиталом», строки плана); каждый раз ловилось проверкой, переделывалось правкой через Edit.

## 5. Где цикл дал сбой

* **Шаг 9: две посылки плана о коде не подтвердились** — диалог у «Зафиксировать» в строке примерки и справка «?» на «Хотелках». План писался по памяти о коде. Это третий и четвёртый случай за два спринта (раздел 6).
* **Шаг 11: юнит проверял вызов запроса, а не результат в базе.** Ошибку порядка поймал Codex. Второй случай после «разорванная пара @Transactional прошла 408 зелёных» (раздел 6).
* **Шаг 6: в сообщении коммита — «21 место» вместо 20.** Пойман до пуша, сообщение исправлено.
* **Правка ревью #211: уборка после мутации через `git checkout` снесла и саму правку.** Пойман сразу по `git diff --stat`, правка внесена заново. Урок — восстанавливать сохранённым текстом, а не из git.
* **Старый отчёт `BackendApplicationTests` выглядел упавшим юнитом.** Исходника нет с `3e9d6dd6`, отчёт без `clean` лежит в `surefire-reports`. Проверено по истории, тревога ложная.

## 6. Правки процесса

По правилу 02.10 — только с доказательством.

| случай | цена | повторится |
|---|---|---|
| посылка плана о коде — по памяти: шаг 9 (диалог фиксации, справка «?»), спринт 6 — шаги 6.5 и 11 | решение правится на ходу; риск строить на том, чего нет; пока — без вреда | да: 4 случая за 2 спринта |
| юнит на моках проверяет вызов, а не результат в базе: шаг 11 (порядок со сбросом Hibernate), раньше — разорванная пара `@Transactional` | ошибка доходит до ревью или до человека; здесь поймал Codex | да: 2 случая |

**Предложение 1.** В подготовке спринта у каждой посылки шага о поведении кода — ссылка `файл:строка`, проверенная грепом в тот же день.

**Предложение 2.** Правка в сервисе, где запрос идёт после изменения сущности в той же транзакции, — IT на этот путь на настоящей базе, а не только юнит.

Решения — твои.

**К прошлому предложению** (обёртка над `gh pr create` против номера задачи в заголовке PR): в этом спринте случаев нет — ни одного на 13 PR. Новых доводов нет, решение по-прежнему твоё.
