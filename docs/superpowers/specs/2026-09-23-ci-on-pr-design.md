# CI на PR (ANO-26): что проверяем и как

Спека и план одним документом — задача короткая, два документа здесь лишние (ретро шага А, 9.5). Объём задан решением владельца 23.09: ретро, разделы 9.3 и 9.5-бис.

---

## 1. Зачем

* Десять PR прошлого спринта ушли в main на доверии к локальному прогону.
* Ограничение — токены, а не секунды. Прогон в CI токенов не стоит, поэтому полный набор уезжает туда, а в сессии гоняется только затронутое.
* Следующая большая миграция — владелец в 11 таблиц (шаг «в»). Проверка «миграция на данных» должна существовать раньше неё.

## 2. Четыре проверки

| проверка | что делает | что ловит |
|---|---|---|
| Фронт | `npm ci` → `tsc` → vitest | ошибки типов, фронтовые тесты, рассинхрон `package-lock.json` |
| Бэк | `mvnw verify` | юниты и интеграционные на Testcontainers; покрытие — строкой в сводке прогона |
| Образ фронта | `docker build frontend` | поломку `Dockerfile` и сборки vite — сейчас она видна только после вливания |
| Миграции на данных | образ бэка из main → синтетика через API → образ бэка из PR на той же базе → сверка файлов миграций с применёнными, отпечаток живых данных до и после, обход 21 ручки чтения | миграцию, которая падает на данных, а на пустой базе проходит; миграцию, которую Flyway молча пропустил из-за имени или каталога; миграцию, которая портит живые данные без единой ошибки — помечает удалёнными, прячет от чтения; образ бэка, который собирается, но не стартует; расхождение схемы и сущностей (`ddl-auto=validate`); код PR, который не может прочесть данные, записанные кодом main |

Образ бэка собирается внутри четвёртой проверки — отдельной сборки ему не нужно.

## 3. Миграции: почему дамп собирается на каждом прогоне, а не лежит файлом

Решение 9.3 говорит «дамп — синтетический или обезличенный, не боевой». Синтетический дамп можно держать двумя способами: (а) файлом в репозитории; (б) собирать самим продуктом на каждом прогоне. Выбран второй.

**Файл устаревает молча.** Дамп, снятый на V25, ничего не знает о таблицах V26. Миграция V27, которая двигает данные в этих таблицах, пройдёт на пустой таблице — и проверка скажет «зелёно». Переснимать файл после каждой миграции — ручная обязанность, а ретро записало, как такие обязанности протухают (9.5, ANO-129 числилась дырой через четыре дня после починки).

**Прогон «main → PR» проверяет ровно путь боевой базы:** база стоит на версии main, данные в ней записаны кодом main, поверх приходят миграции PR.

**Сеятель гоняется на каждом PR** — он не может сгнить незаметно, а заодно это смоук-проверка API main.

**Цена:** две сборки образа бэка и около минуты посева на прогон. Время ограничением не является (9.3).

Если файл всё-таки понадобится — например, для стенда, — его даёт тот же сеятель плюс `pg_dump`.

**Отпечаток живых данных и метка «меняет-данные»** (добавлено по ревью Codex, 23.09). Ручки, отвечающие 200, не доказывают, что данные целы: миграция, пометившая все события удалёнными, проходит обход ручек — списки просто пустые — и не меняет общее число строк. Поэтому до и после миграций PR снимается отпечаток: по каждой таблице — число живых строк (без помеченных удалёнными) и сумма каждого денежного столбца по ним, плюс сколько записей видно через API. Отпечаток строится по схеме, какая есть: новые столбцы и таблицы PR сравнению не мешают, пропавшие считаются изменением. Расхождение валит проверку. Если PR меняет живые данные намеренно — как V24 доплачивала выбывшие копилки, — на PR ставится метка «меняет-данные»: расхождение показывается в сводке, но проверку не валит. Молчаливое изменение — красное, осознанное — видно глазом.

**Сверка файлов миграций с применёнными** (тоже по ревью Codex). Flyway молча пропускает файл с неверным именем (`V26_x.sql` вместо `V26__x.sql`) и файл не в `db/migration`. Без сверки отчёт сказал бы «новых миграций нет», а боевая база изменения так и не получила бы. Скрипт сравнивает файлы миграций main и PR до запуска контейнеров, а после — требует, чтобы каждая добавленная версия нашлась в `flyway_schema_history`.

**Чего проверка не видит:** форм данных, которые создавал только старый код и которые сегодняшний API создать не может. Это закрывает репетиция на копии рабочей базы (ANO-154) — локально, в репозиторий не попадает.

## 4. Синтетика

`tools/seed-synthetic.mjs`, Node без зависимостей, как остальные инструменты в `tools/`. Пишет **только через API** — значит, создаёт только достижимые состояния и не даёт ложных красных на невозможных данных.

Что создаётся — по формам, на которых ломались миграции и расчёт:

* **счета:** основной из миграции плюс накопительный и наличные;
* **категории:** свои поверх стандартных; одна удалена после того, как на неё легли события (форма ANO-178); у одной сменена твёрдость;
* **сверки остатка:** две на основном счёте (ре-якорь), одна на накопительном;
* **история:** полгода зарплаты, аванса, ипотеки и связи — разовыми планами с фактами. Правило нельзя начать в прошлом (инвариант I3: `startDate must be today or later`), поэтому прошлое выглядит так, как у того, кто завёл цепочку не с первого месяца;
* **повторяющиеся правила — с сегодняшнего дня:** зарплата и аванс, ипотека на двадцать лет, связь на 31-е (прижимается к концу короткого месяца), бассейн со звеном на сегодня и фактом на нём (факт, унаследовавший правило, — форма V23); страховка раз в год; правка «с этого звена и дальше» (раскалывает правило — старый хвост уходит в удалённые), перенос одного звена, удаление одного звена;
* **разовые планы:** продукты понедельно и без описания (как у владельца: 99% таких строк без описания), кафе, мелкая хотелка;
* **факты:** полный, частичный, с превышением, два на один план, отдельный без плана, с выражением «1200+350», старый путь `PATCH /fact`;
* **копилки:** конверт с переводами, привязанная к счёту, кредитная, достигнутая, удалённая с возвратом денег;
* **хотелки:** открытая, зафиксированная без конверсии, отклонённая, сконвертированная в план, сконвертированная в копилку;
* **настройки:** буфер кармашка, пороги капитала;
* **капитал:** актив с переоценкой, пассив;
* **снимок бюджета** за текущий месяц.

Даты — от сегодняшнего дня, часовой пояс Europe/Moscow, как в боевом `docker-compose.yml`. Имена выдуманы, суммы круглые. Реальных данных нет нигде.

Сеятель берётся **из main, если он там есть**, иначе из PR — так первый PR (этот) загружает сам себя. Сеятель обязан соответствовать API того бэка, с которым говорит, а говорит он с бэком main.

## 5. Попутно

`backend/mvnw` лежит в git без бита исполнения (`100644`). На Linux `./mvnw` падает с Permission denied — CI споткнулся бы на первом шаге, и любой клон на Linux или Mac тоже. Бит выставлен в индексе.

## 6. Приёмка

* Зелёный прогон на этом PR.
* **Каждая проверка хотя бы раз красная на подсаженной поломке** — CI, который ни разу не краснел, ничего не доказывает. Поломки — в отдельном черновом PR, который не вливается, по одной на проверку, чтобы каждая краснела своей причиной:
  * падающий vitest-тест — краснеет «Фронт», образ фронта тесты не гоняет;
  * падающий юнит-тест — краснеет «Бэк», образ собирается с `-DskipTests`;
  * сломанный `frontend/Dockerfile` — краснеет «Образ фронта»;
  * миграция, которая падает, только если в `target_funds` есть строки, — на пустой базе интеграционных тестов она проходит, краснеть обязана одна «Миграции на данных».
* ANO-129 закрывается вместе с этой задачей.

**Не входит:** сделать проверки обязательными для вливания. Это защита ветки в настройках репозитория — решение владельца.

## 7. План

1. Спека — этот документ.
2. Бит исполнения у `mvnw`.
3. Сеятель; прогон на чистой базе локально.
4. Скрипт проверки миграций `tools/ci-migrations.sh` — вся логика в нём, чтобы гонялся и локально, и в CI; прогон локально.
5. Workflow `.github/workflows/ci.yml`.
6. PR, зелёный прогон.
7. Черновой PR с четырьмя поломками, четыре красных, закрыть без вливания.
8. Linear: ANO-26 и ANO-129 — комментарий и закрытие после вливания.

## 8. Выполнено

**Локальный прогон 23.09** — `tools/ci-migrations.sh` с одним и тем же образом main дважды, на чистом Postgres в своих контейнерах (боевые `selfin-*` не тронуты):

* посев — 141 запрос, ни одного не из 2xx после поправки ниже;
* в базе 12 таблиц; `financial_events` — 725 строк, из них живых 484. Остальные 241 — хвост ипотеки, который правка «с этого звена и дальше» увела в удалённые, расколов правило: `recurring_rule` — 6 строк при пяти заведённых правилах. Мягко удалённые строки в таком количестве — ровно та форма, на которой ломаются миграции с `NOT NULL` и уникальными индексами;
* обход ручек чтения — 21 из 21 ответили 200.

**Что нашлось сверх плана.** Первый посев упал: `POST /events -> 400: startDate must be today or later (I3)` — правило нельзя начать в прошлом. Спека в разделе 4 предполагала полгода истории на правилах; переписана: история — разовыми планами, правила — с сегодняшнего дня.

**Формула покрытия** проверена на локальном отчёте от 16.09: столбцы 8 и 9 `jacoco.csv` — `LINE_MISSED` и `LINE_COVERED`, итог 91,20% (2901 строка из 3181).

**Зелёный прогон на PR #51 (23.09):** все четыре проверки зелёные; 432 юнита и 168 интеграционных; посев в CI — 140 запросов, те же 484 живых события и 21 ручка из 21, что локально. По времени: фронт — 31 с, образ фронта — 1 мин 19 с, миграции — 2 мин 3 с, бэк — 3 мин 44 с. Сеятель взят из PR — в main его ещё нет, сработала ветка «загрузить сам себя».

**Приёмка на подсаженных поломках — черновой PR #52, закрыт без вливания.**

| прогон | поломки | фронт | бэк | образ фронта | миграции |
|---|---|---|---|---|---|
| 1 | все четыре | красный: шаг «Тесты» | красный: `CiMutationTest` | красный: `nginx-missing.conf` | красный: «миграция падает на заполненной базе» |
| 2 | только миграция V26 | зелёный | **зелёный** | зелёный | **красный** |

Второй прогон — главное доказательство задачи. Миграция, которая падает только на данных, прошла все 600 тестов: интеграционные накатили её на пустые базы (в логе — «Migrating schema to version 26» на каждый контекст) и остались зелёными. Покраснела одна проверка миграций на данных. В обоих прогонах #52 база PR — ветка #51, где сеятель уже есть, поэтому он взят из базы, а не из PR: проверена и вторая ветка выбора.
