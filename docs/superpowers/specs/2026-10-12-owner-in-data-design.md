# Владелец в данных: `user_id` в 11 таблиц и четыре замка схемы (ANO-145, ANO-146)

Шаг 3 спринта 5 (`2026-10-11-sprint-5-plan.md`, раздел 3). Обе задачи — один PR: замки снимаются той же миграцией, что вводит владельца. Спека и план одним документом. Факультатив — блок 6.

## Что есть сейчас

* **Владельца нет нигде.** Ни одна из двенадцати таблиц с данными не знает, чья строка. Второй человек невозможен физически — его не пустят четыре замка (ANO-146, проверены 11.09, перепроверены 12.10):
  1. `uq_accounts_single_default` (`V20`) — один счёт по умолчанию на всю базу: регистрация второго упадёт.
  2. Уникальное имя категории — второй не заведёт «Продукты».
  3. `user_settings` — одна строка настроек на ключ: буфер кармашка общий для всех.
  4. Сиды `V2` и `V20` — ничьи строки, они попадут к первому вошедшему.
* **Плюс глобальная уникальность `idempotency_key`** в `financial_events` и `fund_transactions`.
* **Ловушка Flyway подтвердилась на дампе стенда** (`stand-before-v29-2026-10-05.sql` — той же породы, что база владельца). История Flyway начинается с «Flyway Baseline» на версии 2: `V1` и `V2` там не выполнялись, схему когда-то завёл Hibernate. Поэтому имена ограничений расходятся:

  | что | свежая база (`V1`, тесты, CI) | база владельца и стенд |
  |---|---|---|
  | имя категории | `categories_name_unique` | `ukt8o6pivur7nn124jehx7cygw5` |
  | ключ события | `financial_events_idempotency_key_unique` | `uk8ah901xrytr2g6iijijfoeomu` или `uk4k0iv9ql6nf0rucnplt8jebo7` |
  | ключ движения копилки | `fund_transactions_idempotency_key_unique` | второе из этих двух |
  | ключ настроек | `user_settings_settings_key_key` | то же — `V18` выполнял Flyway |

  Миграция, снимающая ограничение по имени из `V1`, на базе владельца промахнулась бы, и второй человек упёрся бы в старый замок.

## Решение

* **Таблица `users`:** `id`, `external_id` — `sub` из токена, уникальный, у синтетического владельца пустой, — и `created_at`. **Синтетический владелец** нынешних данных — строка с постоянным id `00000000-0000-0000-0000-000000000001`. Связать его с `sub` владельца — ANO-195 (рекомендация плана — настройкой).
* **`user_id` в 11 таблиц** — все с данными, кроме `budget_snapshots` (решение 28.09): `accounts`, `balance_checkpoints`, `capital_items`, `capital_revaluations`, `categories`, `financial_events`, `fund_account_links`, `fund_transactions`, `recurring_rule`, `target_funds`, `user_settings`. В `fund_transactions` и `capital_revaluations` владелец денормализован, хотя выводится из родителя, — иначе фильтр по владельцу стоил бы соединения на горячем пути (ANO-145).
* **Одним оператором на таблицу:** `ADD COLUMN user_id uuid NOT NULL DEFAULT <синтетический> REFERENCES users`. План задачи предлагал четыре шага — колонка без `NOT NULL`, проставить владельца, `NOT NULL`, внешний ключ. Это общий путь для больших таблиц и вычисляемого заполнения. У нас значение постоянное, а Postgres с 11-й версии добавляет колонку с постоянным значением по умолчанию без перезаписи таблицы: старые строки получают его сразу. Миграция идёт одной транзакцией — либо владелец появляется у всех одиннадцати таблиц, либо ни у одной.
* **Значение по умолчанию — переход до шага 8** (план, шаг 3). Код записи не меняется: вставка без `user_id` получает синтетического владельца, как сейчас получает «ничью» строку. В шаге 5 оно станет «владелец транзакции, а без него — синтетический», в шаге 8 снимается: забытая запись тогда упадёт на `NOT NULL`, а не уйдёт молча синтетическому владельцу.
* **Сущности почти не трогаем.** `ddl-auto=validate` лишних колонок не замечает, сущность пользователя появится с ANO-195. Снимаются четыре пометки `unique = true` — имени категории, двух ключей и ключа настроек: уникальность теперь в пределах владельца, и пометка врала бы.
* **Четыре замка — по владельцу:**
  1. счёт по умолчанию — `UNIQUE (user_id) WHERE is_default AND NOT is_deleted`;
  2. имя категории — `UNIQUE (user_id, name)`;
  3. настройки — `UNIQUE (user_id, settings_key)`;
  4. сиды `V2`, `V20` получают синтетического владельца вместе со всеми строками; стартовый набор новому человеку — ANO-151.
* **`idempotency_key` — тоже по владельцу:** `UNIQUE (user_id, idempotency_key)` в обеих таблицах. Совпадение UUID клиента у двух людей практически невозможно, но глобальная уникальность связывает людей. После ограничителя (шаг 5) чужая строка не видна, а вставка с тем же ключом падает 409 — по отказу можно узнать, что такой ключ у кого-то есть. Ключ в пределах владельца — рыночная норма: так, например, у Stripe ключи действуют в пределах аккаунта.
* **Старые ограничения — по смыслу, а не по имени.** Миграция ищет в каталоге уникальные ограничения ровно по `categories(name)`, `financial_events(idempotency_key)`, `fund_transactions(idempotency_key)`, `user_settings(settings_key)` и снимает найденные. Если после этого уникальность ровно по такой колонке осталась — например, уникальным индексом, а не ограничением, — миграция падает, а не оставляет замок молча.
* **Индексы — у каждой таблицы ведущий `user_id`:** у четырёх его дают новые уникальности, у остальных семи — индекс `(user_id)`; у событий ещё `(user_id, date)` — журнал и расчёт выбирают их периодом. Под внешний ключ и под фильтр владельца, который добавит ограничитель. Другие — по замеру, когда людей станет больше четырёх.
* **Метка «меняет-данные»** — миграция проставляет владельца каждой строке.

## Не входит

* Ограничитель изоляции (RLS) — шаг 5; владелец в записи и в запросах — шаги 7 и 8; ссылки по владельцу — шаг 8.
* Системные категории по владельцу — шаг 9 (ANO-150). `CategoryService.systemCategory` ищет по имени без владельца; при двух людях запрос вернул бы две строки, но до ограничителя (шаг 5) человек один, а с ним база отдаёт только свои.
* Связь синтетического владельца с `sub` и сущность пользователя — шаг 4 (ANO-195). Стартовый набор при регистрации — шаг 10 (ANO-151).
