### Шаг 1. ANO-143 — Keycloak и вход через Telegram

Решения владельца 11.10: Keycloak — потому что рыночный стандарт, даже если нам он избыточен; первым — Telegram; Яндекс ID и VK ID — позже.

* **Telegram — обычный OIDC-провайдер Keycloak.** У Telegram теперь стандартный OpenID Connect: discovery `https://oauth.telegram.org/.well-known/openid-configuration`, Authorization Code + PKCE, ID token — JWT, отдельного userinfo нет ([документация](https://core.telegram.org/bots/telegram-login); Keycloak в ней назван прямо). Своего кода в Keycloak не нужно. Часть 12 артефакта «Кто вы и что вам можно» об этом устарела.
* **Что входит:** Keycloak рядом с нашим compose, своя база; реалм `selfin` как код — импорт при старте; провайдер Telegram; первый вход — регистрация в Keycloak.
* **Готово, когда** на стенде «Войти через Telegram» → подтверждение в Telegram → человек вернулся в Keycloak залогиненным; реалм воспроизводится из репозитория одной командой.
* **Решить в задаче:** версия Keycloak; его база — отдельная база в нашем Postgres или свой контейнер (рекомендация для стенда — отдельная база в том же контейнере; для сервера — в «Выкладке»).
* **Проверить первым:** принимает ли @BotFather `localhost` в Allowed URLs. Если нет — туннель или домен. **Проверено 13.10:** `localhost` не принят, `127.0.0.1` принят — туннель не нужен, адрес стенда по умолчанию — `127.0.0.1` (#145).
* **У владельца:** бот в @BotFather, Allowed URLs, Client ID и Secret — в `.env` (он в `.gitignore`). Секрет в репозиторий, спеки, комментарии и чат не попадает.

### Шаг 4. ANO-195 — сервер узнаёт владельца

* **По Р-1 = Б:** вход идёт через наш сервер — `oauth2Login`, конфиденциальный клиент реалма; токены — в сеансе на сервере, обновляет их сервер; CSRF включён.
* **Скрипты и CI ходят по Bearer — своей цепочкой фильтров:** без сеанса и без CSRF, с проверкой JWT и **собственной аудиторией selfin** — её вписывает в токен audience mapper в реалме, и сервер сверяет ровно её. `account` в токене `account-console` (замер блока 3) — аудитория встроенной консоли Keycloak, не наша: такой токен сервер отвергает (ревью Codex на #147).
* **Минимальный вход фронта — в этой же задаче**, иначе экран получит 401 и 403 на всём до ANO-152 (ревью Codex на #147):
  * на 401 — уйти на вход;
  * CSRF: сервер кладёт токен в cookie, которую читает JS (`XSRF-TOKEN`), а `client.ts` возвращает его заголовком `X-XSRF-TOKEN` на каждый POST, PUT, PATCH и DELETE — без этого сеанс отвергнет любую запись;
  * **адреса входа и выхода — на сервер:** в проде nginx (`frontend/nginx.conf`) проксирует сейчас только `/api/`, а `/oauth2/…`, `/login/oauth2/…` и `/logout` отдал бы фронту — вход не начался бы; в разработке — прокси Vite на те же адреса;
  * **`VITE_API_URL` в `.env.development` — убрать:** абсолютный `http://localhost:8080/…` идёт мимо прокси Vite, без cookie сеанса и CSRF; `client.ts` тогда берёт относительный `/api/v1` (ревью Codex на #147).
* `sub` → строка пользователя; владелец запроса — оттуда. Открытые адреса — проверка здоровья и `/version`.
* **Связать синтетического владельца с `sub` владельца** при его первом входе — здесь: в шаге 3 синтетический владелец заведён с пустым `external_id` (#146). Рекомендация шага 3 — настройкой.
* **Ломает всё, что зовёт API без токена:** сеятель CI (`tools/seed-synthetic.mjs`, `tools/ci-migrations.sh`), скрипты стенда `tools/ano50-*.mjs`, все IT. Решить: в IT — `spring-security-test`; в CI и на стенде — Keycloak с тестовым реалмом или тестовый профиль без проверки (артефакт, часть 11: правда против цены). Рекомендация — тестовый реалм: сеятель ходит как настоящий клиент.
* Сеятель ветки гонять на образе ветки до PR — комментарий в ANO-135.
* Факультатив — блоки 3 и 4.

### Шаг 5. ANO-144 — ограничитель изоляции

До первой правки запросов: пропущенный фильтр должен падать, а не отдавать чужое. Рекомендация задачи — RLS в Postgres: ловит и `nativeQuery`.

* **Владелец транзакции — владелец запроса из шага 4.** Ограничитель включается, когда сервер уже знает, чьи данные просят (ревью Codex на #143): раньше у политики не было бы владельца, и чтение между PR видело бы пустую базу.
* **Ловушка, найдена 11.10:** приложение ходит в базу пользователем `admin` (`application.properties`, `docker-compose.yml`). Образ Postgres заводит его суперпользователем, а суперпользователь обходит RLS всегда — политики были бы, а защиты нет. Значит, нужна роль приложения: не суперпользователь, без `BYPASSRLS`, не владелец таблиц (или `FORCE ROW LEVEL SECURITY`). Миграции — прежней ролью, приложение — новой.
* Тесты на Testcontainers тоже ходят суперпользователем — без своей роли тест изоляции зелёный вхолостую.
* Пул соединений: владельца ставить на транзакцию (`set_config(…, true)`), не на сессию — иначе соединение из пула унесёт чужого владельца в следующий запрос.
* Решение здесь меняет объём шагов 7 и 8: при RLS чтение фильтрует база, явный фильтр в запросах — второй слой и индексы.
* Факультатив — блок 7.

### Шаг 8. ANO-147 — второй слой: `@TenantId`, ссылки по владельцу, тест в обход RLS

1. **Сначала — проверка на нашем коде.** `@TenantId` на `user_id`, резолвер — `OwnerContext`. В Hibernate 7.2.4 нашей сборки он регистрирует фильтр `_tenantId` на сущности и сам ставит владельца при вставке (`TenantIdBinder`, `TenantIdGeneration`); у резолвера есть «корень» (`isRoot`), которому видно всё. Проверить: тип UUID; производные методы, `@Query`, `@Modifying`-обновления; загрузку по id и ленивые связи; что без владельца. Не ляжет — руками, как было в плане.
2. **`@TenantId` на 11 сущностях.** Правило приёмки остаётся — каждый метод поимённо: под фильтром Hibernate, с владельцем в запросе явно или в списке «только RLS». Нативный `CapitalRevaluationRepository.snapshotAt` фильтр Hibernate не получит — владелец в нём пишется явно, в таблице переоценок и в соединении с предметами (`r.user_id` и `i.user_id`): иначе второй слой в нём пуст. В списке «только RLS» остаётся `JdbcTemplate` по таблице `users` (`OwnerService`), у которой владельца нет.
3. **Ссылки — составные внешние ключи `(user_id, id)`** во всех связях: одно правило в схеме; закрывает `targetFundId` (замер — комментарий в ANO-147) и любую будущую ссылку. Тест шага 6 дополнить записью со ссылкой на строку другого человека.
4. **Второй слой проверяется отдельно:** `TwoPeopleIsolationIT` ещё раз — с пулом в обход RLS, весь оракул. Зелёный там — `@TenantId` и явный владелец в нативном запросе держат изоляцию сами. Без п. 2 для `snapshotAt` этот прогон покраснеет на сводке и траектории капитала: в обход RLS нативный запрос сложит предметы обоих людей (ревью Codex на #154).
5. **Значение по умолчанию у `user_id`** (синтетический владелец для роли владельца таблиц) — решить здесь: при `@TenantId` владельца ставит приложение.
6. Факультатив — блок 8; стержень — артефакт по Hibernate 6+ (раздел 6).

### Шаг 8а. ANO-229 — приложение не стартует под ролью, которая обходит RLS
